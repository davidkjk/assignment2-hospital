# 직원웹 갭 지도 — 실제 앱(frontend/) ↔ 데모(demo/) ↔ 정본 (2026-08-28)

> **왜 이 문서**: 실행 중인 직원웹이 데모와 다르고 "안 되는 게 많다"는 사용자 관찰을, **화면별로 근거를 갖고** 분류한다.
> **분류 범례**: `①배선`=지금 이으면 닫힘 · `②환자앱/배포 대기`=3단계(환자앱)·배포가 있어야 진짜 작동(놔둠, 환자앱 착수 시 자연 해소) · `③시각`=데모 룩과의 시각 갭(목표=`demo/DESIGN-NOTES.md` 직원 콘솔 정체성) · `🐞`=진짜 버그.

## 0. 가장 큰 "빈 곳" — 사실은 범위 밖 (실패 아님)

- **사이드바 21항목 중 7개가 상담봇(4단계) 화면** — frontend에 페이지가 **아예 없음** → 클릭 시 `Placeholder`("본문은 후속 화면 태스크에서 연결됩니다"):
  - 업무: `/tickets`(상담봇 문의함) · 기록: `/chatlog`(상담봇 기록) · **상담봇 관리 그룹 5개**(`/bot/knowledge·unresolved·reports·quality·overview`).
  - 이건 **4단계(ai-chatbot 플랜)** 소유라 직원웹(2단계)에서 안 지은 게 정상. 데모엔 있으나(같은 사이드바) 우리 구현 범위 밖.
  - **선택**: 시연 동안 이 7개를 **사이드바에서 숨기거나** placeholder를 "상담봇 단계에서 제공" 문구로 바꾸면 "안 됨" 인상이 크게 준다(작은 배선).
- **헤더 「세 문」(등록·접수·예약) 패널 = placeholder aside**(`AppShell.tsx:44` "업무 패널 내용은 다음 공통 패널 태스크에서 연결됩니다") → `①배선`(CheckInPage·WalkInPanel·PhoneBookingPanel은 이미 있음, 문에 연결만).

**핵심**: 지은 17개는 **전부 실 백엔드에 물려 동작**한다. 남은 갭의 대부분은 `②`(환자앱/배포 대기)이고, `①`(배선)은 수가 적고 국소적이다. `🐞` 진짜 버그는 거의 없다(방금 고친 인증 ES256·채널 push_sms 외).

## 2. 교차 항목 (여러 화면 공통)

- `①` **헤더 세 문 패널 배선** — 등록/접수/예약 문 ↔ 기존 CheckInPage·WalkIn·PhoneBooking 연결.
- `①` **화면 간 이동 배선** — /today 카드·/checkin 결과 → /queue 하이라이트 등.
- `①` **백엔드 응답 필드 몇 개** — 캘린더 막대 DTO(birth_date·visit_type·slot_duration), 환자상세 sms_dead, 큐 updated_at.
- `③` **시각 정체성 통일** — 목표는 `DESIGN-NOTES`: **딥틸 잉크 사이드바(#0a4a4c)·각지고 촘촘한 패널(얇은 경계+미세 그림자·rounded-xl)·업무용 밀도(text-sm·py-2.5)·헤더 하단 실선**. 지은 앱은 Task0 토큰으로 화면별로 지어 **일관성/폴리시가 데모보다 낮음** → 화면별 폴리시 패스 필요(demo/staff 라우트 = 시각 참고).

## 3. 방향 권고 — A안(지은 frontend 유지·다듬기)

- **B안(데모를 실 프론트로 승격)은 비효율**: 데모 staff 라우트는 목업 데이터 시각 프로토타입이라, 승격하면 **17개 화면의 실 백엔드 배선·인증·마스킹·에러상태·react-query·RLS를 전부 다시** 얹어야 한다 = 이미 있는 것을 재작성.
- **A안 권고**: 지은 frontend는 **17개 화면 전부 실 배선+규칙 커버리지 완비**. 여기에 (1)`①` 배선 마무리, (2)`③` 데모 룩으로 시각 폴리시 패스(DESIGN-NOTES 목표·demo 참고), (3)`②`는 **환자앱(3단계) 지으면 자연 해소**라 놔둠. **데모는 A안에서 시각 참고로 제 역할을 한다**(그동안 "참고 안 됨"은 규칙-우선으로 지어 시각 충실도가 낮았던 것 — 폴리시 패스가 그걸 메움).
