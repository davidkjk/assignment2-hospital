# 병원 통합 서비스 문서 정합성 통합 리포트 (2~5차)

검토 기준: `고객요구사항.txt`, 1~5단계 스펙·구현 계획.

통합 범위: `consistency-review-2026-07-28-round2.md`부터 `round5.md`까지.

제외 범위: 버전 1인 `consistency-review-2026-07-28.md`의 내용은 이 문서에 포함하지 않았다.

## 1. 통합 결론

2~5차 검토에서 확인된 이슈는 총 24건이다.

- P0(배포 전 반드시 차단해야 하는 보안·데이터 무결성 문제): 4건
- P1(핵심 기능·운영 규칙이 실제 동작과 어긋나는 문제): 17건
- P2(보조 흐름·감사·운영 관리의 완성도 문제): 3건

가장 먼저 막아야 할 P0 문제는 다음 네 가지다.

1. 환자가 다른 환자의 예약 슬롯을 빈 슬롯으로 되돌릴 수 있음
2. 의사가 본인 담당이 아닌 환자의 예약·진료정보를 볼 수 있음
3. 승인된 챗봇 지식자료의 수정본이 재승인 없이 즉시 공개됨
4. 환자가 임의의 다른 환자를 자기 가족으로 연결할 수 있음

Superpowers 워크플로우에서는 24건을 모두 최종 구현 계획에 반영해야 한다. 다만 14건은 먼저 `brainstorming`에서 정책·권한·업무 규칙을 결정해야 하고, 나머지 10건은 이미 요구와 해결 방향이 명확하므로 브레인스토밍을 다시 하지 않고 `writing-plans`에서 구현 작업과 테스트만 보강하면 된다.

## 2. Superpowers 워크플로우 적용 기준

### 2.1 brainstorming에서 수정해야 하는 것

다음 항목은 여러 합리적인 선택지가 있거나 병원 정책을 확정해야 하므로, 구현 계획보다 먼저 디자인 스펙에서 결정해야 한다.

| ID | 결정해야 할 내용 | brainstorming 산출물 |
|---|---|---|
| R2-02 | 의사·접수직원·관리자가 볼 수 있는 환자정보 범위 | 역할별 접근권한 표와 예외 상황 |
| R2-04 | 예약·방문·취소·부도 통계가 어느 날짜를 기준으로 하는지 | 지표별 기준일 정의 |
| R2-05 | 상태 변경 알림의 발생 시점, 가족 예약의 수신자, 중복 방지 원칙 | 알림 이벤트·수신자 표 |
| R2-06 | 일반 상담과 의료판단 티켓을 누가 배정·답변할 수 있는지 | 티켓 유형별 담당 역할과 재배정 규칙 |
| R3-01 | 하루 최대 예약 수·예약 마감 변경 시 기존 미래 슬롯을 어떻게 처리할지 | 예약 가능성 규칙과 재계산 정책 |
| R3-02 | 점심·휴진·특정일 일정 변경 시 기존 예약을 보존할지, 재예약할지 | 일정 예외와 영향 예약 처리 정책 |
| R4-01 | 승인 지식자료 수정 시 기존 공개본 유지 또는 즉시 비공개 중 어느 방식을 쓸지 | 지식자료 버전·승인·공개 상태 모델 |
| R4-03 | “내 앞 대기 인원”을 어떤 환자·상태·의사 범위로 계산할지 | 대기 인원 산식과 갱신 조건 |
| R4-04 | UUID를 예약번호로 쓸지 사람이 읽기 쉬운 별도 번호를 만들지 | 예약번호 형식과 QR 접수 흐름 |
| R5-01 | 가족을 새 프로필로만 추가할지, 기존 환자와도 본인확인 후 연결할지 | 가족 등록·동의·본인확인 흐름 |
| R5-02 | 가족 연결 해제 후 과거 예약 보존과 접근권한 제거 범위 | 연결 해제·보존 정책 |
| R5-05 | 전화예약 환자와 앱 계정을 자동 연결할 조건과 동명이인 처리 | 신원 일치·직원 확인·실패 처리 흐름 |
| R5-06 | 목록에서 전화번호·생년월일을 어느 형식으로 가리고 어디서만 원문을 보여줄지 | 화면별 마스킹·감사 기준 |
| R5-09 | 진료과별 문진 양식의 활성 버전, 수정·중지, 과거 응답 보존 방식 | 문진 양식 버전 정책 |

### 2.2 brainstorming에서 수정하지 않아도 되는 것

아래 10건은 고객 요구 또는 기존 스펙에 이미 기대 동작이 명확하다. 같은 결정을 다시 토론할 필요 없이 `writing-plans`에서 누락된 구현과 검증 절차를 추가하면 된다.

| ID | 이유 | writing-plans에서 바로 할 일 |
|---|---|---|
| R2-01 | 다른 환자의 슬롯을 변경하면 안 된다는 보안 원칙이 명확함 | 슬롯 잡기·반납 보안 함수와 RLS 테스트 추가 |
| R2-03 | 대기 시작 시각을 순서 변경 시각과 분리해야 함이 명확함 | `waiting_started_at` 또는 상태이력 기준 구현 |
| R2-07 | 오늘 현황은 오늘 진료할 예약을 세어야 함이 명확함 | 슬롯 날짜·병원 시간대 기반 쿼리로 교체 |
| R3-03 | Realtime을 쓰려면 publication 등록이 필요함 | 마이그레이션과 실제 환경 구독 테스트 추가 |
| R3-04 | `/admin/staff` 화면은 스펙에 이미 있음 | 화면·API 클라이언트·E2E 작업 추가 |
| R4-02 | 진료기록 완료와 예약 완료가 함께 처리되어야 함 | 단일 트랜잭션과 멱등성 테스트 추가 |
| R5-03 | 도착 뒤 문진은 읽기 전용이라는 규칙이 이미 있음 | 직접 UPDATE·DELETE 차단 정책 추가 |
| R5-04 | 익명 사용자의 공개 진료과·시간 조회 허용이 이미 정해짐 | 공개 카탈로그 서비스와 익명 통합 테스트 추가 |
| R5-07 | 직원 웹 폴더를 하나로 통일하면 되는 문서 경로 오류임 | CI·Vercel·계획의 경로를 일괄 통일 |
| R5-08 | 진료기록 열람 시 감사로그를 남긴다는 요구가 이미 있음 | 모든 조회 API에 감사 기록 연결 |

### 2.3 writing-plans에서 수정해야 하는 것

24건 모두 구현 계획에 반영해야 한다.

- brainstorming 대상 14건: 확정된 디자인 결정을 구현 태스크, 데이터 변경, API 계약, 화면 상태, 오류 처리, 테스트로 번역한다.
- brainstorming 불필요 대상 10건: 아래 통합 이슈의 권고안을 바로 구체적인 구현 태스크와 테스트로 작성한다.
- 각 작업에는 수정 파일 경로, 마이그레이션 순서, 실패 시 동작, 자동화 테스트를 포함한다.
- P0 4건은 다른 기능 작업보다 먼저 실행하도록 계획의 선행 조건으로 둔다.

### 2.4 writing-plans에서 수정하지 않아도 되는 것

이 통합 리포트의 24개 이슈 중 구현 계획에서 생략해도 되는 이슈는 없다. 다만 다음 작업은 writing-plans 단계에서 하지 않는다.

- brainstorming에서 확정한 정책을 다시 선택지 상태로 되돌리지 않는다.
- 실제 코드를 구현하지 않는다. writing-plans의 목적은 실행 가능한 작업 순서와 검증 방법을 만드는 것이다.
- 제외하기로 한 버전 1의 이슈를 이 통합 범위에 다시 섞지 않는다.
- 이미 요구가 명확한 10건을 이유 없이 다시 brainstorming으로 되돌리지 않는다.

## 3. 통합 이슈 목록

### 3.1 P0 — 배포 전 반드시 수정

#### R2-01. 다른 환자의 예약 슬롯을 빈 슬롯으로 되돌릴 수 있음

- 근거: 환자 RLS(Row Level Security, 행 단위 보안)는 모든 로그인 환자에게 슬롯의 `빈시간`/`예약됨` 상태 UPDATE를 허용하고, 해당 슬롯 예약의 소유자를 확인하지 않는다(환자 앱 계획 101~104).
- 영향: 다른 환자의 예약 유실, 이중예약, 운영 일정 훼손이 가능하다.
- 수정: 환자의 `appointment_slots` 직접 UPDATE를 막는다. 보안 정의 RPC 또는 서버 트랜잭션에서 계정 소유자, 예약 상태, 슬롯 상태를 함께 확인한 뒤에만 슬롯을 잡거나 반납한다.
- 검증: 환자 A가 환자 B의 예약 슬롯을 직접 `빈시간`으로 변경하려 할 때 데이터베이스 수준에서 거부되는지 확인한다.

#### R2-02. 의사가 본인 담당이 아닌 환자정보를 볼 수 있음

- 근거: 현재 직원이면 모든 예약·진료기록·수정이력을 SELECT할 수 있고, 대기목록 API에도 의사 필터가 없다(기반 계획 678~680, 851~853, 864~866; 직원 웹 계획 3163~3175).
- 영향: “의사는 본인의 오늘 환자만 조회”하는 요구와 역할별 개인정보 접근 원칙을 위반한다.
- 수정: 의사는 `appointments.doctor_id = 자기 staff.id`인 예약과 연결된 문진·기록·수정이력만 조회하도록 RLS와 API를 함께 제한한다. 접수직원·관리자의 넓은 권한은 역할표로 별도 정의한다.
- 검증: 의사 A가 의사 B의 예약·문진·진료기록·수정이력을 직접 조회와 API 조회 모두에서 받지 못하는지 확인한다.

#### R4-01. 승인 지식자료 수정본이 재승인 없이 즉시 공개됨

- 근거: `update_document`는 기존 승인 상태를 유지한 채 내용을 갱신하고, 승인 문서이면 즉시 청크와 임베딩을 다시 만든다(챗봇 계획 925~952). 챗봇은 `approved` 문서를 검색 대상으로 삼는다(챗봇 스펙 90).
- 영향: “수정 내용을 관리자가 확인한 뒤 적용”한다는 요구를 위반하고, 검수되지 않은 의료·운영 안내가 즉시 답변에 사용된다.
- 수정: 기존 공개본과 수정 초안을 버전으로 분리하거나, 수정 즉시 `draft`로 돌려 검색 대상에서 제거한다. 승인 작업에서 새 검색 조각을 원자적으로 교체한다.
- 검증: 승인된 안내를 수정한 뒤 재승인 전에는 기존 승인 문구만 답하고, 승인 후에만 새 문구로 교체되는지 확인한다.

#### R5-01. 임의의 다른 환자를 자기 가족으로 연결할 수 있음

- 근거: 가족 링크 INSERT 정책은 `account_patient_id`가 로그인 본인인지만 확인하고, `family_patient_id`의 생성 주체·동의·기존 소유관계를 검사하지 않는다. `patient_owns()`는 링크 존재만으로 가족 소유권을 인정한다(환자 앱 계획 44~61, 75~87, 293~325).
- 영향: 다른 환자의 기본정보·예약·문진·공개 안내를 읽거나 수정할 수 있는 개인정보 침해가 발생한다.
- 수정: 클라이언트의 가족 링크 직접 INSERT를 막는다. 서버가 새 가족 프로필 생성과 링크 생성을 같은 트랜잭션에서 처리한다. 기존 환자 연결이 필요하면 본인확인·동의 절차를 거치는 별도 보안 함수로 분리한다.
- 검증: 환자 A가 환자 B의 UUID를 가족 링크로 직접 INSERT하려 할 때 데이터베이스 수준에서 거부되는지 확인한다.

### 3.2 P1 — 핵심 기능·운영 규칙 수정

#### R2-03. 대기시간이 일반 수정 때마다 초기화됨

- 근거: 대기열·장기대기·대기시간 계산이 예약 행의 공통 `updated_at`을 사용한다(직원 웹 계획 3129~3137, 3163~3175). 순서 변경과 주의 표시도 이 값을 갱신한다(기반 계획 2006~2008, 2169~2197).
- 영향: 순서 조정이나 메모 수정만으로 대기시간이 0분부터 다시 계산된다.
- 수정: `진료대기`로 전환된 시각을 상태이력에서 읽거나 `waiting_started_at`에 별도로 기록한다. 현재 대기시간·장기대기·평균대기시간이 같은 기준을 사용하게 한다.
- 검증: 대기순서 조정과 주의 표시 뒤에도 대기 시작 시각과 계산 결과가 유지되는지 확인한다.

#### R2-04. 운영 통계가 모두 예약 생성일을 기준으로 집계됨

- 근거: 상태별 건수와 앱 예약 비율이 `appointments.created_at::date`만 필터링한다(직원 웹 계획 3207~3239).
- 영향: 예약한 날과 방문·취소·부도 발생일이 다르면 일별 운영 보고가 왜곡된다.
- 수정: 신규 예약 유입은 생성일, 방문은 `진료완료` 전이일, 취소·부도는 해당 상태 전이일, 평균 대기는 대기 시작일 등으로 지표별 사건 기준일을 확정한다. 슬롯일 기준 지표와 생성일 기준 지표의 이름을 구분한다.
- 검증: 예약 생성일과 실제 운영 발생일이 다른 데이터로 각 지표가 정의된 날짜에만 집계되는지 확인한다.

#### R2-05. 상태 변경 알림의 책임 단계와 수신자가 완결되지 않음

- 근거: `hospital_cancelled`, `visit_completed` 문구는 있지만 실제 호출 책임이 계획에 배정되지 않았다. 직원 웹에서 명시된 호출은 취소요청 반려뿐이다(환자 앱 계획 2265~2275, 2308~2340, 5554~5556; 직원 웹 스펙 102~104).
- 영향: 병원 취소·진료 완료·취소요청 승인 같은 중요 변경이 환자에게 전달되지 않거나 중복 발송될 수 있다.
- 수정: 상태전이 서비스가 도메인 이벤트를 만들고, 커밋 후 알림 작업이 병원 취소, 진료 완료, 취소요청 승인·반려, 일정변경 재예약을 처리하게 한다. 가족 예약의 계정 주인과 진료 대상 중 실제 수신자를 정하고 중복 방지 키를 둔다.
- 검증: 각 이벤트에서 정해진 대상에게 알림이 정확히 한 번 기록·발송되는지 확인한다.

#### R2-06. 상담 티켓 담당자와 의료판단 역할을 검사하지 않음

- 근거: 답변 서비스는 티켓이 `pending` 또는 `in_progress`이면 어떤 직원도 답변할 수 있고, `assigned_staff_id`와 의료판단에 적합한 역할을 확인하지 않는다(챗봇 계획 2675~2707, 3347~3361).
- 영향: 배정되지 않은 직원이나 접수직원이 의료판단 답변을 완료할 수 있다.
- 수정: 답변 시 `assigned_staff_id == staff.id`를 원자적으로 확인한다. `medical_judgment`는 확정된 허용 역할만 배정·답변할 수 있게 하고, 재배정 대상의 활성 상태와 역할도 검사한다.
- 검증: 비배정 직원 또는 허용되지 않은 역할의 직원이 답변할 때 403 또는 409로 거부되는지 확인한다.

#### R2-07. 오늘 현황이 슬롯 날짜가 아닌 생성·수정일을 셈

- 근거: 오늘 요약은 `updated_at::date` 또는 `created_at::date`가 오늘인 예약을 센다(직원 웹 계획 3115~3126).
- 영향: 오늘 만든 다음 주 예약이나 오늘 수정한 과거 예약이 오늘 환자로 표시된다.
- 수정: 슬롯이 있는 예약은 `appointment_slots.slot_date = 병원 기준 오늘`로 집계한다. 워크인은 `visit_date` 또는 접수 시각을 별도로 사용하고 시간대는 `Asia/Seoul` 원칙으로 통일한다.
- 검증: 오늘 생성한 미래 예약과 오늘 수정한 과거 예약이 오늘 현황에 포함되지 않는지 확인한다.

#### R3-01. 하루 최대 예약 수와 예약 마감 시간이 실제 예약을 막지 않음

- 근거: `max_daily_appointments`, `booking_deadline` 컬럼은 있지만 슬롯 조회·생성·예약 서비스에서 사용하지 않는다(기반 계획 372~383; 환자 앱 계획 1366~1395).
- 영향: 관리자가 설정한 최대 예약 수와 마감 시간이 앱·웹·챗봇 어느 경로에서도 강제되지 않는다.
- 수정: 공통 availability(예약 가능성) 계약을 만들고 슬롯 생성·조회와 앱·직원 웹·챗봇 예약 직전에 같은 규칙을 재검증한다. 미래 슬롯 재계산 정책도 포함한다.
- 검증: 최대 3건인 날의 네 번째 슬롯·예약과 예약 마감 직후 요청이 모든 채널에서 동일하게 거부되는지 확인한다.

#### R3-02. 점심·정규시간·특정일 예외가 슬롯과 예약에 강제되지 않음

- 근거: 정규·예외 스케줄 구조는 있지만 슬롯 생성기가 없고, 예약 서비스는 선택한 슬롯의 상태만 확인한다(기반 계획 372~393, 2236~2259).
- 영향: 점심시간, 휴진일, 단축 진료시간에도 예약 가능한 슬롯이 남을 수 있다.
- 수정: `정규시간 − 점심시간 − 휴진/예외`와 슬롯 단위·최대 인원을 계산하는 생성기·재생성기 계약을 추가한다. 예약 직전에도 슬롯이 현재 규칙상 유효한지 확인하고 기존 예약 영향 처리를 같은 정책으로 연결한다.
- 검증: 점심시간, 휴진일, 특정일 단축 진료에서 시간 목록과 최종 예약이 같은 결과를 내는지 확인한다.

#### R3-03. 예약 Realtime 구독에 필요한 publication 설정이 없음

- 근거: 앱과 직원 웹은 `appointments` 변경을 구독하지만, `supabase_realtime` publication에는 챗봇 관련 테이블만 추가되어 있다(환자 앱 스펙 21, 69; 직원 웹 계획 3407~3424; 챗봇 계획 191~193, 587).
- 영향: 코드가 구독 중이어도 실제 원격 환경에서는 예약 변경이 즉시 반영되지 않을 수 있다.
- 수정: 마이그레이션에 `appointments`와 실제 구독에 필요한 테이블을 publication에 추가한다. RLS가 구독 결과에도 같은 범위를 적용하게 한다.
- 검증: 직원이 바꾼 상태가 해당 환자 앱과 권한 있는 직원 화면에만 도착하는지 원격 Supabase 환경에서 확인한다.

#### R3-04. 관리자 직원 계정 관리 화면이 구현 계획에 없음

- 근거: 스펙은 `/admin/staff`에서 직원·의사 계정을 관리하도록 하지만, 구현 계획에는 백엔드 초대·중지 API만 있고 화면·라우트·API 클라이언트 태스크가 없다(직원 웹 스펙 25, 81; 기반 계획 1672~1683, 2722~2739; 직원 웹 계획 4641~4658).
- 영향: 관리자가 웹에서 직원과 의사를 초대하거나 사용 중지할 수 없다.
- 수정: 직원 목록, 초대 폼, 역할·의사 진료과 검증, 사용 중지 확인, 현재 로그인 관리자와 최후 관리자 보호, 재초대·부분 실패 처리를 포함한 명시적 태스크를 추가한다.
- 검증: 관리자가 웹에서 의사를 초대·중지했을 때 메뉴와 API/RLS 접근이 즉시 맞게 바뀌는지 확인한다.

#### R4-02. 진료기록 완료와 예약 `진료완료` 상태가 연결되지 않음

- 근거: 완료 서비스와 의사 화면은 `medical_records.is_completed`만 변경하고 예약 상태를 바꾸지 않는다(기반 계획 2533~2541; 직원 웹 계획 2711~2741).
- 영향: 의사가 기록을 완료해도 환자 앱에는 진료 완료가 표시되지 않고 상태이력·알림도 누락된다.
- 수정: 한 트랜잭션에서 기록 완료, 예약의 `진료중→진료완료` 전이, 상태이력, 공개 안내와 알림 이벤트를 처리하는 단일 도메인 작업을 만든다. 재시도는 멱등으로 처리한다.
- 검증: 완료 버튼 한 번으로 기록과 예약이 함께 완료되고 상태이력이 한 번만 남으며 앱에도 반영되는지 확인한다.

#### R4-03. 환자 앱의 “내 앞 대기 인원” 계약이 없음

- 근거: 앱 스펙은 도착 후 내 앞 대기 인원의 Realtime 갱신을 약속하지만, API는 본인의 `queue_position`만 반환하고 화면도 인원을 표시하지 않는다(환자 앱 스펙 69; 환자 앱 계획 1729~1745, 4724~4751, 4817~4834).
- 영향: 고객에게 약속한 대기 안내가 앱에 나타나지 않는다.
- 수정: 같은 의사·당일·유효 대기 상태를 기준으로 서버가 `patients_ahead`만 계산해 반환한다. 순서 변경, 진료 시작, 취소·부도 때 갱신하고 다른 환자의 개인정보는 반환하지 않는다.
- 검증: 앞 환자의 취소·진료 시작·순서 변경에 따라 숫자는 바뀌되 다른 환자의 식별정보가 노출되지 않는지 확인한다.

#### R5-02. 가족 연결 해제 뒤에도 접근권한이 유지됨

- 근거: 해제 서비스는 가족 환자의 `is_active=false`만 설정하고 링크는 남겨 둔다. `patient_owns()`와 접근 가능 목록은 링크나 가족의 활성 여부를 확인하지 않는다(환자 앱 계획 44~61, 704~709, 1031~1041).
- 영향: 가족 목록에서 사라져도 예약·문진·방문 안내를 계속 조회할 수 있다.
- 수정: 링크에 `is_active` 또는 `unlinked_at`을 두고 링크 자체를 비활성화한다. 권한 함수와 모든 가족 조회는 활성 링크만 인정한다. 과거 예약 보존을 위해 환자 행은 유지할 수 있다.
- 검증: 연결 해제 직후 앱 API와 Supabase 직접 조회 모두에서 가족 데이터 접근이 차단되는지 확인한다.

#### R5-03. 도착·진료 완료 뒤에도 문진을 직접 수정·삭제할 수 있음

- 근거: 앱 서비스는 `예약신청/예약확정`에서만 저장을 허용하지만, RLS는 소유 예약의 문진 응답에 SELECT/INSERT/UPDATE/DELETE를 모두 허용한다(환자 앱 스펙 62; 환자 앱 계획 322~325, 1868~1901).
- 영향: 의사가 확인했거나 진료 근거로 사용한 문진이 사후 변경·삭제될 수 있다.
- 수정: 환자의 직접 테이블 쓰기를 막고 예약 상태를 검사하는 RPC로 원자화하거나, UPDATE·DELETE 정책에 허용 예약 상태를 강제한다.
- 검증: `도착`, `진료대기`, `진료중`, `진료완료` 상태에서 직접 UPDATE와 DELETE가 모두 거부되는지 확인한다.

#### R5-04. 익명 웹 상담의 진료과·예약시간 조회가 실패함

- 근거: 익명 사용이 가능한 도구인데도 구현은 `PatientContext`가 필요한 환자 앱 서비스에 `None`을 전달한다(챗봇 스펙 22, 207~212; 환자 앱 계획 1174~1213; 챗봇 계획 1337~1339, 1518~1532).
- 영향: 익명 사용자가 진료과 추천이나 빈 시간 조회에 도달하면 예외가 발생하고 일반 장애 안내로 끝난다.
- 수정: 개인정보가 필요 없는 공개 카탈로그 읽기 서비스·엔드포인트를 만들고 활성 진료과·의사·현재 규칙상 유효한 슬롯만 반환한다.
- 검증: 로그인하지 않은 사용자가 진료과 추천과 빈 시간 조회를 끝까지 정상 이용하는지 확인한다.

#### R5-05. 전화예약 환자와 새 앱 계정이 연결되지 않음

- 근거: 직원이 만든 환자는 인증계정이 없고, 앱 가입은 같은 전화번호·생년월일의 기존 환자를 찾지 않고 새 행을 만든다. 가입 요청 본문의 전화번호도 Auth에서 검증된 번호가 아니라 그대로 저장한다(기반 계획 1637~1654; 환자 앱 계획 824~837, 2391~2405).
- 영향: 기존 예약·방문이력은 옛 환자 행에 남고 새 앱에서 보이지 않으며, 요청 본문 변조로 잘못된 전화번호가 저장될 수 있다.
- 수정: Supabase Auth의 검증된 전화번호를 사용한다. 안전한 일치 조건으로 기존 후보를 연결하고, 동명이인·복수 후보·불일치는 직원 확인 흐름으로 보낸다.
- 검증: 전화예약 이력이 있는 환자가 같은 검증 전화번호로 가입할 때 기존 환자와 연결되고, 본문 전화번호 변조는 무시·거부되는지 확인한다.

#### R5-06. 직원 목록에서 개인정보가 마스킹되지 않음

- 근거: 대기목록과 취소요청은 전체 생년월일을, 일정변경 영향목록은 전체 전화번호를 렌더링한다(직원 웹 계획 1920~1954, 2889, 4611). 요구사항은 목록에서 일부를 가리고 상세에서만 전체를 보이도록 한다.
- 영향: 옆자리, 화면 공유, 캡처를 통해 불필요한 개인정보가 노출된다.
- 수정: 서버 목록 DTO부터 `masked_birth_date`, `masked_phone`만 반환한다. 전체 값은 감사로그가 남는 환자 상세에서만 조회한다.
- 검증: 대기·캘린더·영향목록·취소요청·통계 상세의 응답과 화면에 전체 전화번호·생년월일이 없는지 확인한다.

#### R5-07. 직원 웹 구현 폴더와 CI·배포 폴더가 다름

- 근거: 직원 웹 계획은 `frontend/`에 파일을 만들지만 배포 계획, 오류 화면, CI, Vercel은 `web/`을 사용한다(직원 웹 계획 720~742; 배포 계획 9, 14, 956~958, 1573, 1619, 1803~1818).
- 영향: CI가 직원 웹 테스트·빌드를 실행하지 못하고 Vercel도 잘못된 루트에서 배포될 수 있다.
- 수정: `frontend/` 또는 `web/` 중 실제 표준 폴더 하나를 정하고 계획의 파일 경로, CI working directory와 캐시, Vercel Root Directory를 모두 같은 값으로 바꾼다.
- 검증: 표준 폴더 한 곳에서 CI 빌드가 통과하고 같은 산출물이 Vercel에 배포되는지 확인한다.

### 3.3 P2 — 운영 완성도 수정

#### R4-04. QR·예약번호로 접수할 직원 웹 흐름이 없음

- 근거: 환자 앱은 UUID QR과 텍스트 예약번호를 표시하지만, 직원 웹 검색은 전화번호+생년월일만 지원한다(환자 앱 스펙 67~69; 환자 앱 계획 4825~4829; 직원 웹 계획 1285~1291, 1378~1458).
- 영향: 환자가 QR이나 예약번호를 보여줘도 직원이 해당 번호로 예약을 열어 도착 처리할 수 없다.
- 수정: 인증된 QR 스캔·예약번호 입력과 예약 조회 API를 추가한다. 번호 형식, 오입력, 취소·과거 예약, 동명이인 확인 방식을 디자인 스펙에서 먼저 결정한다.
- 검증: 유효한 번호로 예약을 열어 도착 처리할 수 있고, 잘못된 번호와 취소·부도 예약은 안전한 안내를 보여주는지 확인한다.

#### R5-08. 진료기록 열람 감사로그가 실제 조회 경로에 연결되지 않음

- 근거: 감사 함수는 독립적으로만 존재하고 진료기록 조회 API에는 연결되지 않았다. 환자 상세 조회는 `patient_detail` 한 건만 기록한다(기반 계획 2607~2695; 직원 웹 계획 3180~3196).
- 영향: 관리자 화면에 진료기록 열람 로그 항목이 있어도 실제로 누가 기록을 봤는지 남지 않는다.
- 수정: 진료기록 원문, 과거 기록, 수정이력 조회 API마다 성공적인 열람 요청 안에서 `medical_record` 감사로그를 남긴다.
- 검증: 기록과 수정이력을 열 때마다 관리자 감사 화면에 직원·환자·자료 종류·시각이 남는지 확인한다.

#### R5-09. 진료과별 문진 양식 관리 API·화면이 없음

- 근거: `questionnaire_templates` 테이블과 관리자 RLS만 있고 관리자용 편집 화면·API가 없다. 환자 앱은 같은 진료과의 임의 첫 행을 `limit 1`로 선택한다(기반 계획 976~1020; 환자 앱 계획 1871~1878).
- 영향: 운영자가 질문을 만들거나 바꿀 수 없고, 여러 양식이 생기면 어떤 양식이 적용될지 결정적이지 않다.
- 수정: 관리자 편집 화면·API, 진료과당 활성 버전 1개 제약, 버전 생성·사용 중지 정책을 추가한다. 과거 응답에는 제출 당시 질문 스냅샷을 유지한다.
- 검증: 활성 양식을 바꾸면 새 예약부터 새 양식이 적용되고 과거 응답의 질문 의미는 유지되는지 확인한다.

### 6.3 완전 반영된 8건

#### R2-01 — 다른 환자의 예약 슬롯 반납 차단

- 환자 앱 계획 117~147의 `patients_can_update_slots_for_booking` 정책은 이미 예약된 슬롯을 반납할 때 해당 슬롯을 참조하는 예약이 본인·활성 가족 소유인지 검사한다.
- 환자 앱 계획 310 이후에 타인 슬롯 반납 실패와 본인 슬롯 반납 성공을 각각 직접 RLS로 검증하는 테스트가 있다.
- 이 판정은 R2-01의 원래 범위인 “타인의 예약된 슬롯 반납 차단”에 대한 것이다. 장기적으로는 빈 슬롯의 직접 상태 변경도 RPC로 원자화하는 편이 최소권한 원칙에 더 안전하다.

#### R2-03 — 대기 시작 시각

- 직원 웹 계획의 오늘 현황과 대기열은 `appointment_status_history`에서 실제 `진료대기` 전이의 최신 `changed_at`을 사용한다.
- 순서 변경·주의 표시에서 남기는 같은 상태 메모는 `from_status is distinct from to_status` 조건으로 제외된다.

#### R2-06 — 상담 티켓 담당자와 의료 역할

- AI 상담봇 계획은 답변 시 티켓 행을 잠그고 현재 담당자와 일치하는지 검사한다.
- `medical_judgment`는 의사·관리자만 답변할 수 있고, 재배정 대상의 활성 상태와 역할을 확인하는 테스트가 있다.

#### R2-07 — 오늘 현황 기준일

- 슬롯이 있는 예약은 `appointment_slots.slot_date`, 슬롯이 없는 워크인은 한국시간 기준 `appointments.created_at`을 사용한다.

#### R3-03 — Realtime publication

- 직원 웹 계획에 `appointments`, `appointment_slots`, `appointment_status_history` publication 등록이 포함돼 있다.
- 실제 Supabase 환경에서 권한 있는 구독자에게만 이벤트가 전달되는지 확인하는 수동 검증도 명시돼 있다.

#### R2-02 — 의사의 환자정보 열람 범위 **[2026-07-28 재검증으로 이동]**

- 기반 계획 Task 3의 `receptionist_admin_can_read_patients`가 접수직원·관리자 전용으로 바뀌었고, 의사용 `doctor_can_read_scoped_patients`(Task 4, `doctor_can_view_patient()`)가 담당 예약 또는 진료 연속성이 있는 환자만 허용한다.
- 의사 A가 담당 아닌 환자를 UUID로 직접 조회해도 0행을 받는지 확인하는 테스트가 추가됨.
- SDB-06으로 반영(`docs/supabase-postgres-review-2026-07-28.md` 참고).

#### R4-03 — 내 앞 대기 인원 **[2026-07-28 재검증으로 이동]**

- `patient_queue_position_ahead_count()` SECURITY DEFINER RPC가 호출자의 예약 소유권을 `patient_owns()`로 먼저 확인한 뒤, 환자 RLS 범위와 무관하게 전체 대기열을 집계해 숫자만 반환한다.

### 6.4 부분 반영된 8건과 필요한 보완

#### R2-04 — 운영 통계

- 사건별 기준일 쿼리는 추가됐다.
- 시간대별 내원 환자 통계가 없고 API 필드가 `reserved`, `cancelled`처럼 어떤 사건 날짜를 기준으로 했는지 드러내지 않는다.
- 예약 생성일과 각 상태전이일이 다른 테스트 데이터를 사용해 모든 지표 경계를 검증해야 한다.

#### R3-01 — 슬롯 생성과 최대 예약 수

- 8주 재계산, 점심 제외, 최대 인원, 예약된 슬롯 보존은 들어 있다.
- `(doctor_id, weekday)` UNIQUE 제약 없이 SELECT 후 UPDATE/INSERT하는 일정 저장은 동시 요청에서 중복 행을 만들 수 있다.
- UNIQUE 제약과 `INSERT ... ON CONFLICT DO UPDATE` 또는 동등한 원자적 UPSERT를 계획해야 한다.

#### R3-02 — 일정 예외와 영향 예약

- 규칙 변경 미리보기와 `needs_rescheduling` 표시는 들어 있다.
- 예외일정 화면은 아직 저장되지 않은 새 예외 값이 아니라 DB에 이미 저장된 예외 행으로 영향 예약을 조회하므로 저장 전 경고를 정확히 계산하지 못한다.
- 미리보기 API가 새 규칙·예외 값을 요청 본문으로 받아 dry-run 계산하도록 바꿔야 한다.
- 재예약뿐 아니라 취소 완료 시에도 `needs_rescheduling=false`를 명시적으로 정리해야 한다.

#### R3-04 — 직원 계정 관리

- 직원 목록, 초대, 비활성화, 자기 자신·최후 관리자 보호가 추가됐다.
- 의사 초대 화면과 요청에 `department_id`가 없고, 재초대 동작 및 메뉴/API/RLS가 함께 바뀌는 E2E 테스트가 없다.
- 계획의 최후 관리자 테스트는 관리자를 추가한 뒤에도 기존 관리자 비활성화를 실패로 기대해 서비스 규칙과 맞지 않는다.

#### R4-01 — 승인 지식자료 수정본 재승인

- 승인본을 유지한 채 pending 컬럼에 수정본을 보관하고 재승인 시 승격하는 흐름은 들어 있다.
- 문서 목록 응답에는 pending 본문이 없으며 “라이브 내용 보기”와 “대기 중 수정본 보기”를 비교하는 상세 API·화면이 없다.

#### R4-04 — 예약코드와 QR 접수

- 6자리 예약코드, 만료 필드, 환자 QR 표시, 직원 코드 검색은 들어 있다.
- 직원 화면의 QR 스캔은 주석으로만 남아 있고 카메라 스캐너 컴포넌트·라이브러리·권한 오류·스캔 테스트가 없다.
- 코드 생성의 존재 확인 후 INSERT 방식은 동시 충돌 시 예약 전체가 실패할 수 있으므로 UNIQUE 충돌 재시도도 계획해야 한다.

#### R5-01 — 가족 등록과 기존 환자 연결 **[2026-07-28 재검증으로 이동, ❌→⚠️]**

- 직접 INSERT 제거, OTP 서비스, `patient_family_links` 직접 UPDATE/DELETE 제거(SDB-19)까지 핵심 우회 경로는 모두 막힘.
- 다만 정책 스펙에서 확정한 `create_family_member`/`link_existing_family_member`/`staff_link_family_member`라는 이름의 정식 RPC 계약으로 문서화되지는 않았다(대신 기존 `add_family_member`/`confirm_family_link_otp` 서비스 함수가 같은 역할을 이미 수행 중).
- 남은 작업: 정책 스펙과 계획서의 함수 이름·계약을 통일하거나, 스펙 쪽 이름을 실제 구현에 맞게 갱신.

#### R5-06 — 개인정보 마스킹

- 대기·취소·일정영향 목록은 서버에서 원문을 제거하고 마스킹 값을 반환하도록 바뀌었다.
- 직원 웹 환자 병합 후보 조회는 여전히 `birth_date`, `phone` 원문을 반환하고 화면에 표시한다.
- 병합 후보도 목록 정책에 맞게 마스킹하고, 전체값은 감사로그가 남는 상세 확인에서만 보여야 한다.

### 6.5 핵심 미반영 또는 오류 8건

#### R2-05 — 알림 이벤트·수신자·중복 방지 **[2026-07-28 재검증: 인덱스 서브 이슈만 해결]**

- `visit_completed` 문구는 있지만 호출 지점이 없고, 일정 변경으로 `needs_rescheduling=true`가 되는 경로도 변경 알림을 호출하지 않는다.
- 취소 거절 알림은 가족 예약의 계정 소유자가 아니라 진료 대상 환자 ID를 수신자로 사용하며 예약 ID도 전달하지 않는다.
- ~~`sent_at::date` 표현식 인덱스는 `timestamptz`의 날짜 변환이 세션 시간대에 의존하므로 PostgreSQL immutable 인덱스 조건을 만족하지 못할 수 있다.~~ SDB-04로 해결됨 — `notification_date` 칼럼(KST 기준 저장)과 부분 유니크 인덱스 2개(일단위/1회성)로 교체했다.
- 위 두 알림 미호출 문제는 여전히 남아 있다. 일회성 이벤트는 `(appointment_id, type)`, 반복 리마인더만 병원 기준 발송일을 포함하는 별도 중복 키로 설계해야 한다는 원칙은 이미 반영됨.

#### R4-02 — 진료기록 완료와 예약 완료

- 기반 계획의 `complete_record()`는 `medical_records.is_completed=true`만 갱신한다.
- 예약의 `진료중→진료완료`, 상태이력, 환자 공개, 진료완료 알림이 같은 작업에 포함되지 않는다.
- 짧은 단일 트랜잭션 또는 원자적 DB 함수로 기록과 예약 상태를 함께 완료하고 재시도 멱등성 테스트를 추가해야 한다.
- `patient_family_links`의 직접 UPDATE는 계정 소유자 조건만 확인해 링크 대상을 다른 환자로 바꾸거나 해제된 링크를 다시 활성화할 수 있다.
- 클라이언트의 일반 INSERT·UPDATE·DELETE를 모두 차단하고 새 가족 생성, OTP 연결, 직원 확인 연결을 각각 제한된 트랜잭션/RPC로 분리해야 한다.

#### R5-03 — 도착 후 문진 수정 차단

- `questionnaire_service`는 `예약신청`, `예약확정`에서만 저장하도록 검사한다.
- 하지만 `patients_can_manage_own_questionnaire_responses` RLS가 `FOR ALL`이며 예약 상태를 확인하지 않아 Supabase 직접 UPDATE·DELETE로 우회할 수 있다.
- 환자 직접 쓰기를 제거하고 예약 상태를 검사하는 RPC로 저장하거나, UPDATE·DELETE RLS에 허용 상태를 강제해야 한다.

#### R5-04 — 익명 사용자의 공개 카탈로그

- AI 계획의 진료과 추천과 슬롯 도구는 익명 컨텍스트에서 `ctx.patient=None`을 기존 `patient_catalog_service`로 전달한다.
- 기존 카탈로그 함수는 `PatientContext.auth_user_id`와 인증 RLS를 요구하므로 익명 요청은 실패한다.
- 활성 진료과·의사·유효한 빈 슬롯만 읽는 공개 전용 서비스/API와 익명 전체 흐름 테스트를 추가해야 한다.

#### R5-05 — 전화예약 환자와 앱 계정 병합

- 검증된 Auth 전화번호를 사용하고 단일 일치 시 자동 연결하는 부분은 들어 있다.
- 병합 후보 조회는 `auth_user_id IS NULL`만 조회해 새 앱 계정에 연결된 환자를 후보에서 제외한다.
- 병합 함수는 기존 연결을 먼저 해제하지 않고 대상 행에 `auth_user_id`를 설정해 UNIQUE 충돌이 발생할 수 있고 두 UPDATE도 트랜잭션으로 묶이지 않았다.
- 연결된 앱 환자와 미연결 병원 환자를 한 쌍으로 제시하고, 잠금·검증·연결 이전·비활성화를 하나의 짧은 트랜잭션으로 처리해야 한다.

#### R5-07 — 직원 웹 폴더 통일

- 직원 웹 및 AI 관리자 화면 계획은 `frontend/`를 표준 경로로 사용한다.
- 배포 계획의 CI 캐시·작업 디렉토리·Vercel Root Directory·배포 명령은 여전히 `web/`을 사용한다.
- 실제 표준을 하나 선택한 뒤 모든 계획, CI, Vercel, 오류화면, 문서 경로를 일괄 변경해야 한다.

#### R5-08 — 진료기록 열람 감사로그

- `audit_service.log_access()`와 관리자 조회 화면은 존재한다.
- 실제 연결 지점은 `get_patient_detail()`의 `patient_detail` 로그뿐이며 진료기록 원문, 과거 기록, 수정이력 조회에 `medical_record` 로그 호출이 없다.
- 성공적으로 자료를 반환하는 각 조회 서비스의 동일 요청 흐름 안에서 감사로그를 기록하고, 각각의 API 테스트가 로그 생성을 확인해야 한다.

#### R5-09 — 진료과별 문진 템플릿

- 관리자 서비스의 UPSERT SQL에 `values (...)`가 연속 두 번 적혀 있어 실행할 수 없다.
- 중복 템플릿 정리 마이그레이션은 참조 중인 템플릿을 임의로 삭제할 수 있어 `questionnaire_responses.template_id` FK 때문에 실패하거나 과거 응답 의미를 훼손할 수 있다.
- 화면에는 실제 진료과 선택, 질문 순서 변경, 질문 유형, 필수 여부 편집이 없다.
- 중복 데이터 정리 시 응답 참조를 안전하게 보존하고, 과거 응답·작성 중 응답·새 예약에 미치는 영향을 각각 테스트해야 한다.
