## 1. 검토 결론

현재 계획의 큰 방향은 적절하다. 민감한 테이블에 RLS(Row Level Security, 행 단위 보안)를 적용하고, 예약 슬롯을 조건부 UPDATE로 점유하며, 완료된 진료기록 수정에 행 잠금·변경 사유·수정 이력을 함께 사용하는 점은 좋은 설계다.

그러나 현재 SQL을 계획서 그대로 구현하면 일부 마이그레이션은 실행 도중 실패하고, 첫 번째 `staff` RLS 정책부터 재귀 오류가 발생할 가능성이 높다. 또한 `SECURITY DEFINER` 함수의 공개 범위와 인덱스가 충분히 통제되지 않았다.

2차 재검토에서는 31개 테이블, 67개 RLS 정책, 13개 함수, 7개 트리거, 11개 명시적 인덱스를 다시 추출해 명령별 권한과 실제 서비스 쿼리를 교차검증했다.

최종 판정:

- P0 — 구현 전에 반드시 수정: 13건
- P1 — 핵심 기능 구현과 함께 수정: 15건
- P2 — 데이터 증가 전 최적화: 6건

이 보고서는 계획서의 데이터베이스 부분만 정적으로 검토한 결과다. 아직 실제 `supabase/migrations/*.sql` 파일과 로컬 DB가 없으므로 `supabase db reset`, 실제 RLS 요청, 동시성 테스트까지 실행한 검증은 아니다.

## 3. P0 — 구현 전에 반드시 수정

### SDB-01. 세 영역이 같은 `00012` 마이그레이션 번호를 사용한다

근거:

- 직원 웹: `2026-07-27-staff-web.md:4880`
- 환자 앱: `2026-07-27-patient-app.md:2496`
- AI 챗봇: `2026-07-27-ai-chatbot.md:14,71`

문제:

Supabase 마이그레이션은 파일명 앞 버전으로 실행 순서를 관리한다. 서로 다른 워크트리에서 같은 번호를 만들면 병합 시 버전 충돌이 생기고, 어떤 SQL이 먼저 적용돼야 하는지도 불분명해진다.

권장 수정:

- 기반: `00001~00099`
- 직원 웹: `00100~00199`
- 환자 앱: `00200~00299`
- AI 챗봇: `00300~00399`
- 배포·운영: `00400~`

번호 대역은 예시다. 중요한 것은 영역마다 겹치지 않는 대역을 미리 고정하고, 챗봇처럼 환자 테이블을 참조하는 영역을 환자 앱보다 뒤에 두는 것이다.

완료 기준:

- 모든 마이그레이션 버전이 유일하다.
- 파일명 정렬 순서가 실제 테이블 의존 순서와 일치한다.

### SDB-02. 예약 상태전이 테이블에 넣는 `NULL`이 기본키와 충돌한다

근거:

- 기본키 선언: `2026-07-27-foundation-auth-data-model.md:882~885`
- `NULL` 삽입: `2026-07-27-foundation-auth-data-model.md:888~889`

문제:

`primary key (from_status, to_status)`를 선언하면 두 칼럼 모두 자동으로 `NOT NULL`이 된다. 따라서 `(null, '예약신청')`과 `(null, '예약확정')` 삽입은 실패한다.

권장 수정:

현재 트리거는 INSERT가 아니라 UPDATE 상태전이만 이 표로 검사하므로 `from_status = NULL`인 두 행을 제거하는 것이 가장 단순하다. 신규 예약의 초기 상태는 별도의 INSERT 제약이나 예약 생성 RPC에서 채널별로 검사한다.

완료 기준:

- `supabase db reset`이 해당 INSERT에서 실패하지 않는다.
- 허용 전이는 성공하고 임의 상태 점프는 실패하는 테스트가 있다.

### SDB-03. `staff`와 `patients`의 RLS가 같은 테이블을 다시 조회한다

근거:

- `staff` 정책 안에서 `staff` 재조회: 기반 계획 `225~232`
- `patients` INSERT 정책 안에서 `patients` 재조회: 환자 앱 계획 `69~74`
- 다수 정책이 권한 확인을 위해 `staff`를 조회함: 기반 계획 `216~232`, `399~415`, `536~551` 등

문제:

RLS 정책을 계산하는 동안 같은 테이블의 RLS를 다시 계산하면 PostgreSQL이 `infinite recursion detected in policy` 오류를 낼 수 있다. `staff` 조회가 권한 판단의 출발점이므로 이 오류는 다른 테이블 정책에도 연쇄적으로 영향을 준다.

권장 수정:

1. API에 노출하지 않는 `private` 스키마를 만든다.
2. `private.current_staff_id()`, `private.current_staff_role()`, `private.current_patient_id()` 같은 작은 `SECURITY DEFINER` 헬퍼를 만든다.
3. 헬퍼는 `set search_path = ''`를 사용하고 `public.staff`처럼 스키마를 완전히 적는다.
4. RLS에서는 같은 테이블을 직접 재조회하지 않고 헬퍼 결과를 사용한다.
5. 함수 기본 실행 권한을 회수하고, RLS 실행에 필요한 최소 역할만 허용한다.

완료 기준:

- 인증된 직원·환자로 `staff`, `patients` SELECT/INSERT 테스트가 재귀 오류 없이 실행된다.
- 익명 사용자는 허용되지 않은 행을 읽거나 쓸 수 없다.

### SDB-04. 알림 중복방지 인덱스의 `sent_at::date`가 마이그레이션을 실패시킬 수 있다

근거: 환자 앱 계획 `2757~2767`

문제:

`sent_at`은 `timestamptz`다. 이를 바로 `date`로 바꾸면 세션 시간대에 따라 날짜가 달라질 수 있어 PostgreSQL이 인덱스 표현식에 필요한 불변 함수로 인정하지 않는다. 계획된 인덱스는 생성 단계에서 실패할 가능성이 높다.

추가로 현재 규칙은 “1회성 알림”도 다음 날 다시 보낼 수 있다. 하루 단위 리마인더와 예약당 한 번만 보내야 하는 알림은 중복 기준이 다르다.

권장 수정:

- 하루 단위 알림: 업무 시간대가 명확한 `notification_date date`를 저장하고 `(appointment_id, notification_type, notification_date)`를 유일하게 만든다.
- 1회성 알림: `(appointment_id, notification_type)`를 유일하게 만든다.
- 두 유형이 섞인다면 `dedupe_key`를 서비스가 명시적으로 생성하는 방법도 가능하다.

완료 기준:

- 시간대 설정이 달라도 동일한 업무일의 알림이 한 번만 발송된다.
- 다음 날 리마인더는 다시 발송되지만 예약확정 같은 1회성 이벤트는 다시 발송되지 않는다.

### SDB-05. `SECURITY DEFINER` 함수가 공개 스키마와 안전하지 않은 검색 경로를 사용한다

근거:

- 기반 계획: `683~684`, `721~722`, `765~766`, `846~847`, `902~903`, `928~929`, `1421~1422`, `1444~1445`, `1472~1473`
- 환자 앱 계획: `48~49`, `450~451`
- 모두 `set search_path = public` 사용
- 계획에서 함수별 `revoke execute`/최소 권한 부여가 확인되지 않음

문제:

`SECURITY DEFINER`는 호출한 사용자가 아니라 함수 소유자의 강한 권한으로 실행된다. 이름만 적힌 테이블이나 함수를 `public`에서 찾게 하면 같은 이름의 객체를 이용한 우회 위험이 생긴다. PostgreSQL 함수는 기본적으로 `PUBLIC`에 실행 권한이 생길 수 있으므로 RPC 함수의 직접 호출 범위도 명시해야 한다.

권장 수정:

- 내부 헬퍼를 API 비노출 `private` 스키마로 이동한다.
- `set search_path = ''`를 사용한다.
- 함수 안의 모든 객체를 `public.appointments`, `auth.uid()`처럼 완전한 이름으로 참조한다.
- `PUBLIC`, `anon` 등 불필요한 역할의 실행 권한을 회수한다.
- `revise_medical_record`처럼 클라이언트가 호출해야 하는 RPC만 `authenticated`에 명시적으로 허용한다.
- 함수 내부에서 `(select auth.uid())`와 현재 직원·환자 권한을 다시 검사한다.

완료 기준:

- `pg_proc.prosecdef = true`인 모든 함수에 소유자, 스키마, `search_path`, 실행 역할 표가 존재한다.
- `anon`과 다른 환자·의사가 직접 RPC를 호출해도 데이터가 바뀌지 않는다.

### SDB-06. 의사의 기본 환자정보 조회 범위가 담당 환자로 제한되지 않는다

근거: 기반 계획 `536~538`

문제:

현재 `staff_can_read_patients`는 활성 직원이면 역할과 진료 관계를 확인하지 않고 모든 환자 행을 읽게 한다. 의사에게는 본인 예약 또는 현재 진료 연속성에 필요한 환자만 보여야 한다는 다른 계획의 규칙과 어긋난다.

권장 수정:

- 접수직원·관리자의 범위와 의사의 범위를 별도 정책으로 나눈다.
- 의사는 본인 담당 예약 또는 확정된 진료 연속성 규칙에 연결된 환자만 조회하게 한다.
- API 필터와 RLS를 모두 적용하되, 최종 차단은 RLS가 담당한다.

완료 기준:

- 의사 A가 의사 B만 담당하는 환자를 UUID로 직접 조회해도 0행을 받는다.
- 접수직원·관리자의 허용 범위는 확정된 역할표와 일치한다.

이 항목은 `docs/consistency-review-2026-07-28-round2-5-consolidated.md`의 R2-02와 같은 문제를 데이터베이스 관점에서 재확인한 것이다.

### SDB-17. 상태전이 규칙표만 RLS가 빠져 있다

근거:

- 계획된 애플리케이션 테이블 31개 중 RLS 활성화 테이블은 30개
- 누락 테이블: `appointment_status_transitions`
- 테이블 생성: 기반 계획 `882~886`

문제:

이 표는 어떤 예약 상태 변경을 허용할지 결정하는 보안 규칙표다. 그런데 공개 `public` 스키마에 있으면서 RLS가 없고, 별도의 REVOKE도 계획되지 않았다. Supabase 기본 테이블 권한이 적용되면 클라이언트 역할이 허용 전이를 추가·삭제해 상태전이 트리거의 판단 기준을 바꿀 수 있다.

권장 수정:

- 가장 안전한 방법은 규칙표를 API 비노출 `private` 스키마로 옮기는 것이다.
- `anon`, `authenticated`, 일반 애플리케이션 역할의 모든 권한을 명시적으로 회수한다.
- 운영 중 규칙 변경이 필요하면 관리자 전용 RPC와 감사로그를 사용한다.

완료 기준:

- 환자·직원 인증 세션의 직접 SELECT/INSERT/UPDATE/DELETE가 모두 거부된다.
- 상태전이 트리거만 해당 표를 읽을 수 있다.

### SDB-18. 환자가 프로필의 인증 연결과 활성 상태까지 바꿀 수 있다

근거:

- 환자 프로필 UPDATE 정책: 환자 앱 계획 `80~83`
- 추가된 민감 칼럼: `patients.auth_user_id`(환자 앱 계획 `42`)

문제:

정책은 “본인 또는 가족 행인가”만 검사하고 변경 가능한 칼럼을 제한하지 않는다. 따라서 직접 Supabase UPDATE로 `auth_user_id`, `is_active`, 전화번호 등도 변경할 수 있다. 환자는 스스로 비활성화를 되돌리거나 가족 프로필의 인증 연결을 조작할 수 있다.

권장 수정:

- `patients` 직접 UPDATE를 제거하고 용도별 RPC로 분리한다.
- 일반 프로필 RPC는 이름·연락처처럼 허용된 칼럼만 변경한다.
- `auth_user_id`, `is_active`는 본인확인·관리자 절차에서만 변경한다.
- 필요하면 PostgreSQL 칼럼 권한도 함께 REVOKE한다.

완료 기준:

- 환자 역할로 `auth_user_id`, `is_active`, `created_at` 직접 변경이 실패한다.
- 비활성 환자는 본인 스스로 재활성화할 수 없다.

### SDB-19. 기존 가족 링크의 대상을 바꾸면 OTP를 우회할 수 있다

근거: 환자 앱 계획 `96~99`

문제:

INSERT 정책은 제거됐지만 UPDATE 정책은 `account_patient_id`가 본인인지만 검사한다. 기존 가족 링크 한 개가 있는 환자는 그 행의 `family_patient_id`를 임의의 다른 환자 UUID로 바꿀 수 있다. 그러면 `patient_owns()`가 새 대상을 즉시 가족으로 인정한다. `is_active = true`로 되돌려 해제된 링크를 직접 재활성화하는 것도 가능하다. 서비스의 `list_accessible_patient_ids()`도 `is_active=true`를 확인하지 않아 해제된 가족을 계속 반환한다.

권장 수정:

- 클라이언트의 `patient_family_links` 직접 UPDATE/DELETE를 모두 제거한다.
- 연결은 새 가족 생성 또는 OTP 확인 RPC만 수행한다.
- 해제는 대상 ID를 바꾸지 않고 `is_active=false`, `unlinked_at=now()`만 실행하는 RPC로 제한한다.
- 재연결은 새 OTP 또는 확정된 병원 정책을 거치게 한다.
- 가족 목록과 소유권 확인은 항상 활성 링크만 포함하게 한다.

완료 기준:

- 기존 링크의 `family_patient_id`, `account_patient_id`, `is_active` 직접 변경이 실패한다.
- OTP를 통과한 서버 트랜잭션만 신규 연결·재연결에 성공한다.

### SDB-20. 슬롯 UPDATE 정책이 상태 외의 의사·날짜·시간도 변경하게 한다

근거: 환자 앱 계획 `117~129`

문제:

`WITH CHECK`는 새 행의 `status`와 로그인 환자 존재만 확인한다. 따라서 환자는 자신이 UPDATE 가능한 빈 슬롯 또는 자기 예약 슬롯에서 `doctor_id`, `slot_date`, `start_time`까지 변경할 수 있다. 예약 생성과 슬롯 점유가 한 RPC에 묶이지 않아 “슬롯만 예약됨” 또는 “예약은 있는데 슬롯은 빈시간”인 상태도 만들 수 있다.

권장 수정:

- 환자 역할의 `appointment_slots` 직접 UPDATE 정책을 제거한다.
- 슬롯 점유·반납은 예약 생성·변경·취소 RPC 안에서 조건부 UPDATE로만 수행한다.
- RPC는 슬롯 ID, 현재 상태, 의사, 진료과, 날짜, 예약 소유자를 한 트랜잭션에서 검사한다.

완료 기준:

- 환자 세션의 슬롯 직접 UPDATE는 모두 실패한다.
- 같은 슬롯 동시 예약에서는 정확히 한 요청만 성공한다.

### SDB-21. 환자 조회 쿼리와 RLS 범위가 서로 맞지 않는다

근거:

- 환자의 슬롯 SELECT는 `status='빈시간'`만 허용: 환자 앱 계획 `113~115`
- 예약 목록·상세·방문이력은 예약된 슬롯과 LEFT JOIN: 환자 앱 계획 `2100~2145`, `2447~2465`
- 대기인원은 같은 의사의 다른 환자 예약을 COUNT: 환자 앱 계획 `2150~2180`
- 환자는 본인·가족 예약만 SELECT 가능: 환자 앱 계획 `414~416`
- 환자의 의사 조회 정책은 `is_active`를 검사하지 않음: 환자 앱 계획 `109~111`

문제:

- 예약된 슬롯은 환자 SELECT 정책에서 숨겨지므로 자기 예약 화면의 날짜·시간이 NULL로 보일 수 있다.
- “내 앞 대기 인원” COUNT는 RLS가 다른 환자 예약을 제거하므로 실제 전체 대기열이 아니라 본인·가족만 세게 된다.
- 비활성 진료과는 환자 정책에서 숨겨져 과거 예약 INNER JOIN 결과까지 사라질 수 있다.
- 반대로 비활성 처리된 의사는 신규 예약 목록에 계속 노출될 수 있다.

권장 수정:

- 본인 예약에 연결된 예약 슬롯의 제한된 칼럼을 읽을 수 있는 정책 또는 안전한 뷰를 만든다.
- 대기인원은 본인 예약 소유권을 확인한 `SECURITY DEFINER` 집계 RPC가 숫자만 반환하게 한다.
- 과거 기록에 필요한 의사·진료과 이름은 비활성 여부와 무관하게 안전한 칼럼만 조회할 수 있게 한다.
- 신규 예약의 의사 목록은 활성 의사만 반환하고, 과거 기록 조회 경로와 분리한다.

완료 기준:

- 자기 예약의 날짜·시간이 정상 표시된다.
- 테스트용 타 환자 3명을 앞에 두면 집계 RPC가 3을 반환하되 이름·ID는 노출하지 않는다.
- 비활성 진료과의 과거 진료기록도 보존된 이름과 함께 조회된다.

### SDB-22. 비활성 환자도 직접 Supabase 접근 권한이 남는다

근거:

- `patient_owns()`가 현재 환자의 `is_active`를 검사하지 않음: 환자 앱 계획 `44~62`
- 다수 정책의 환자 존재 검사에도 `is_active`가 없음: 환자 앱 계획 `92~129`, `482~501`, `662~665`
- 챗봇 환자 정책도 활성 상태를 검사하지 않음: AI 챗봇 계획 `192~201`

문제:

FastAPI의 `get_current_patient`는 비활성 환자를 거부하지만, 환자가 Supabase REST/Realtime을 직접 호출하면 RLS는 여전히 본인·가족 데이터 접근을 허용한다. 계정 중지의 효과가 API 경로에만 있고 DB 최종 방어선에는 없다.

권장 수정:

- `private.current_patient_id()`가 `is_active=true`를 반드시 검사하게 한다.
- 모든 환자 RLS는 이 헬퍼를 공통으로 사용한다.
- 가족 대상 환자도 비활성·병합 상태를 어떻게 처리할지 명시한다.
- 챗봇 대화 정책에도 같은 활성 계정 기준을 적용한다.

완료 기준:

- 환자를 비활성화한 직후 FastAPI뿐 아니라 직접 REST, Realtime, RPC 접근도 모두 실패한다.

### SDB-23. AI 챗봇 DB 풀 호출이 비동기 인터페이스와 맞지 않는다

근거:

- 기반의 `get_pool` 정의는 `async def`: 기반 계획 `2130~2134`
- AI 챗봇 계획에서 `pool = get_pool()` 또는 `get_pool().fetchval(...)` 사용: AI 계획 `994`, `1024`, `1044`, `1083`, `1114`, `1214`, `1717`, `2389` 등 30회 이상
- AI 오류 처리에서 비동기 `log_error()`를 await하지 않음: AI 계획 `734`, `2550`, `2848`, `3006`

문제:

`get_pool()`의 결과는 풀 객체가 아니라 코루틴(coroutine, 아직 실행하지 않은 비동기 작업)이다. 현재 코드대로면 첫 DB 호출에서 `coroutine has no attribute fetch/fetchval/acquire` 오류가 난다. `log_error()`도 실행되지 않아 오류로그가 남지 않는다.

권장 수정:

- 모든 AI 서비스에서 `pool = await get_pool()`로 통일한다.
- `await get_pool().fetchval(...)`처럼 괄호가 잘못된 호출도 두 문장으로 분리한다.
- 모든 비동기 오류기록을 `await log_error(...)`로 호출한다.
- 정적 검사와 AI 서비스 스모크 테스트를 추가한다.

완료 기준:

- `rg` 기준 await 없는 `get_pool()`·`log_error()` 호출이 0개다.
- 지식자료 생성, 상담 시작, 메시지 저장, 티켓 생성의 최소 통합 테스트가 실제 DB에서 통과한다.

완료 기준:

### SDB-08. 환자용 진료기록 뷰가 기본 테이블 RLS를 우회한다

### SDB-09. 핵심 외래키와 RLS 조회 칼럼의 인덱스가 부족하다

### SDB-10. 소프트 삭제 원칙과 실제 DELETE SQL이 충돌한다

근거:

- 전역 원칙: 기반 계획 상단 “어떤 테이블도 실제 DELETE를 사용하지 않는다”
- 관리자 `FOR ALL` 정책: 기반 계획 `220~232`, `403~415`, `796~799`, `1750~1753`
- 의사 상용구 `FOR ALL`: 직원 웹 계획 `53~56`
- 문진응답·기기토큰 `FOR ALL`: 환자 앱 계획 `486~489`, `662~665`
- 가족 연결 실제 DELETE 정책: 환자 앱 계획 `101~103`
- 문진 템플릿 중복 정리 DELETE: 기반 계획 `1882~1884`
- 지식자료 하위 행의 `ON DELETE CASCADE`: AI 챗봇 계획 `348`, `360`
- 슬롯 재생성·토큰 해제·지식조각 재생성의 실제 DELETE: 직원 웹 계획 `5464`, 환자 앱 계획 `2640`, AI 챗봇 계획 `1004`, `1132`

문제:

`FOR ALL`은 SELECT/INSERT/UPDATE뿐 아니라 DELETE도 포함한다. 따라서 현재 정책은 관리자에게 직원·진료과·일정·슬롯·문진 양식의 실제 삭제를 허용한다. 가족 연결은 `is_active`, `unlinked_at`으로 해제하도록 설계했지만 별도 DELETE 정책도 있다. 문진 템플릿 정리는 UUID의 대소 비교로 임의의 한 행을 삭제하며, 참조 중인 `questionnaire_responses`가 있으면 외래키 때문에 마이그레이션 자체가 실패할 수 있다. 지식자료는 `kb_documents`가 삭제되면 검색 조각과 수정이력이 연쇄 삭제되어 과거 근거와 변경 기록이 사라질 수 있다.

권장 수정:

- 보존 대상 업무 테이블의 `FOR ALL`을 SELECT/INSERT/UPDATE 정책으로 분리하고 DELETE 권한을 제거한다.
- 가족 연결 DELETE 정책과 DELETE 권한을 제거한다.
- 해제는 검증된 RPC가 `is_active = false`, `unlinked_at = now()`만 변경하게 한다.
- 문진 템플릿 중복은 임의 삭제하지 말고 명시적 버전·활성 상태 정책으로 정리한다.
- 지식자료는 `status = 'archived'`로 보관하고, 특히 수정이력 외래키의 `ON DELETE CASCADE`를 제거한다.
- 불가피한 일회성 데이터 정리는 백업, 대상 목록, 선택 기준, 건수 검증을 포함한 별도 운영 마이그레이션으로 분리한다.

완료 기준:

- 애플리케이션 역할은 업무 테이블을 DELETE할 수 없다.
- 가족 해제 후 과거 기록은 보존되고 현재 접근권한만 사라진다.

### SDB-11. 6자리 예약번호 생성의 충돌 확인이 원자적이지 않다

근거: 기반 계획 `666~706`

문제:

트리거는 새 번호가 없는지 먼저 SELECT한 뒤 INSERT한다. 동시에 두 트랜잭션이 같은 번호를 뽑으면 둘 다 “없음”을 확인할 수 있다. 유일 인덱스가 중복 저장은 막지만 두 번째 예약 전체가 실패하며, 주석에 적힌 “충돌 시 재시도”는 실제 INSERT 충돌을 재시도하지 않는다.

권장 수정:

- 예약 생성 전체를 DB 함수로 감싸 `unique_violation` 발생 시 새 코드를 만들어 제한 횟수만큼 재시도한다.
- 또는 더 긴 코드로 충돌 가능성을 충분히 낮추되 유일 제약은 유지한다.
- 예약번호 발급과 슬롯 점유는 짧은 트랜잭션 안에서 완료한다.

완료 기준:

- 다수 동시 예약 테스트에서 예약번호가 모두 유일하고, 코드 충돌 때문에 정상 예약 전체가 실패하지 않는다.

### SDB-12. 행위자가 없는 상태 변경은 이력 없이 조용히 통과한다

근거:

- 기반 계획 `937~955`
- 환자 앱 계획 `460~478`

문제:

JWT가 없는 시드·배치·관리 작업에서는 `changed_by`를 찾지 못해 상태 변경 이력을 기록하지 않는다. “상태가 바뀌면 이력이 반드시 남는다”는 감사 원칙에 예외가 생긴다. 환자 앱 계획의 행위자 제약은 직원과 환자 중 하나 이상만 요구하므로 두 행위자가 동시에 들어간 모순된 이력도 허용한다.

권장 수정:

- `actor_type`을 `staff`, `patient`, `system`으로 구분하고 각 행위자 ID를 선택적으로 저장한다.
- 시스템 작업에는 명시적인 시스템 행위자와 사유를 전달한다.
- 직원/환자 두 칼럼을 유지한다면 둘 중 정확히 하나만 채워지도록 XOR CHECK를 적용한다.
- 행위자를 결정할 수 없는 변경은 조용히 건너뛰지 말고 실패시키거나 운영 오류로그에 남긴다.

완료 기준:

- 직원, 환자, 크론, 시드·관리 작업의 모든 실제 상태 변경에 행위자 유형·시각·사유가 남는다.

### SDB-13. 환자가 자기 자신을 가족으로 연결할 수 있다

alter table public.patient_family_links

완료 기준:

- 자기 자신 연결 INSERT가 DB 제약에서 실패한다.
- 같은 두 환자의 중복 활성 연결도 허용되지 않는다.

### SDB-24. 직원 일정 서비스가 인증 사용자 없이 직원 전용 RLS를 호출한다

근거:

- 직원 일정 조회에서 `acquire_as(None)` 사용: 직원 웹 계획 `5213`, `5226`, `5266`
- 직원 RLS는 현재 인증 사용자가 활성 직원인지 검사함

문제:

`acquire_as(None)`은 DB 역할만 `authenticated`로 바꾸고 JWT의 사용자 ID(`sub`)는 넣지 않는다. 따라서 `auth.uid()`는 NULL이고, 활성 직원만 허용하는 RLS는 진료과·일정 규칙·예외 일정 조회를 모두 거부하거나 빈 결과를 반환한다. 애플리케이션 화면에서 이미 직원을 인증했더라도 그 신원이 DB 세션으로 전달되지 않는 문제다.

권장 수정:

- 일정 서비스 함수가 `StaffContext` 또는 `auth_user_id`를 받도록 한다.
- 모든 직원용 DB 접근을 인증 사용자 ID가 설정된 공통 연결 헬퍼로 통일한다.
- 관리자, 의사, 비활성 직원, 환자 역할별 일정 조회 통합 테스트를 추가한다.

완료 기준:

- 활성 직원은 허용된 일정 데이터를 보고, 환자·비활성 직원·인증 ID가 없는 요청은 DB에서 거부된다.

### SDB-25. 애플리케이션 연결 역할과 연결 풀 제한이 명확하지 않다

근거:

- 공통 풀은 `asyncpg.create_pool(settings.database_url)`만 호출함: 기반 계획 `2130~2154`
- 로컬 예시 URL은 `postgres` 사용자임: 기반 계획 `90`

문제:

연결 문자열이 소유자 또는 서비스 역할이면 RLS를 우회할 수 있어 애플리케이션 코드 한 곳의 실수가 전체 의료데이터 접근으로 이어진다. 또한 풀의 최소·최대 크기, 명령 제한시간, 유휴 트랜잭션 제한이 없어 여러 Railway 프로세스가 DB 연결 한도를 소진하거나 오래 열린 트랜잭션이 잠금을 유지할 수 있다. Supabase 트랜잭션 풀러와 함께 사용할 경우 prepared statement 설정도 드라이버와 맞춰야 한다.

권장 수정:

- 일반 API는 필요한 테이블·함수만 사용할 수 있고 RLS를 따르는 별도 최소권한 역할을 사용한다.
- 관리자·백그라운드 작업의 권한 연결은 별도 풀과 별도 코드 경로로 격리한다.
- 프로세스 수를 포함해 `min_size`, `max_size`, `command_timeout`을 계산하고 DB의 `statement_timeout`, `idle_in_transaction_session_timeout`도 설정한다.
- Supabase 직접 연결, 세션 풀러, 트랜잭션 풀러 중 배포 환경의 방식을 명시하고 asyncpg prepared statement 호환성을 검증한다.

완료 기준:

- API 연결로는 RLS 우회와 임의 DDL을 할 수 없다.
- 전체 프로세스의 최대 연결 합계가 Supabase 연결 한도 안에 있고, 느린 쿼리와 유휴 트랜잭션이 제한시간 후 종료된다.

### SDB-26. 진료 일정 규칙과 슬롯 재생성이 동시 실행에 안전하지 않다

근거:

- 일정 규칙에 `(doctor_id, weekday)` 유일 제약과 시간 범위 CHECK가 없음: 기반 계획 `373~383`
- 규칙 저장이 조회 후 INSERT/UPDATE 순서임: 직원 웹 계획 `5233~5262`
- 슬롯 재생성이 슬롯별 DELETE·INSERT를 반복함: 직원 웹 계획 `5427~5464`

문제:

같은 의사·요일 규칙을 두 요청이 동시에 만들면 중복 규칙이 생길 수 있다. 종료시간이 시작시간보다 이르거나 슬롯 길이·최대 예약 수가 0 이하인 값도 DB가 허용한다. 슬롯 재생성 두 건이 동시에 실행되면 서로 삭제·삽입을 방해하거나 유일 제약 충돌이 나고, 중간 실패 시 일부 날짜만 새 규칙이 반영될 수 있다.

권장 수정:

- `(doctor_id, weekday)`에 UNIQUE를 추가한다.
- `start_time < end_time`, 양수인 슬롯 길이·최대 예약 수, 점심시간의 시작·종료 동시 입력을 CHECK로 강제한다.
- 조회 후 분기 대신 `INSERT ... ON CONFLICT ... DO UPDATE`를 사용한다.
- 의사 ID 단위 트랜잭션 advisory lock을 잡고, 재생성 대상은 가능한 한 집합 기반 DELETE/INSERT 또는 UPSERT로 짧게 처리한다.

완료 기준:

- 같은 의사의 규칙 저장·슬롯 재생성을 동시에 여러 번 실행해도 중복, 부분 반영, 예약된 슬롯 삭제가 발생하지 않는다.

### SDB-27. 알림 기록이 실제 전송 성공을 뜻하지 않고 기기 토큰 소유권도 모호하다

근거:

- 기기 토큰 UNIQUE는 `(patient_id, fcm_token)` 조합임: 환자 앱 계획 `652~658`
- 알림 로그를 먼저 커밋한 뒤 외부 푸시·SMS를 호출함: 환자 앱 계획 `2812~2845`

문제:

같은 FCM 토큰이 여러 환자에게 동시에 연결될 수 있어 공용·양도 기기에서 이전 환자의 알림이 잘못 전달될 수 있다. 알림 로그는 외부 전송 전에 `sent`처럼 기록되므로 전송이 실패해도 재시도가 이미 보낸 알림으로 오인할 수 있다. 푸시 토큰이 존재하지만 모든 푸시가 실패한 경우 SMS 대체 경로가 실행되지 않고, 실제 SMS여도 채널을 항상 `push`로 기록하는 흐름도 있다.

권장 수정:

- `fcm_token` 자체를 전역 UNIQUE로 만들고 로그인·등록 시 현재 환자에게 원자적으로 소유권을 이전한다.
- 알림을 `pending/sending/sent/failed`, `attempt_count`, `last_error`, `sent_at`을 가진 outbox로 저장한다.
- 워커는 `FOR UPDATE SKIP LOCKED`로 작업을 가져오고 외부 전송 성공 후에만 `sent`로 바꾼다.
- 모든 푸시 실패 시 SMS 대체 여부를 정책으로 정하고 실제 채널을 기록한다.

완료 기준:

- 한 기기 토큰은 한 환자만 소유한다.
- 전송 실패는 성공으로 기록되지 않고 안전하게 재시도되며, 중복 워커가 같은 알림을 동시에 처리하지 않는다.

### SDB-28. 가족 연결 OTP에 시도 제한이 없고 해제된 관계를 다시 연결하기 어렵다

근거:

- 요청 테이블에 시도 횟수·잠금 정보가 없음: 환자 앱 계획 `2911~2919`
- 6자리 코드를 일반 SHA-256으로 해시함: 환자 앱 계획 `3069~3070`
- 검증 후 가족 관계를 단순 INSERT함

문제:

6자리 코드는 경우의 수가 작아 일반 SHA-256 해시가 유출되면 빠르게 전수 대입할 수 있다. 온라인 검증 횟수, 요청 재전송 간격, 전화번호별 제한도 없어 무차별 대입과 SMS 남용을 막기 어렵다. 기존 관계를 소프트 삭제한 뒤에는 복합 UNIQUE 때문에 검증이 성공해도 새 관계 INSERT가 실패할 수 있다.

권장 수정:

- 서버 비밀키를 사용한 HMAC 또는 느린 비밀번호 해시를 적용하고 원문 코드는 저장하지 않는다.
- `attempt_count`, `max_attempts`, `locked_at`과 요청 재전송 간격·IP/계정/전화번호별 제한을 둔다.
- 새 요청을 만들 때 같은 대상의 이전 미사용 코드를 만료시킨다.
- OTP 검증이 성공한 트랜잭션에서만 `ON CONFLICT`로 기존 관계를 재활성화한다.

완료 기준:

- 제한 횟수 초과, 만료, 재사용 코드는 실패한다.
- 해제된 가족은 새 OTP 검증 후에만 정상적으로 다시 연결된다.

### SDB-29. 진료기록 수정 이력을 실제 변경 없이 만들 수 있다

근거:

- 의사가 자기 ID로 보이는 수정 이력 행을 직접 INSERT할 수 있음: 기반 계획 `1408~1410`

수정 이력 테이블에 직접 INSERT할 수 있으면 실제 진료기록은 바꾸지 않고도 임의의 이전 내용·사유를 가진 “수정 이력”을 만들 수 있다. `revised_by`는 현재 의사와 일치하지만 이 행이 실제 원본 수정 트랜잭션에서 생겼는지는 보장되지 않아 감사 기록의 신뢰성이 떨어진다. 내부 메모는 현재 정책이 작성자를 올바르게 묶으므로 그 방식을 다른 감사 테이블에도 일관되게 적용해야 한다.

- 감사 테이블은 일반 사용자가 UPDATE/DELETE하지 못하게 한다.

완료 기준:

- 실제 업무 변경 없이 이력만 만드는 직접 요청이 DB에서 거부된다.

### SDB-30. 외부 임베딩 API를 DB 트랜잭션 안에서 기다린다

근거:

- 지식자료 조각 재생성 중 `embedder.embed(...)`를 await함: AI 챗봇 계획 `1002~1013`
- 이 함수가 문서 생성·수정 트랜잭션 안에서 호출됨: AI 챗봇 계획 `1025~1034`, `1083~1110`

문제:

외부 임베딩 API가 느리거나 실패하는 동안 DB 연결과 행 잠금이 계속 유지된다. 여러 문서를 동시에 처리하면 연결 풀이 고갈되고 다른 편집 요청이 오래 대기할 수 있다. 네트워크 호출은 DB 트랜잭션처럼 원자적으로 되돌릴 수도 없다.

권장 수정:

- 텍스트 분할과 임베딩 생성은 DB 트랜잭션 밖에서 수행한다.

- 대용량 자료는 outbox/job 테이블과 워커를 사용해 `pending → processing → ready/failed` 상태로 처리한다.
- 같은 문서의 동시 재생성에는 버전 비교 또는 문서 단위 advisory lock을 사용한다.

완료 기준:

- 외부 API 지연 중 열린 DB 트랜잭션이 없고, 실패 후 재시도해도 이전 정상 검색 조각이 사라지지 않는다.

### SDB-31. 병원 업무 날짜에 KST와 서버 기본 시간대가 섞여 있다

근거:

- SQL에서 세션 기준 `current_date` 사용: 기반 계획 `694`, `779`; 환자 앱 계획 `1489`, `2117`, `2170`
- 일부 Python 코드는 `Asia/Seoul`을 사용하지만 일정 코드는 `date.today()`를 사용함: 환자 앱 계획 `1655`, `1717`; 직원 웹 계획 `5427`, `5491`

문제:

Railway나 Postgres 세션이 UTC이면 한국 자정 전후에 “오늘 예약”, 예약번호 만료, 재예약 기간, 슬롯 생성 날짜가 서로 하루 다르게 계산될 수 있다. `date`를 `timestamptz`와 비교할 때도 세션 시간대에 따라 만료 순간이 달라진다.

권장 수정:

- 업무 시간대를 `Asia/Seoul`로 한 곳에 정의하고 SQL과 애플리케이션에서 공통 사용한다.
- 업무 날짜는 `(now() at time zone 'Asia/Seoul')::date`처럼 명시한다.
- 예약번호 만료 순간도 한국 자정을 명시적으로 `timestamptz`로 변환한다.
- 서버 기본 시간대가 UTC인 통합 테스트에서 한국 자정 전후 사례를 검사한다.

완료 기준:

- UTC 오후 3시, 한국 자정 전후에도 SQL과 Python이 같은 업무 날짜와 만료시각을 계산한다.

## 5. P2 — 데이터 증가 전 최적화

### SDB-14. RLS에서 `auth.uid()`를 행마다 반복 계산한다

근거: 네 구현 계획 전반의 다수 RLS 정책이 `auth.uid()`를 직접 호출함.

문제:

Supabase 권장 방식은 RLS에서 `(select auth.uid())`를 사용해 요청마다 한 번 계산하도록 하는 것이다. 직접 호출은 큰 테이블에서 행마다 반복 평가되어 느려질 수 있다.

권장 수정:

```sql
-- 변경 전
using (auth_user_id = auth.uid())

-- 변경 후
using (auth_user_id = (select auth.uid()))
```

RLS가 조회하는 `staff.auth_user_id`, `patients.auth_user_id`에는 UNIQUE 인덱스가 유지되어야 한다.

### SDB-15. 다수 정책에 적용 역할 `TO authenticated`가 명시되지 않았다

근거: 기반 계획의 다수 `create policy` 구문.

문제:

역할을 생략한 정책은 기본적으로 `PUBLIC`에 적용된다. `auth.uid()`가 NULL이어서 익명 요청이 대부분 거부되더라도 최소 권한 원칙과 정책 의도가 불명확하다.

권장 수정:

- 로그인 사용자 정책에는 `to authenticated`를 명시한다.
- 익명 조회가 정말 필요한 테이블만 `to anon` 정책을 별도로 만든다.
- 서비스 역할 우회는 백엔드의 제한된 연결에서만 사용한다.

### SDB-16. 모든 주요 테이블이 무작위 UUIDv4 기본키를 사용한다

근거: 계획 전반의 `id uuid primary key default gen_random_uuid()`.

문제:

무작위 UUID는 데이터가 매우 커지면 B-tree 인덱스 페이지를 흩어지게 해 쓰기 성능과 저장 효율을 떨어뜨릴 수 있다. 다만 현재 규모에서 즉시 재설계해야 할 차단 문제는 아니다.

권장 수정:

- 외부 노출 식별자로 UUID가 필요한 현재 설계는 유지할 수 있다.
- 대규모 로그·메시지 테이블은 UUIDv7 또는 순차 bigint 내부키를 검토한다.
- 실제 데이터 증가와 인덱스 크기를 측정한 뒤 결정한다.

### SDB-32. 목록 API에 일관된 페이지네이션과 최대 개수 제한이 없다

근거: 환자 예약·방문이력, 직원 감사·취소 목록, 지식자료·수정이력·티켓·대화·예시답변 목록 쿼리 전반.

문제:

운영 데이터가 쌓이면 한 요청이 전체 행을 읽고 전송해 응답시간과 메모리 사용량이 계속 증가한다. 단순 `OFFSET` 방식은 뒤 페이지로 갈수록 느려지고, 조회 도중 새 행이 추가되면 중복·누락도 생길 수 있다.

권장 수정:

- 큰 목록은 `(created_at, id)` 또는 업무 정렬키를 사용한 커서 페이지네이션을 적용한다.
- 기본·최대 `limit`을 정하고 정렬키와 필터에 맞는 복합 인덱스를 둔다.
- 진료과처럼 매우 작은 기준정보 목록만 전체 조회 예외로 명시한다.

### SDB-33. 슬롯 재생성에 반복 쿼리와 행별 쓰기가 있다

근거: 직원 웹 계획의 슬롯 재생성 로직 `5427~5464`.

문제:

슬롯마다 예약 여부를 별도 조회하고 DELETE/INSERT를 반복하면 N+1 쿼리가 발생한다. 날짜 범위와 의사 수가 늘수록 왕복 횟수와 트랜잭션 시간이 급격히 커진다.

권장 수정:

- 예약된 슬롯은 한 번의 조인 또는 집합 쿼리로 가져온다.
- 생성할 슬롯은 배열/레코드 묶음, `unnest`, 일괄 INSERT/UPSERT로 처리한다.
- 변경 없는 슬롯은 쓰지 않고, 실행 전후 생성·유지·제외 건수를 기록한다.

### SDB-34. 운영 쿼리와 DB 상태를 측정하는 기준이 없다

근거: 배포 계획에 `pg_stat_statements`, 대표 쿼리 실행계획, autovacuum·교착·연결 수 점검 기준이 명시되지 않음.

문제:

인덱스와 RLS를 정적으로 잘 설계해도 실제 데이터 분포에서는 다른 실행계획이 선택될 수 있다. 측정 기준이 없으면 느린 쿼리, 연결 고갈, deadlock, 테이블 팽창을 장애가 난 뒤에야 알게 된다.

권장 수정:

- 가능한 환경에서는 `pg_stat_statements`로 총시간·평균시간·호출횟수 상위 쿼리를 정기 확인한다.
- 오늘 예약, 의사 대기열, 환자 방문이력, RLS 직접 접근의 대표 `EXPLAIN (ANALYZE, BUFFERS)` 결과를 기준선으로 보관한다.
- 연결 사용률, 장기 트랜잭션, deadlock, autovacuum 지연, 테이블·인덱스 크기에 경보 기준을 둔다.

## 6. 긍정적으로 확인된 설계

- 민감한 테이블 대부분에 RLS를 켜려는 방향이 맞다.
- `appointment_slots`의 조건부 UPDATE는 같은 슬롯의 이중예약을 막는 좋은 원자적 패턴이다.
- 의사·진료과·슬롯의 관계를 DB 트리거에서도 검사해 서버 우회를 방지하려는 점이 좋다.
- 완료된 진료기록 수정에 `FOR UPDATE`, 예상 `updated_at`, 수정 사유, 이전 값 보존을 한 트랜잭션으로 묶은 방향이 좋다.
- 예약번호에 유일 인덱스를 두고 만료 조건에 `now()`를 넣은 부분 인덱스를 피한 판단은 맞다.
- 챗봇 메시지·임베딩 검색에는 핵심 복합/HNSW 인덱스가 일부 계획되어 있다.
- 외부 SMS·푸시 호출을 DB 잠금 트랜잭션 밖에서 수행하려는 서비스 구조가 유지된다면 잠금 경합을 줄일 수 있다.

### 10.1 “반영 완료”가 의미하는 범위

이 보고서에서 사용하는 **계획 반영**과 **구현 완료**는 서로 다른 상태다.

| 구분 | 의미 | 현재 상태 |
|---|---|---|
| 검토 보고서 작성 | 위험과 권장 수정 방법을 문서로 기록함 | 완료 |
| 계획 문서 반영 | 앞으로 만들 SQL·서비스·테스트 계획에 수정 방향을 적음 | P0는 완료 |
| 구현 반영 | 실제 `supabase/migrations`, 백엔드, 웹·앱 코드에 적용함 | 미착수 |
| 검증 완료 | 로컬 DB 초기화, RLS 직접 접근, 동시성 테스트가 실제로 통과함 | 미검증 |

2026-07-28 현재 저장소에는 `supabase/`, `backend/`, `frontend/`, `web/`, `mobile/` 구현 디렉터리가 없다. 따라서 9장의 `[x]`는 **실제 데이터베이스 수정 완료가 아니라 계획 문서 수정 완료**를 뜻한다.

34개 SDB 항목의 현재 상태는 다음과 같다.

| 범위 | 항목 수 | 계획 문서 상태 | 실제 구현·테스트 상태 |
|---|---:|---|---|
| P0: SDB-01~06, SDB-17~23 | 13 | 구체적인 수정 위치까지 반영 | 미구현·미검증 |
| P1: SDB-07~13, SDB-24~31 | 15 | 각 계획서 상단에 보고서 포인터만 추가하고 실제 수정은 구현 시점으로 연기 | 미구현·미검증 |
| P2: SDB-14~16, SDB-32~34 | 6 | 기술부채로 추적하며 구현·측정 시점으로 연기 | 미구현·미검증 |

결론적으로 **보고서 내용 전체가 구현에 반영된 상태는 아니다.** P0는 설계·계획에 반영됐고, P1·P2는 대부분 “나중에 반드시 확인할 항목”으로 연결만 해 둔 상태다.

| 고객 완료 시나리오 | ERD 지원 | 판정 | 남은 조건 |
|---|---|---|---|
| 1. 환자가 앱으로 예약 | 환자, 진료과, 의사, 슬롯, 예약, 문진, 알림 테이블이 연결됨 | 조건부 적합 | 슬롯 원자적 점유, 알림 전송상태·재시도, 실제 앱↔직원 웹 통합 테스트 필요 |
| 2. 상담봇을 통한 예약 | 상담방, 메시지, 예약 확인 카드, 슬롯, 일반 예약이 연결됨 | 조건부 적합 | 카드 사용과 예약 생성을 한 트랜잭션으로 처리하고 일반 예약과 같은 중복방지 규칙을 적용해야 함 |
| 3. 전화 예약과 당일 방문 | 로그인 계정이 없는 환자, 직원 생성 예약, 슬롯 없는 워크인을 표현할 수 있음 | 구조 적합 | 동명이인 재확인과 직원 권한 테스트 필요 |
| 4. 도착부터 진료 완료 | 예약 상태, 상태 이력, 문진, 진료기록이 예약을 중심으로 연결됨 | 조건부 적합 | 진료기록 완료와 예약 `진료완료` 전이를 같은 트랜잭션으로 처리해야 함 |
| 5. 완료 진료기록 수정 | 현재 기록과 수정 전 전체 내용·수정자·사유가 분리됨 | 구조 적합 | 수정 RPC만 이력을 만들 수 있도록 권한을 차단하고 동시수정 테스트 필요 |
| 6. 의사 일정 변경 | 날짜 예외와 `needs_rescheduling`, 재예약 서비스와 사유 이력이 계획됨 | 조건부 적합 | 일정 변경 경고·영향 목록·재예약·알림 통합 테스트가 필요하며 전후 슬롯 감사는 선택 보강 사항임 |
| 7. 상담봇에서 직원에게 넘기기 | 상담 메시지와 `support_tickets`에 대화 요약·사유·담당자·상태를 저장함 | 부분 적합 | 예약과 무관한 직원 답변 알림을 현재 `notification_log`로 표현하기 어려움 |
| 8. 중복 예약과 중복 클릭 방지 | 슬롯의 조건부 상태 변경과 챗봇 카드 `nonce`가 계획됨 | 조건부 적합 | 모든 예약 경로가 같은 원자적 서비스를 사용하고 실제 동시성 테스트를 통과해야 함. 일반 멱등키는 선택 가능한 추가 방어임 |
| 9. 역할별 권한 확인 | RLS 계획이 별도 문서에 존재함 | ERD만으로 판정 불가 | 8.2의 역할별 직접 SELECT/INSERT/UPDATE/DELETE 테스트가 통과해야 함 |
| 10. 하루 운영 보고 | 예약 현재값·상태 변경시각·생성경로·상담 티켓으로 대부분 집계 가능 | 구조 적합 | 시간대 기준, 페이지네이션, 실행계획, CSV 다운로드 서비스 검증 필요 |

### 10.3 기존 P1·P2와의 중복 및 추가 권고 분류

아래 REQ-DB 항목은 **새로운 P0 문제가 아니다.** 기존 SDB·후속 정합성 검토와 중복되는 내용, 고객 시나리오 관점의 확장, 선택적 감사 보강을 구분해야 한다.

| 항목 | 기존 항목과의 관계 | 재분류 | 처리 판단 |
|---|---|---|---|
| REQ-DB-01 | SDB-27의 알림 outbox와 중복하고 상담 답변 알림 원인만 추가 | P1 확장 | 알림 기능 구현 때 함께 반영 |
| REQ-DB-02 | 후속 정합성 검토 R5-09와 동일 | P2 기존 항목 | 새 이슈로 계산하지 않고 R5-09를 참조 |
| REQ-DB-03 | 기존 재예약 서비스의 감사정보를 더 자세히 남기는 제안 | P2 보강 | 고객이 변경 전후 슬롯 감사까지 원하는지 결정 후 적용 |
| REQ-DB-04 | 고객이 명시한 변경자·사유는 현재 계획이 충족하며 전후 순번은 추가 제안 | 선택적 P2 | 필수 불일치가 아니라 감사 편의 개선 |
| REQ-DB-05 | 조건부 슬롯 UPDATE가 이미 핵심 중복방지를 담당하며 멱등키는 추가 방어 | 선택적 P2 | 동시성 테스트로 충분하면 생략 가능 |
| REQ-DB-06 | 계획 ERD의 ERD-04와 동일하고 SDB-10의 삭제·보존 정책과 연관 | P2, 감사정책에 따라 P1 | 장기간 근거 재현을 요구할 때 연결 테이블 적용 |

따라서 REQ-DB-01~06을 기존 P1·P2보다 앞서 모두 반영해야 하는 것으로 해석하면 안 된다. P0 계획을 먼저 구현하고, 각 기능을 만들 때 기존 P1·P2와 함께 판단한다.

#### REQ-DB-01. 예약과 무관한 알림 원인을 표현할 수 없다 — P1, SDB-27 확장

고객은 예약 알림뿐 아니라 사전문진 미작성, 직원 상담 답변, 진료 완료 안내를 요구한다. 현재 `notification_log.appointment_id`는 예약에만 연결되고 전송상태도 없다.

권장 수정:

- `appointment_id`를 선택값으로 바꾸고 `conversation_id` 또는 `support_ticket_id`를 추가하거나, `subject_type + subject_id` 구조를 사용한다.
- `status(pending/sending/sent/failed)`, `attempt_count`, `next_attempt_at`, `last_error`, `sent_at`을 둔다.
- 같은 업무 알림의 중복 생성을 막을 `idempotency_key` 또는 업무별 UNIQUE 제약을 둔다.
- SDB-04, SDB-27과 같은 작업에서 함께 반영한다.

#### REQ-DB-02. 사전문진 양식의 활성 버전이 없다 — P2, R5-09와 동일

고객은 진료과별 질문을 관리하고 환자가 진료 전까지 답변을 수정할 수 있기를 원한다. 현재 양식에는 `department_id`, `questions`만 있어 어느 양식이 현재 활성본인지, 과거 응답이 어떤 질문 버전을 기준으로 작성됐는지 명확하지 않다.

이 항목은 새 발견이 아니라 `docs/consistency-review-2026-07-28-round5.md`의 R5-09를 데이터베이스 관점으로 다시 적은 것이다.

권장 수정:

- `version`, `is_active`, `created_at`, `retired_at`을 추가한다.
- 진료과별 활성 양식은 한 개만 허용하는 부분 UNIQUE 인덱스를 둔다.
- 사용된 양식 행은 수정하지 않고 새 버전을 생성하거나, 응답에 질문 스냅샷을 함께 저장한다.
- 도착 이후 문진 변경·삭제를 RLS 또는 전용 RPC에서 차단한다.

#### REQ-DB-03. 예약 변경의 전후 연결 보강 — P2 제안

`needs_rescheduling`은 재예약 필요 여부만 알려준다. 고객이 요구한 예약시간 변경·일정변경 영향 추적을 위해서는 어떤 예약이 어느 예약 또는 슬롯으로 이동했는지 확인할 수 있어야 한다.

현재 계획도 재예약을 짧은 트랜잭션으로 처리하고 `appointment_status_history`에 변경자와 사유를 남기므로 고객의 기본 요구는 충족한다. 아래 구조는 변경 전후 슬롯을 직접 조회해야 한다는 운영정책이 있을 때 추가하는 감사 보강안이다.

권장 수정:

- 간단한 방식: `appointments.rescheduled_from_appointment_id` 자기참조 FK 추가
- 상세 감사 방식: `appointment_changes(appointment_id, change_type, old_slot_id, new_slot_id, changed_by_staff_id, changed_by_patient_id, reason, changed_at)` 추가
- 취소와 새 예약 생성이 한 업무였음을 같은 트랜잭션 또는 공통 변경 ID로 묶는다.

#### REQ-DB-04. 대기 순서 변경의 전후 값 보강 — 선택적 P2

현재 계획은 `appointment_status_history`에 `진료대기 → 진료대기`와 변경자·사유를 넣지만, 이전 순서와 새 순서를 저장하지 않는다.

고객 요구사항은 순서를 바꾼 사람과 이유를 남기는 것이며 현재 계획이 이를 충족한다. 따라서 이전·새 순번 저장은 필수 불일치가 아니라 감사 화면의 편의성과 복원 가능성을 높이는 선택 사항이다.

권장 수정:

- REQ-DB-03의 `appointment_changes`에 `old_queue_position`, `new_queue_position`을 포함하거나 별도 대기열 이력 테이블을 둔다.
- 순서 변경과 이력 생성을 같은 짧은 트랜잭션으로 처리한다.

#### REQ-DB-05. 일반 예약 요청의 멱등키 — 선택적 P2

챗봇 예약 확인 카드에는 `nonce`가 있지만 앱·직원 웹의 일반 예약 요청에는 같은 버튼이나 네트워크 재전송을 식별할 키가 없다.

현재 계획의 조건부 슬롯 UPDATE와 단일 트랜잭션이 모든 예약 경로에서 지켜지면 같은 슬롯의 예약은 하나만 성공한다. 따라서 별도 멱등키는 고객 요구 충족의 유일한 방법이 아니며, 네트워크 재시도 때 최초 성공 응답을 안전하게 재현하기 위한 추가 방어다.

권장 수정:

- 클라이언트 요청마다 `idempotency_key`를 발급하고 예약 테이블 또는 별도 요청 테이블에 UNIQUE로 저장한다.
- 같은 키의 재요청에는 새 예약을 만들지 않고 처음 생성된 예약을 반환한다.
- 슬롯 상태 변경과 예약 INSERT는 하나의 짧은 트랜잭션으로 처리한다.

#### REQ-DB-06. AI 답변 근거의 참조 무결성 — P2, ERD-04와 동일

`chat_messages.source_chunk_ids`는 UUID 배열이라 각 값이 실제 `kb_chunks.id`인지 PostgreSQL FK로 보장할 수 없다. 고객이 요구한 “답변에 사용한 병원 안내 확인”을 장기간 보장하려면 관계를 명확히 해야 한다.

이 항목은 새 발견이 아니라 `docs/supabase-planned-erd-2026-07-28.md`의 ERD-04와 동일하다. 승인 자료와 과거 조각을 삭제하지 않고 보존하면 현재 배열 구조도 단기적인 출처 확인에는 사용할 수 있다. 별도 연결 테이블은 장기간 감사 재현을 정책으로 확정할 때 필요하다.

권장 수정:

```text
chat_message_sources(
  message_id -> chat_messages.id,
  chunk_id -> kb_chunks.id,
  similarity,
  displayed_order,
  source_content_snapshot
)
```

지식자료와 검색 조각은 물리 삭제보다 `archived` 처리를 기본으로 하고, 과거 답변의 근거 스냅샷은 유지한다.

### 10.4 구현 착수 전 갱신할 판정 기준

- [ ] REQ-DB-01은 SDB-27 구현과 함께 처리하고, REQ-DB-02는 R5-09를 기준으로 처리
- [ ] 선택적 P2인 REQ-DB-03~06은 채택·보류·제외 중 하나로 결정하고 이유 기록
