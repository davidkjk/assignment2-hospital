# 병원 통합 서비스 문서 정합성 재검토 리포트 (3차)

검토 기준: `고객요구사항.txt`, 1~5단계 스펙·구현 계획.

범위: 1·2차 보고서에 수록한 이슈는 제외했다. 이번에는 기능이 “테이블/문구 선언”을 넘어 실제 화면·API·운영 동작으로 연결되는지를 다시 대조했다.

## 결론

이번 회차의 핵심은 **일정 규칙이 저장만 되고 예약 가능 여부에 강제되지 않는 점**, **예약 변경의 즉시 반영을 약속한 Realtime 구독에 DB publication 설정이 없는 점**, 그리고 **관리자의 직원 계정 관리 화면이 구현 계획에서 빠진 점**이다. 모두 개별 화면의 완성도 문제가 아니라, 고객이 관리한 규칙이나 변경이 실제 운영에 반영되지 않는 문제다.

## 신규 발견 사항

| 우선순위 | 이슈 | 근거 | 권고 |
|---|---|---|---|
| P1 | 의사 일정의 하루 최대 예약 수와 예약 마감 시간이 데이터 컬럼으로만 존재하고, 슬롯 조회·생성·예약 서비스에서 사용되지 않는다. | 규칙 테이블에는 `max_daily_appointments`, `booking_deadline`이 정의돼 있다(기반 계획 372~383). 그러나 전 계획에서 이 필드를 참조하는 곳은 마이그레이션/테스트 데이터뿐이며, 환자 예약 생성은 슬롯을 잡은 뒤 바로 예약을 INSERT한다(환자 앱 계획 1366~1395). | 고객 요구 3.7의 두 규칙이 실제 예약을 막도록 공통 `availability` 계약을 만든다. 슬롯 생성 시 최대 건수를 초과한 슬롯을 만들지 않고, 슬롯 조회·챗봇 시간 조회·앱/직원 예약 생성 모두에서 병원 시간대 기준 마감 시각을 재검증한다. 관리자가 값을 바꾼 뒤 이미 생성된 미래 슬롯을 어떻게 재계산할지도 정하고 경계값 테스트를 넣는다. |
| P1 | 점심시간·정규 진료시간·특정일 시간 변경도 현재는 스케줄 테이블에만 있고, 예약 슬롯을 만들거나 예약 직전에 막는 공통 구현 계약이 없다. | 정규/예외 스케줄 구조는 정의돼 있지만(기반 계획 372~393), 1단계 계획의 구현 태스크에는 슬롯 생성기가 없고, 예약 서비스는 선택한 슬롯의 상태만 확인한다(기반 계획 2236~2259). | 1·2차에서 지적된 “슬롯 생성 배치 추가”와 별도로, 생성기/재생성기의 입력·출력 계약을 명시한다. `정규시간 − 점심시간 − 휴진/예외`, 슬롯 단위, 최대 인원을 계산하고, 예약 시에도 슬롯이 해당 규칙에서 여전히 유효한지 재확인한다. 일정 변경 후에는 기존 예약 보존/영향목록 처리와 새 예약 차단이 같은 트랜잭션 규칙을 따라야 한다. |
| P1 | 앱·직원 웹은 예약 상태의 즉시 반영을 Supabase Realtime으로 설계했지만, `appointments`(및 필요한 상태이력) 테이블을 `supabase_realtime` publication에 추가하는 마이그레이션이 없다. | 앱 스펙은 본인 예약 상태 구독을 명시한다(환자 앱 스펙 21, 69). 웹도 `appointments`의 `postgres_changes` 구독을 구현한다(직원 웹 계획 3407~3424). 반면 publication 추가 SQL은 챗봇 테이블과 티켓에만 있다(챗봇 계획 191~193, 587); 예약 테이블 마이그레이션에는 없다(기반 계획 665~709). | 마이그레이션에 `appointments`를 publication에 추가하고, 필요한 경우 환자 화면의 대기 인원 계산에 쓰는 변경 대상도 함께 정한다. 환자 A의 예약 변경이 A에게만, 직원 화면 변경이 권한 범위 안에서만 도착하는지 실제 원격 Supabase 환경에서 검증하는 구독 테스트/스모크 테스트를 5단계에 추가한다. |
| P1 | 관리자용 직원·의사 계정 생성/사용 중지 기능은 백엔드 API만 있고, 직원 웹의 `/admin/staff` 화면·라우트·API 클라이언트 구현 태스크가 없다. | 스펙은 `/admin/staff`를 라우트로 정하고 그곳에서 의사 계정을 만든다고 한다(직원 웹 스펙 25, 81). 기반 계획은 초대·중지 서비스/API만 제공한다(기반 계획 1672~1683, 2722~2739). 직원 웹 계획의 태스크/커버리지에는 해당 화면이 배정되지 않았고, 문서 자체도 전체 라우트 조립을 후속 작업으로 남긴다(직원 웹 계획 4641~4658). | `/admin/staff`를 명시 Task로 승격한다: 직원 목록(활성/중지), 초대 폼(역할·의사 진료과 검증), 중지 확인 및 현재 로그인 관리자/최후 관리자 보호, 초대 실패·재초대 처리, 역할 기반 E2E 테스트를 포함한다. 초대 메일의 발송 성공과 DB 직원 행 생성이 엇갈릴 때의 보상 처리도 정한다. |

## 추가 검증 시나리오

- 한 의사의 `max_daily_appointments=3`일 때 네 번째 슬롯/예약이 앱·직원 웹·챗봇 어느 경로에서도 노출·생성되지 않는지
- 당일 `booking_deadline` 직전/직후, 점심시간, 특정일 단축 진료에서 시간 목록과 예약 확정이 모두 같은 결과를 내는지
- 직원이 도착 처리한 예약이 로그인한 환자 앱과 다른 직원의 캘린더에 Realtime으로 갱신되는지
- 관리자가 웹에서 의사를 초대하고 중지했을 때 메뉴 접근과 API/RLS 접근이 모두 즉시 막히는지
