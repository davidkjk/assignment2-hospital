# 병원 통합 서비스 문서 정합성 재검토 리포트 (5차)

검토 기준: `고객요구사항.txt`, 1~5단계 스펙·구현 계획.

범위: 기존 1~4차 보고서에 수록된 이슈는 제외했다. 이번 회차는 가족 연결 경계, 사전문진 변경 권한, 익명 상담, 환자 신원 연결, 개인정보 마스킹·열람기록, 실제 배포 경로를 추가로 대조했다.

## 결론

기존 보고서와 겹치지 않는 신규 이슈는 9건이다. 가장 위험한 문제는 환자가 Supabase를 직접 호출해 임의의 다른 환자를 자기 가족으로 연결할 수 있는 RLS 정책이다. 연결 해제 후에도 실제 조회 권한이 사라지지 않고, 사전문진도 도착·진료 완료 뒤에 직접 수정하거나 삭제할 수 있다. 기능 측면에서는 익명 웹 상담의 진료과·예약 가능 시간 조회가 환자 전용 서비스를 호출해 실패하고, 직원 웹의 구현 폴더와 배포·CI가 바라보는 폴더가 달라 실제 배포가 막힌다.

## 신규 발견 사항

| 우선순위 | 이슈 | 근거 | 영향과 권고 |
|---|---|---|---|
| P0 | 환자가 임의의 다른 환자 UUID를 자기 가족으로 연결해 개인정보 접근권한을 얻을 수 있다. 가족 링크 INSERT 정책은 `account_patient_id`가 본인인지만 검사하고 `family_patient_id`의 생성 주체·기존 소유관계를 검사하지 않는다. 링크가 생기면 `patient_owns()`가 그 환자를 곧바로 본인 가족으로 인정한다. | 가족 링크 RLS는 계정 쪽만 확인한다(환자 앱 계획 84~87). `patient_owns()`는 링크 존재만으로 가족 소유권을 인정한다(44~61). 이 함수는 환자정보, 예약, 문진 등 환자용 RLS의 공통 권한 기준이다(75~82, 293~325). | 다른 환자의 기본정보·예약·공개 안내를 읽거나 환자정보를 수정할 수 있는 개인정보 침해다. 클라이언트의 가족 링크 직접 INSERT를 막고, 서버가 같은 트랜잭션에서 새 가족 프로필을 생성한 뒤 그 새 ID에만 링크하도록 한다. 기존 환자 연결이 필요하다면 별도의 본인확인·동의 절차를 거친 보안 함수로 분리하고, 임의 UUID 연결 거부 RLS 테스트를 추가한다. |
| P1 | 가족을 “연결 해제”해도 데이터 접근권한이 유지된다. 서비스는 가족 환자의 `is_active=false`만 설정하고 링크 행을 그대로 남긴다. `patient_owns()`와 접근 가능 환자 목록은 링크 또는 가족의 활성 여부를 확인하지 않는다. | 고객은 가족정보 연결 해제를 요구한다(고객요구사항 245~249). 해제 구현은 가족 환자를 비활성화할 뿐 링크를 끊지 않는다(환자 앱 계획 1031~1041). 권한 함수와 접근목록은 남은 링크를 계속 인정한다(44~61, 704~709). | 가족 목록에서는 사라져도 예약·문진·방문 안내는 API나 Supabase 직접 조회로 계속 접근할 수 있다. `patient_family_links.is_active/unlinked_at`을 두어 링크 자체를 비활성화하고, `patient_owns()`·모든 가족 조회가 활성 링크만 인정하게 한다. 가족 환자 행은 과거 예약 보존을 위해 유지하되 연결 해제 즉시 권한이 사라지는 회귀 테스트를 추가한다. |
| P1 | 환자가 병원 도착 또는 진료 완료 뒤에도 사전문진을 Supabase에서 직접 수정·삭제할 수 있다. API 서비스는 상태를 검사하지만 RLS는 문진 응답에 `for all`을 허용하고 예약 상태 조건을 두지 않는다. | 스펙은 도착 이후 읽기 전용을 약속한다(환자 앱 스펙 62). 서비스는 `예약신청/예약확정`에서만 저장을 허용한다(환자 앱 계획 1868~1901). 그러나 RLS는 소유 예약이면 SELECT/INSERT/UPDATE/DELETE를 모두 허용한다(322~325). | 의사가 확인한 문진이나 진료 당시 근거가 사후에 바뀌거나 삭제될 수 있다. 환자 직접 테이블 쓰기를 막고 상태를 검사하는 RPC로 제출·수정을 원자화하거나, UPDATE/DELETE 정책에서 허용 예약 상태를 강제한다. `도착/진료대기/진료중/진료완료` 각각의 직접 UPDATE·DELETE 거부 테스트가 필요하다. |
| P1 | 익명 웹 상담에서 진료과 추천과 예약 가능 시간 조회가 실패한다. AI 스펙은 이 두 도구를 로그인 없이 사용할 수 있다고 정했지만, 구현은 `PatientContext`가 필수인 환자 앱 카탈로그 서비스에 `None`을 전달한다. | 웹 상담은 기본 익명이며(챗봇 스펙 22), 진료과·의사 및 예약 가능 시간 조회는 로그인 불필요 도구다(챗봇 스펙 207~212). 환자 카탈로그 서비스는 `patient.auth_user_id`를 사용한다(환자 앱 계획 1174~1213). 익명 상담 코드는 이 서비스에 `ctx.patient` 또는 `patient=None`을 넘긴다(챗봇 계획 1337~1339, 1518~1532). | 익명 사용자가 진료과 안내의 마지막 단계나 빈 시간 조회에 도달하면 예외가 발생해 일반 장애 안내로 떨어진다. 개인정보가 없는 공개 카탈로그용 읽기 서비스/엔드포인트를 별도로 만들고 활성 진료과·의사·유효 슬롯만 반환하게 한다. 익명 `patient=None`으로 진료과 추천과 시간 조회를 끝까지 수행하는 통합 테스트를 추가한다. |
| P1 | 전화예약 등으로 이미 등록된 환자가 앱에 가입하면 기존 환자 행에 계정을 연결하지 않고 새 환자 행을 만든다. 또한 프로필 전화번호는 OTP로 확인된 Auth 전화번호가 아니라 요청 본문 값을 그대로 저장한다. | 직원 등록은 인증계정 없는 `patients` 행을 만든다(기반 계획 1637~1654). 앱 가입은 동일인의 전화번호·생년월일을 조회하지 않고 `auth_user_id` 중복만 확인한 뒤 새 행을 INSERT한다(환자 앱 계획 824~837). 가입 API는 요청 본문의 `phone`을 그대로 전달한다(2391~2405). | 기존 예약·방문이력은 옛 환자 행에 남고 새 앱 계정에서는 보이지 않아 “웹·앱이 같은 환자정보를 사용”한다는 요구가 깨진다. 서버가 Supabase Auth의 검증된 전화번호를 읽고, 전화번호+생년월일 등으로 기존 후보를 안전하게 연결하되 동명이인·복수 후보는 직원 확인 절차로 보낸다. 요청 본문 전화번호 변조와 기존 환자 가입 시나리오를 테스트한다. |
| P1 | 직원 목록 화면에서 생년월일과 전화번호가 마스킹되지 않는다. 대기목록은 전체 생년월일을 그대로 렌더링하고, 일정변경 영향 환자 목록은 전체 전화번호를 표시한다. 취소요청 목록도 전체 생년월일을 표시한다. | 고객은 목록에서 전화번호와 생년월일 일부를 가리길 요구한다(고객요구사항 81). 직원 웹 스펙도 상세 화면에서만 전체 노출한다고 정한다(직원 웹 스펙 64). 그러나 대기 행은 전체 생년월일을 출력하고(직원 웹 계획 1920~1954), 영향 예약은 전체 전화번호를 표시하며(2889), 취소요청 표도 전체 생년월일을 출력한다(4611). | 옆자리·화면공유·캡처를 통한 불필요한 개인정보 노출이 생긴다. 서버 목록 DTO부터 `masked_birth_date`, `masked_phone`만 반환하고, 전체 값은 감사로그가 남는 환자 상세에서만 조회하게 한다. 대기·캘린더·영향목록·취소요청·통계 드릴다운을 한꺼번에 점검하는 마스킹 테스트가 필요하다. |
| P1 | 직원 웹 구현 폴더는 `frontend/`인데 배포 계획과 CI는 `web/`을 대상으로 한다. 오류 로그 화면도 존재하지 않을 `web/src`에 추가하도록 되어 있다. | 직원 웹 계획은 `frontend/package.json`, `frontend/src/...`를 생성한다(직원 웹 계획 720~742). 배포 계획은 직원 웹 디렉터리를 `web/`으로 고정하고(배포 계획 9, 14), 오류 화면·CI·Vercel도 모두 `web/`을 사용한다(956~958, 1573, 1619, 1803~1818). | CI가 직원 웹 테스트와 빌드를 실행하지 못하고 Vercel도 잘못된 루트에서 배포되어 고객의 인터넷 접속 가능한 직원 웹 납품이 막힌다. 표준 폴더를 `frontend/` 또는 `web/` 하나로 확정한 뒤 오류 화면 파일, CI working directory·캐시 경로, Vercel Root Directory, 문서를 전부 일괄 수정한다. |
| P2 | 진료기록 열람 감사로그를 실제로 남기는 조회 경로가 없다. 감사 서비스는 만들어져 있지만 의료기록 조회 API에 연결되지 않았고, 환자 상세 조회는 `patient_detail` 한 건만 기록한다. | 고객은 누가 환자정보와 진료기록을 열었는지 확인하길 원한다(고객요구사항 82). 기반 스펙은 진료기록 조회 시점 기록을 명시한다(기반 스펙 130~132). 구현 계획의 감사 함수는 독립 함수로만 존재하고(기반 계획 2607~2667), 의료기록 라우터는 저장·완료·수정만 제공한다(2683~2695). 환자 상세는 `patient_detail`만 기록한다(직원 웹 계획 3180~3196). | 관리자 화면에 `medical_record` 로그가 표시되더라도 실제 열람에서 생성되지 않아 감사 기능이 형식적으로만 존재한다. 진료기록 원문·과거기록·수정이력 조회 API마다 성공적인 열람과 같은 요청 안에서 `medical_record` 로그를 남기고, 의사 화면 및 환자 상세 탭에서 로그가 생성되는 통합 테스트를 추가한다. |
| P2 | 진료과별 사전문진 양식을 관리자가 설정할 API·화면이 없다. 테이블과 RLS만 있고 직원 웹 관리자 메뉴에는 양식 관리 작업이 배정되지 않았다. | 고객은 진료과에 따라 질문을 다르게 설정할 수 있길 원한다(고객요구사항 282). 기반 계획은 `questionnaire_templates` 테이블과 관리자 RLS만 만든다(기반 계획 976~1020). 환자 앱은 해당 테이블에서 임의의 첫 행을 `limit 1`로 읽는다(환자 앱 계획 1871~1878). 직원 웹 스펙·계획의 관리자 화면에는 문진 양식 관리가 없다. | 운영자가 질문을 만들거나 바꿀 정상 경로가 없고, 같은 진료과에 여러 행이 생기면 어떤 양식이 선택될지도 결정적이지 않다. 관리자용 양식 편집 화면/API, 진료과당 활성 버전 1개 제약, 버전·사용중지 정책을 추가하고 과거 답변은 제출 당시 질문 스냅샷을 유지하게 한다. |

## 추가 검증 시나리오

- 환자 A가 환자 B의 UUID로 가족 링크를 직접 INSERT하려 하면 DB 수준에서 거부되는지
- 가족 연결 해제 직후 가족의 예약·문진·방문 안내가 앱 API와 Supabase 직접 조회 모두에서 차단되는지
- 환자가 도착·진료완료 뒤 문진 응답을 직접 UPDATE 또는 DELETE하려 하면 거부되는지
- 로그인하지 않은 웹 상담 사용자가 진료과 추천과 빈 시간 조회를 끝까지 정상 이용할 수 있는지
- 전화예약 이력이 있는 환자가 같은 검증 전화번호로 앱 가입했을 때 기존 환자 행과 안전하게 연결되는지
- 대기·일정영향·취소요청 목록 응답과 화면에 전체 전화번호·생년월일이 포함되지 않는지
- 진료기록과 수정이력을 열 때마다 관리자 감사 화면에 직원·환자·자료종류·시각이 남는지
- 실제 직원 웹 폴더 하나를 기준으로 CI 빌드가 통과하고 같은 산출물이 Vercel에 배포되는지
- 관리자가 진료과별 활성 문진 양식을 바꾸면 새 예약에만 새 양식이 적용되고 과거 답변 의미는 유지되는지
