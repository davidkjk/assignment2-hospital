# 병원 통합 서비스 문서 정합성 재검토 리포트 (4차)

검토 기준: `고객요구사항.txt`, 1~5단계 스펙·구현 계획.

범위: 1·2·3차 보고서에 수록한 이슈는 제외했다. 이번 회차는 승인 후 공개 규칙, 진료 완료의 상태 연결, 환자 대기 표시, QR/예약번호 접수 흐름을 대조했다.

## 결론

가장 중요한 신규 불일치는 **관리자가 수정한 승인 지식자료가 재승인 없이 즉시 챗봇에 반영되는 문제**다. 이는 “수정 후 관리자 확인 뒤 적용” 요구를 직접 위반한다. 또한 의사가 진료기록만 완료하면 예약 상태가 완료로 바뀌지 않아 환자 앱에 진료 완료가 전달되지 않으며, 앱이 약속한 ‘내 앞 대기 인원’과 QR/예약번호 기반 접수도 현재 API·화면 계약에 없다.

## 신규 발견 사항

| 우선순위 | 이슈 | 근거 | 권고 |
|---|---|---|---|
| P0 | 승인된 지식자료를 수정하면 상태를 `draft`로 되돌리거나 재승인을 요구하지 않고 즉시 재청킹·재임베딩한다. 즉 수정 내용이 곧바로 RAG 검색 대상이 된다. | 스펙은 `approved`만 검색 대상이며(챗봇 스펙 90), 요구사항은 수정 내용을 관리자가 확인한 뒤 적용하길 원한다. 그러나 `update_document`는 기존 상태를 유지한 채 내용을 갱신하고, 기존 상태가 `approved`면 즉시 `_rebuild_chunks`를 실행한다(챗봇 계획 925~952). | 수정 시 기존 공개본은 유지하고 수정본을 `draft` 버전으로 분리하거나, 단일 문서 방식이면 수정 즉시 `draft`로 전환해 검색 조각을 제거한다. 승인 작업이 새 조각을 원자적으로 교체하도록 하고, “수정→미승인 상태에서는 이전 안내가 계속 답변됨 / 승인 후 새 안내로 교체됨” 테스트를 추가한다. |
| P1 | 의사 화면의 ‘완료’는 `medical_records.is_completed`만 바꾸며 예약 상태 `진료완료` 전이와 연결되지 않는다. | 진료기록 완료 서비스는 기록 행만 UPDATE한다(기반 계획 2533~2541). 의사 화면도 `completeRecord(recordId)`만 호출한다(직원 웹 계획 2711~2741). 반면 고객 시나리오 4는 기록 완료 후 환자 앱 상태가 완료로 바뀌어야 한다. | `완료 진료`를 하나의 도메인 작업으로 만든다. 같은 트랜잭션에서 기록 완료, 예약 `진료중→진료완료` 전이, 상태이력, 환자 공개 안내/알림 이벤트를 처리한다. 이미 완료된 예약·기록의 재시도는 멱등으로 처리하고, 앱 상태 갱신까지 통합 테스트한다. |
| P1 | 환자 앱은 ‘내 앞 대기 인원’을 보여주겠다고 설계했지만, 예약 조회 API는 본인의 `queue_position`만 반환하고 앞선 유효 대기 인원 산식·필드를 제공하지 않는다. 홈/목록 모델과 화면도 이를 표시하지 않는다. | 환자 앱 스펙은 도착 뒤 `내 앞 대기 인원`의 Realtime 갱신을 명시한다(환자 앱 스펙 69). 상세 조회는 `queue_position`만 선택한다(환자 앱 계획 1729~1745), 홈 모델/화면은 상태·예약정보·문진 여부만 다룬다(4724~4751, 4817~4834). | 서버가 같은 의사·당일·대기 대상 상태를 기준으로 `patients_ahead`를 계산해 반환한다. 대기 순서 변경, 진료 시작, 취소·부도 때 재계산되도록 하고, 환자에게는 “예상 대기시간은 변동 가능” 문구와 함께 이 수치만 표시한다. 다른 환자 개인정보는 절대 반환하지 않는다. |
| P2 | QR/예약번호는 환자 앱에서 UUID로 표시하지만, 직원 웹에는 그 번호로 예약을 찾거나 접수 처리할 API·화면이 없다. | 환자 앱 스펙은 직원 웹이 이 예약번호로 검색해 접수한다고 명시한다(환자 앱 스펙 67~69). 실제 홈은 UUID QR과 텍스트만 생성한다(환자 앱 계획 4825~4829). 직원 웹의 환자 검색 계약은 전화번호+생년월일뿐이다(직원 웹 계획 1285~1291, 1378~1458). | 직원 웹에 `GET /appointments/lookup?reservation_number=` 또는 인증된 QR 스캔/입력 흐름을 추가한다. UUID를 그대로 예약번호로 쓸지, 사람이 읽기 쉬운 별도 번호를 발급할지도 결정하고, 번호 오입력·취소/과거 예약·동명이인 경우의 안전한 확인 화면을 테스트한다. |

## 추가 검증 시나리오

- 승인된 ‘주차 안내’를 수정한 뒤 재승인 전에는 챗봇이 이전 승인 문구만 답하고, 재승인 뒤에만 새 문구가 답변되는지
- 의사가 화면에서 진료기록 완료를 누르면 예약 상태이력에 `진료중→진료완료`이 한 번 남고, 환자 앱 조회에도 완료가 보이는지
- 대기 중인 앞 환자가 취소·진료 시작·순서 변경될 때 해당 환자의 `patients_ahead`가 즉시 바뀌되 다른 환자 식별정보는 노출되지 않는지
- 앱 QR/예약번호로 직원이 예약을 열어 도착 처리할 수 있고, 취소·부도 번호는 안전하게 안내되는지
