# 병원 통합 서비스 문서 정합성 재검토 리포트 (2차)

검토 기준: `고객요구사항.txt`, 1~5단계 스펙·구현 계획.

범위: 기존 `docs/consistency-review-2026-07-28.md`에 이미 적힌 이슈(예약 상태전이/RLS 우회 일반론, 슬롯-의사-진료과 정합성, 직원 웹 일정·캘린더 구현 공백, 앱 식별자·예약 플로우, 챗봇 확인카드·문진 상태, 웹 상담 배포 계약 등)는 **의도적으로 제외**했다. 아래는 그 외에 새로 확인된 항목만 정리한다.

## 결론

새로 확인된 가장 큰 위험은 환자 계정이 Supabase를 직접 호출했을 때 **다른 환자의 예약 슬롯을 다시 빈 슬롯으로 바꿀 수 있는 RLS 정책**이다. 이 문제는 API가 정상이어도 클라이언트가 DB API를 직접 호출하면 발생하므로 배포 전 수정이 필요하다. 그 밖에 의사별 열람 범위, 운영통계의 날짜 기준, 대기시간 산식, 상태 변경 알림의 책임 위치, 의료판단 티켓의 담당자 권한이 문서 사이에서 완결되지 않았다.

## 즉시 수정 필요

| 우선순위 | 이슈 | 근거 | 영향과 권고 |
|---|---|---|---|
| P0 | 로그인 환자가 타인의 `예약됨` 슬롯을 `빈시간`으로 되돌릴 수 있다. | 환자 RLS는 모든 로그인 환자에게 슬롯 `빈시간`/`예약됨` 상태의 UPDATE를 허용할 뿐, 그 슬롯의 예약 소유 여부를 확인하지 않는다(환자 앱 계획 101~104). | 악의적 또는 오류 난 앱이 다른 환자의 시간을 풀어 이중예약·예약유실을 만들 수 있다. 환자에게 `appointment_slots` UPDATE를 직접 허용하지 말고, 보안 정의 RPC/서버 트랜잭션에서 **해당 예약의 계정 소유자·예약 상태·슬롯 상태**를 한 번에 검증한 뒤에만 잡기/반납을 수행한다. 최소한 반납은 `appointments.account_patient_id = auth.uid()` 관계를 확인하는 별도 함수로 제한한다. |
| P0 | 의사가 본인 담당이 아닌 환자의 예약·진료기록·수정이력을 읽을 수 있다. | 직원이면 모든 예약을 SELECT할 수 있고(기반 계획 678~680), 모든 진료기록과 수정이력을 SELECT할 수 있다(851~853, 864~866). 대기목록 API도 의사 필터 없이 전체 `도착/대기/진료중`을 반환한다(직원 웹 계획 3163~3175). | 요구사항의 “의사는 본인의 오늘 환자” 및 역할별 개인정보 접근 원칙과 어긋난다. RLS와 API를 함께 제한해 의사는 `appointments.doctor_id = 자기 staff.id`인 예약 및 그에 연결된 문진·기록·수정이력만 조회하게 한다. 접수직원/관리자의 넓은 조회 권한은 별도로 명시한다. |

## 높은 우선순위 보완

| 영역 | 이슈 | 근거 | 권고 |
|---|---|---|---|
| 오늘 현황·대기 | 대기시간과 장기대기 판정이 `updated_at` 기준이라, 대기 순서 변경·주의 표시·다른 수정만 해도 대기시간이 0부터 다시 계산된다. | `updated_at`은 예약 행의 공통 수정시각(기반 계획 651)이고, 대기열·장기대기·대기분 계산이 모두 이를 사용한다(직원 웹 계획 3129~3137, 3163~3175). 대기순서/주의표시는 예약을 갱신하는 서비스다(기반 계획 2006~2008, 2169~2197). | `진료대기`로 전환된 시각을 상태이력에서 구하거나 `waiting_started_at`을 상태전이 때만 기록한다. 장기대기·현재 대기시간·평균대기시간에 동일한 기준을 쓰고, 순서변경 후에도 값이 유지되는 회귀 테스트를 추가한다. |
| 운영 통계 | 선택 기간의 예약·취소·부도·방문·채널 비율을 모두 `created_at`으로 집계한다. 예약을 잡은 날과 실제 방문/취소/부도 발생일이 다르면 하루 운영 보고가 왜곡된다. | 통계 쿼리의 상태별 건수와 앱 예약 비율이 `appointments.created_at::date`만 필터링한다(직원 웹 계획 3207~3239). | 지표마다 사건 기준일을 확정한다. 예: 예약 건수는 슬롯일 또는 생성일을 화면에 명시, 방문은 `진료완료` 전이시각, 취소·부도는 해당 상태 전이시각, 평균 대기는 대기 시작일을 쓴다. 상태이력에 같은 예약이 여러 번 있을 수 있으므로 각 최종/대상 전이를 정확히 선택하는 테스트가 필요하다. |
| 오늘 현황 | 오늘 요약이 예약 슬롯 날짜가 아니라 `updated_at` 또는 `created_at`이 오늘인 행을 센다. 며칠 뒤 예약을 오늘 생성해도 오늘 환자로 보이고, 과거 예약을 오늘 수정해도 오늘 현황에 들어간다. | 오늘 요약 필터가 `updated_at::date = current_date or created_at::date = current_date`다(직원 웹 계획 3115~3126). | 슬롯이 있는 예약은 `appointment_slots.slot_date = 병원 기준 오늘`으로 집계한다. 워크인은 별도 `visit_date`/접수 시각을 둔다. 시간대 기준은 배포 문서의 `Asia/Seoul` 원칙과 단일화한다. |
| 알림 | 알림 문구는 정의했지만, 병원 취소·진료 완료·마감 후 취소요청 승인에 실제로 알림을 호출할 책임 단계가 없다. 환자 앱 계획도 이를 “다른 단계에서 호출”한다고 남긴다. | 알림 종류에는 `hospital_cancelled`, `visit_completed`가 있다(환자 앱 계획 2265~2275). 그러나 연결 코드는 앱 예약 생성/변경만 다루고(2308~2340), 커버리지 표는 병원취소 등의 호출을 5단계 또는 2단계에 미배정 상태로 남긴다(5554~5556). 직원 웹에서 명시된 호출은 취소요청 **반려**뿐이다(직원 웹 스펙 102~104). | 상태전이 서비스에 도메인 이벤트를 발행하고, 커밋 후 알림 작업이 `병원취소`, `진료완료`, 취소요청 승인/반려, 일정변경 재예약을 각각 처리하게 배정한다. 각 이벤트는 수신 대상(가족 예약 시 계정 주인과 진료 대상 중 누구인지)과 중복 발송 방지 키를 함께 정의한다. |
| 상담 티켓 | 티켓이 특정 직원/의사에게 재배정되어도, 답변 서비스는 배정된 담당자인지 또는 의료판단 티켓에 적합한 역할인지 확인하지 않는다. | 재배정은 `assigned_staff_id`만 바꾼다(챗봇 계획 2675~2684). 답변은 `pending`/`in_progress`면 어떤 `staff`라도 완료·답변자로 바꿀 수 있다(2687~2707). 라우터도 접수직원·의사·관리자 모두 답변 가능하다(3347~3361). | `answer_ticket`에서 `assigned_staff_id == staff.id`를 원자적으로 검사하고, `medical_judgment`는 의사/관리자에게만 배정·답변 가능하게 강제한다. 재배정 대상이 활성 상태이며 허용 역할인지도 서버에서 검증한다. |

## 함께 결정할 항목

1. **통계의 “기간” 의미**: 예약을 만든 기간인지, 실제 방문 예정일/운영 발생일인지 지표별로 확정해야 한다. 추천은 운영 보고에는 실제 발생일을 기본으로 하고, 신규 예약 유입은 별도 지표로 분리하는 방식이다.
2. **가족 예약 알림 수신자**: 현재 `for_patient_id`에만 알림을 보내는 설계다. 가족 환자는 보통 로그인·기기 토큰이 없으므로, 예약을 관리한 계정 주인(`account_patient_id`)에게도 보내야 하는지 정책을 정해야 한다.

## 추가 테스트 권고

- 환자 A가 환자 B의 `예약됨` 슬롯을 빈 슬롯으로 UPDATE하려 하면 DB 수준에서 거부되는지
- 의사 A가 의사 B의 예약, 문진, 진료기록, 수정이력을 직접 조회·API 조회 모두에서 받지 못하는지
- 대기순서 조정·주의 표시 후에도 장기대기 판정과 대기시간이 변하지 않는지
- 오늘 생성한 다음 주 예약과 오늘 수정한 과거 예약이 오늘 현황에 포함되지 않는지
- 병원취소·진료완료·취소요청 승인/반려·일정변경 재예약 때 각각 한 번만 알림이 기록·발송되는지
- 의료판단 티켓을 접수직원이 재배정 뒤 직접 답변하거나, 비배정 직원이 답변하려 할 때 403/409으로 막히는지
