# 병원 통합 서비스 문서 정합성 검토 리포트

검토 기준: `고객요구사항.txt`, 단계별 설계 스펙 및 구현 계획(1~5단계).

판정 기준: 모든 고객 요구 기능은 구현 대상으로 본다. 과설계는 요구 충족에 필요하지 않은 복잡도만 지적하며, 보안·권한·감사·백업과 AI 단계의 LangChain/명시적 분기 구조는 과설계로 보지 않았다.

## 결론

문서는 기능 범위가 넓게 반영되어 있고 AI의 LangChain 3갈래 구조도 요구와 일관된다. 그러나 구현 전에 해결해야 할 **치명적 계약 공백**이 있다. 가장 큰 위험은 (1) DB/RLS를 우회하는 예약·진료기록 변경, (2) 직원 웹의 일정·캘린더·진료 핵심 기능이 실제 계획에서 빠진 점, (3) 환자 앱의 본인 식별자와 예약 플로우 불완전, (4) 챗봇 예약/문진 상태 계약, (5) 웹 상담 배포 산출물의 불일치다.

## 높은 우선순위 보완

- 1단계: 슬롯 생성 배치가 설계에만 있고 구현 단계가 없다(기반 스펙 81~86). 일정 설정 뒤 예약 가능 시간이 생기도록 idempotent 생성·휴진 반영·테스트를 배정한다.
- 1단계: 직원 30분 무활동 로그아웃은 JWT 30분 만료와 다르며, 직원 비활성화도 Auth 세션을 무효화하지 않는다(기반 스펙 28, 계획 53~57, 1801~1810).
- 1단계: 예약 생성 시 초기 상태를 요청값 그대로 받지 말고 예약 채널별 허용 상태를 서버에서 고정한다(기반 계획 2225~2257).
- 2단계: 의사 화면에는 대기목록·사전문진·과거기록·수정이력 UI가, 환자 상세에는 예약/방문이력·문진·과거기록·가족관계가 빠져 있다(직원 웹 스펙 59, 67; 계획 2576, 2718, 3179).
- 2단계: 운영통계의 과/의사별·시간대·장기대기·드릴다운·CSV와 전화 신규환자 등록, 오늘 현황 타일의 목록 이동을 추가한다(고객요구사항 194; 직원 웹 계획 1796, 2972, 3207, 3557).
- 2→3단계: 취소요청 대기열은 3단계 마이그레이션과 알림 서비스에 의존한다. 2단계 완료 조건에서 분리하거나 공통 기반으로 승격한다.
- 3단계: 예약 API에서 요청한 진료과/의사/슬롯 관계를 검증하고, 문진 템플릿이 예약 진료과와 맞는지 서버에서 검증한다(환자 앱 계획 1347~1451, 1861~1901).
- 3단계: 홈 예약 카드의 병원 위치와 변경/취소 재확인 UX를 보완하고, Task 27이 BusyButton/OfflineBanner를 되돌리지 않게 한다.
- 4단계: 업무시간 외 예상 답변 시점을 실제 응답에 반영하고, 익명 인계 연락처 경합과 의료 판단 티켓 재배정 권한을 서버에서 처리한다.
- 5단계: KST 08:00 크론과 UTC `date.today()`의 날짜 경계 오류를 `Asia/Seoul` 기준으로 고친다(배포 계획 782~804, 1879).
- 5단계: `ALLOWED_ORIGINS` 기반 CORS 및 preflight 스모크 테스트를 추가한다. 현재 Vercel 웹/상담창 → Railway 호출 계약이 없다.
- 5단계: CI와 배포 게이트에 확정된 웹 상담 앱을 포함하고, Claude/OpenAI/FCM 장애·티켓 fallback·익명 rate limit을 배포 검증한다.

## 교차 단계 결정이 필요한 항목 → 확정된 결정 (2026-07-28 사용자 확정)

1. **마감 후 환자 취소**: ✅ **별도 취소요청 큐 유지.** 고객요구사항의 “상담으로 연결”은 상담봇이 아니라 **직원 상담**을 뜻하는 것으로 확정. 취소요청 큐(직원이 목록을 보고 처리)가 곧 그 구현이므로 2·3단계 현행 설계가 맞다. 문서 변경 불필요.
2. **상담봇 웹 제공 방식**: ✅ **독립 `webchat` 웹앱 + iframe 위젯 래퍼.** 상담창 본체는 AI 계획대로 독립 웹앱으로 만들고, 배포 단계에서 얇은 `widget.js` 로더가 iframe으로 webchat을 띄운다(상용 상담위젯 표준 방식). AI 계획 Task 18에 로더 산출물 추가, 배포 계획의 위젯 계약을 이 구조로 갱신 필요.
3. **예약 원자성의 책임 위치**: ✅ **치명적 규칙만 DB, 안내는 서버.** 슬롯 중복 방지·담당의-슬롯 일치·상태전이·완료기록 수정사유는 DB(RPC/트리거/제약)가 최종 심판이 되어 우회 불가로 강제하고, 입력 검증·한글 오류 안내는 서버 코드가 담당한다. 위 “즉시 수정 필요”의 1단계 항목들을 이 원칙으로 반영한다.
4. **iOS 납품 범위**: ✅ **Apple 개발자 계정 등록 후 서명된 IPA 산출.** 요구사항 “심사 제출 가능한 빌드”를 문자 그대로 충족한다. 배포 스펙·계획에 계정 등록, 서명, Release Archive/IPA 산출·검증 절차 추가 필요(실제 심사 제출은 여전히 범위 밖).

## 과설계 판정

다음은 과설계로 판단하지 않았다.

- Supabase RLS, 감사 로그, 수정 이력, 낙관적 잠금, 백업·복구 검증
- React/Flutter 및 캘린더·Realtime 기반의 업무 화면
- LangChain LCEL/RunnableBranch/AgentExecutor를 활용한 응급 검사 → 인계 감시 → RAG·문진·행동의 명시적 분기
- 오답 피드백, 예시은행, 미해결 질문 묶음(운영 개선 요구와 직접 연결)

과설계 후보는 하나다. AI의 약 300개 지식문서 시드와 별도 Vercel 위젯 데모는 운영 납품물과 중복될 수 있다. 전자는 **비운영 RAG 평가 데이터**로 격리하고, 후자는 웹 상담 제공 방식을 확정한 뒤 독립 `webchat`과 통합하거나 삽입형 데모의 필요성을 명시하면 된다.
