# 2단계: 직원용 웹(React) 구현 플랜 — **재작성본**

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. 각 태스크는 TDD(실패 테스트 → 구현 → 통과)로 진행한다.
>
> ⚠️ **이 파일은 `plans/2026-07-27-staff-web.md`(9,659줄)를 대체한다.** 옛 파일은 삭제하지 않고 **재작성의 입력**으로 남긴다(태스크 구조·`R*` 정합성 표시의 원본). 충돌하면 **이 파일이 정본**이다.

**Goal:** 직원(접수직원·의사·관리자)이 쓰는 React 웹 앱을 **활성 route 18개** 범위로 구현하고, 그에 필요한 백엔드(서비스·라우터·마이그레이션)를 1단계 FastAPI 위에 추가한다. **화면 규칙 1,173개를 태스크의 실패 테스트 문장으로 옮기는 것**이 이 재작성의 목적이다.

**Architecture:** 백엔드는 1단계의 `acquire_as`/`require_role`/`AppError` 패턴을 그대로 재사용해 서비스·라우터를 추가한다. 프론트엔드는 Vite+React+TypeScript SPA로, Supabase Auth로 로그인하고 역할에 따라 라우팅을 분기하며, React Query로 REST를 호출하고 여러 직원이 동시에 보는 화면은 Supabase Realtime을 구독한다. **모든 화면은 Task 0이 만든 시각 토큰만 소비한다.**

**Tech Stack:** React, TypeScript, Vite, React Router, TanStack React Query, `@supabase/supabase-js`, FullCalendar(`@fullcalendar/react`), `@dnd-kit/core`, Vitest + Testing Library + MSW.

**Spec:** `docs/superpowers/specs/2026-07-27-staff-web-design.md`(③에서 재작성) · 공용 데이터 모델은 `specs/2026-07-27-foundation-auth-data-model-design.md` 섹션 4.

**규칙·결정 원본:**
- 화면 규칙 = `docs/design/screen-behaviors.md` **1~2535줄**(직원 웹 영역, 규칙 1,173개)

### 유지되는 제약

- **[정합성 검토 P1/P2 추적]** `docs/supabase-postgres-review-2026-07-28.md`의 SDB-07~16, SDB-24~34는 해당 기능을 실제로 만들 때 함께 반영한다(2026-07-28 결정). 옛 플랜의 `R*` 표시(R2-02~07·R3-01~04·R4-04·R5-01·02·05·06·08·09)는 **해당 태스크에 그대로 옮긴다.**
- 백엔드 신규 코드는 1단계의 `backend/app/db/pool.py`(`acquire_as`), `core/security.py`(`StaffContext`, `require_role`), `core/errors.py`(`AppError`)를 **재사용한다 — 새로 만들지 않는다.**
- 프론트엔드는 `frontend/`, 백엔드는 `backend/`.
- 모든 API 오류 메시지는 한글로 노출한다.
- 여러 직원이 동시에 보는 화면(`/today`·`/calendar`·`/queue`)은 Supabase Realtime으로 동기화한다.
- 동명이인 재확인 팝업은 **접수직원의 환자 선택·예약 확정 시점에만** 적용하고 의사 화면에는 적용하지 않는다.
- 대기 순서 변경은 드래그앤드롭이며, 드롭 시 사유 입력 모달이 뜨고 취소하면 원래 위치로 되돌아간다.
- ⛔ **`supabase db reset` 금지** — 로컬 DB는 다른 세션과 공용이다. 새 마이그레이션은 **`supabase migration up`**으로만 적용한다.

### 신설 제약 (규칙에서 올라온 것)

- **토큰 밖의 색·글자 크기를 화면 코드에 쓰지 않는다.** 색은 `var(--color-*)`, 크기는 `var(--fs-*)`만. 위반은 `npm run lint:tokens`가 CI에서 막는다(Task 0).
- **새 색 토큰을 만들지 않는다**(`AD-070`). 필요해 보이면 기존 토큰의 오용이거나 결정이 필요한 사안이다.
- ⭐ **`DISP-COLOR-01` 색만으로 상태를 구분하지 않는다 — 항상 텍스트를 병기한다.** 모든 화면 태스크의 상태 표시 테스트에 이 검사가 들어간다.
- ⭐ **못 누르는 버튼을 그리지 않는다.** 권한이 없으면 **회색 비활성이 아니라 아예 그리지 않는다**(`SHELL-NAV-03`·`SHELL-ACT-03`·`CAL-COLOR-05`·`SEND-DOOR-07`이 모두 같은 태도).
- ⭐ **막다른 길을 만들지 않는다.** 막을 때는 해결 경로를 같은 자리에 준다(`CAL-COLOR-07`·`PICK-ALL-04`).
- **역할 노출 정본은 `SHELL-NAV-01·02·03`**(`AD-069` + `MR2-07` 4그룹 최종). 사이드바 = 진료 화면(의사 단독) + 업무/기록/설정/상담봇 4그룹. 접수직원은 업무 8개만, 의사는 2개만.
- **마스킹은 전역 규칙**(`MASK-*`) — 목록 화면 전부에 적용하고, **번호를 펼치면 열람 기록이 남는다**(`MASK-VIEW-02`).

 *  글자는 읽혀야 하므로 대비는 별도로 지킨다. */
function contrast(hex1, hex2) {
  const lum = (hex) => {
    const c = [1, 3, 5].map((i) => parseInt(hex.slice(i, i + 2), 16) / 255);
    const [r, g, b] = c.map((v) => (v <= 0.03928 ? v / 12.92 : ((v + 0.055) / 1.055) ** 2.4));
    return 0.2126 * r + 0.7152 * g + 0.0722 * b;
  };
  const [a, b] = [lum(hex1), lum(hex2)].sort((x, y) => y - x);
  return (a + 0.05) / (b + 0.05);
}

/** 색상환 각도(0~360). 「두 색이 비슷한가」를 눈이 아니라 값으로 판정하려고 쓴다. */
function hue(hex) {
  const [r, g, b] = [1, 3, 5].map((i) => parseInt(hex.slice(i, i + 2), 16));
  const max = Math.max(r, g, b), min = Math.min(r, g, b);
  if (max === min) return 0;
  const d = max - min;
  const h = max === r ? ((g - b) / d) % 6 : max === g ? (b - r) / d + 2 : (r - g) / d + 4;
  return (h * 60 + 360) % 360;
}
