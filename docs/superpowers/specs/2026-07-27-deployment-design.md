# 5단계: 통합 테스트 & 배포 — 설계 스펙

> 근거 문서: `고객요구사항.txt` 6장(공통 규칙), 8장(완료 시나리오), 10장(납품 결과)
> 전체 5단계 중 **5단계**(마지막)의 설계입니다.
>
> 1. 기반: 인증/권한 + 데이터 모델 (스펙·계획 완료)
> 2. 직원용 웹 (React) (스펙·계획 완료)
> 3. 환자 모바일 앱 (Flutter) (스펙·계획 완료)
> 4. AI 상담봇 (스펙 완료)
> 5. **통합 테스트 & 배포 (이 문서)**
>
> 전제: 이 단계의 실제 실행은 1~4단계 구현 완료 후다.

## 범위와 핵심 결정

| 결정 항목 | 확정 내용 |

## 배포 아키텍처

```
[직원 브라우저] → Vercel ─┬─ 직원용 웹 (React)
                          ├─ 상담봇 webchat 앱 (Vite, `webchat/`)
                          └─ 위젯 데모 페이지 (로더 widget.js가 webchat을 iframe으로 로드)
[환자 안드로이드폰] → .apk 직접 설치 (Flutter)
        ↓
   Railway ─┬─ FastAPI 백엔드
            ├─ cron ① 매일 08:00 KST: 리마인더 알림 발송
            └─ cron ② 매일 03:00 KST: pg_dump 백업
        ↓
   Supabase(원격) ─ PostgreSQL(RLS) · Auth · Realtime · Storage(백업 버킷)
   외부: Claude API · OpenAI 임베딩 · FCM · Twilio
```

- ⚠️ **인바운드 경로 1개(Twilio)**: 위 외부 서비스는 전부 **나가는** 방향인데, **Twilio만 들어오는 방향이 있다** — 문자 도달 결과를 알려주는 상태 되알림이다. 공개 엔드포인트 + 서명 검증이 필요하다(→ 「만드는 것들」 7번, 갭 #122).
- **CI/CD**: GitHub push → GitHub Actions 테스트 통과 시에만 Railway/Vercel 자동 배포.
- **비밀키(요구사항 6.5)**: 저장소에는 `.env.example`(키 이름 목록)만. 실제 값은 각 플랫폼 환경변수에만 저장.
- **상담봇 웹 위젯 (확정 계약)**: 4단계 산출물은 독립 `webchat/` Vite 웹앱 + 그것을 iframe으로 띄우는 얇은 로더(`webchat/dist/widget.js`, 전역 `HospitalChatWidget.init({ webchatUrl })` — 우하단 플로팅 버튼, 클릭 시 iframe). webchat 앱 자체를 Vercel 별도 프로젝트로 배포하고, 별도 병원 홈페이지가 없으므로 Vercel에 간단한 데모 페이지를 만들어 로더를 탑재. 백엔드 CORS 허용 오리진에 webchat 배포 주소를 포함해야 한다.
- **검수 접속 방법**: 웹·상담봇(webchat 앱·위젯 데모)은 URL, 안드로이드는 .apk 설치, iOS는 실기기(아이폰) 설치 확인 + 시뮬레이터 실행법(README).

## 만드는 것들

### 1. 시나리오 API 통합 테스트 (자동)

요구사항 8장의 10개 시나리오 중 서버 검증 가능한 것을 API 호출 시퀀스로 재연.

- 자동화: 시나리오 1(앱 예약), 3(전화 예약·당일 접수), 4(도착→진료 완료), 5(기록 수정), 6(일정 변경), 8(중복 방지), 9(권한), 10 일부(운영 통계 API `GET /stats` 수치 검증 — 화면 없이 API 레벨로 확인 가능)
- 수동 전용: 시나리오 2·7(상담봇 대화), 10 일부(통계 화면 렌더링·CSV 다운로드 버튼 동작), 푸시알림 실제 수신
- 로컬 DB에서 개발·실행. 배포 후 같은 테스트를 클라우드 환경 대상으로 재실행(스모크 테스트).

### 2. 수동 검수 체크리스트

10개 시나리오 전체를 "누가 / 어떤 화면에서 / 뭘 누르고 / 뭐가 보여야 통과" 단계별 표로 작성 (`docs/manual/scenario-checklist.md`). 최종 검수의 대본이자 납품물.

### 3. 데모 데이터 시드 스크립트

- 계정: 관리자 1, 접수직원 2, 의사 3(진료과별), 환자 5(가족 등록 포함 1명)
- 기준: 진료과 3~4개, 의사별 주간 일정, 상담봇 지식 문서 15개 내외
- 과거 3주치 예약·진료기록(통계·방문이력·캘린더 채움) + 오늘~다음 주 예약(시연용)
- 명령 한 번으로 초기화+재생성. 실제 환자정보 사용 금지(요구사항 6.5).

### 4. Railway cron 2종

- **알림 크론**(매일 08:00 KST): FastAPI 리마인더 발송 API 호출 — 전날·당일 예약 알림, 사전문진 미작성 알림. 실행 결과 로그 기록.
- **백업 크론**(매일 03:00 KST): `pg_dump` → `backup-YYYY-MM-DD.sql.gz`로 Supabase Storage 비공개 버킷 업로드, 14일 초과분 자동 삭제. 복구 절차 문서화 + **복구 리허설 1회 실제 수행**(복원 가능성 검증이 핵심).

### 5. 관리자용 오류 로그 화면

직원용 웹 관리자 메뉴에 "시스템 오류" 페이지: 발생 시각·기능·메시지 최신순 표 + 날짜 필터. 조회 전용. 기존 `system_error_log` RLS(관리자 read) 재사용. — 1단계가 "관리자 화면에서 조회 가능"을 전제했으나 화면이 어느 단계에도 배정되지 않았던 공백을 여기서 메움.

### 6. 앱 릴리즈 빌드

- 안드로이드: 서명 키 생성 → 서명된 .aab(제출용) + .apk(직접 설치용)
- iOS: 번들 ID·아이콘·스플래시·버전·권한 설명문 완비 → Apple 개발자 계정 등록(연 $99, 등록 심사 대기 1~2일 — 미리 시작) → 인증서/프로비저닝 프로파일 설정 → Release Archive 및 서명된 IPA 산출·검증(Xcode Organizer Validate로 App Store Connect 업로드 가능 상태 확인) + 실기기(아이폰) 실행 확인
- 공통: 릴리즈 모드에서 서버 주소가 클라우드를 향하도록 개발용/배포용 설정 분리

### 7. Twilio 문자 상태 되알림 엔드포인트 (갭 **#122**) 🆕

> ⚠️ **이 절이 없으면 `sms_dead`가 영원히 비어 있는 칸이 된다.** ④에서 `00014`로 컬럼은 만들었지만, 그 칸을 채워 줄 신호가 바로 이 되알림이다.

**왜 필요한가**: `messages.create()`가 즉시 주는 것은 **`queued`(접수)까지**다. **없는 번호로 보낸 것도 똑같이 「접수」로 보인다.** 실제 도달·실패는 Twilio가 우리 서버로 되알려주는 것을 받아야 안다. 결정 *「어디까지를 닿았다로 보나 → **진짜 도달까지**」*(사용자 확정)가 이것 없이는 **설 땅이 없다** — 직원이 *"34명에게 보냈다"*고 믿고 **전화를 안 건다.**

📌 **푸시는 이 문제가 없다** — `messaging.send()`는 죽은 토큰이면 즉시 예외를 던진다. **문자만의 문제다.**

**이 단계(배포)가 소유하는 것** — 공개 주소와 그 주소의 안전:

- **공개 콜백 엔드포인트 1개**: `POST /webhooks/twilio/status`. 바깥(Twilio)에서 **우리 서버로 들어오는 유일한 경로**다 — 다른 모든 외부 연동은 나가는 방향이다.
- ⚠️ **서명 검증 필수**: 공개 주소라 **인증이 없다.** `X-Twilio-Signature` 헤더를 `TWILIO_AUTH_TOKEN`으로 검증해, **아무나 두드려 *"도달했다"*(또는 *"이 번호 죽었다"*)고 거짓 보고하지 못하게** 한다. 검증 실패는 **401로 조용히 거절**하고 본문을 신뢰하지 않는다. 요구사항 6.5 `:452`와 같은 자리다.
- **환경변수**: `TWILIO_AUTH_TOKEN`(검증용) · `PUBLIC_BASE_URL`(발송 시 넘길 콜백 주소를 만든다). 값은 Railway 환경변수에만 두고 저장소에는 `.env.example`의 **키 이름만**.
- **CI/CD 주의**: 이 경로는 **인증 미들웨어에서 제외**해야 한다(직원 JWT가 없다). 제외 목록에 넣되 **서명 검증은 반드시 통과**하도록 순서를 고정한다.

**이 단계가 소유하지 않는 것**(경계):

| 넘기는 것 | 받는 곳 |
|---|---|
| `messages.create()`에 콜백 주소를 넘기는 발송 코드 | **3단계(환자 앱) 발송 함수** |
| 받은 상태를 `notification_log`에 반영(성공/영구 실패/일시 실패 구분) | 〃 — `channel`은 **실제 보낸 채널**로 기록(#120) |
| 영구 실패 시 `patients.sms_dead` 표식 세우기 | 〃 (칸은 ④ `00014`) |
| 일시 실패만 자동 재시도 2번(1분·5분), **모르는 오류 코드는 일시로 보지 않는다**(모르면 돈을 쓰지 않는다) | 〃 |
| 실패 명단 화면·탭 | **2단계 `/messages`** |

## 오류·보안 최종 점검 (요구사항 6장 대응)

- **외부 서비스 차단 실험**: FCM/Twilio/Claude API 키를 일부러 무효화해도 예약·진료기록이 정상 동작하는지 확인 (6.4)
- **비밀키 점검**: 저장소 전체 키 유출 스캔 1회, 프론트엔드 번들에 서버 전용 키 미포함 확인 (6.5)
- ⚠️ **Twilio 콜백 서명 검증**(6.5 · 갭 #122): 서명 없는 요청·**위조 서명** 요청을 실제로 쏴서 **401로 거절되는지** 확인한다. ⭐ **검증이 없으면 아무나 「이 번호 죽었다」를 보고해 환자에게 문자가 안 가게 만들 수 있다** — 공개 엔드포인트라 인증이 없으므로 이 검사가 유일한 문지기다. 정상 서명 요청은 통과해 `notification_log`에 반영되는지도 함께 본다
- **권한 검증**: 시나리오 9를 자동 테스트 + RLS 직접 조회 시도로 이중 확인
