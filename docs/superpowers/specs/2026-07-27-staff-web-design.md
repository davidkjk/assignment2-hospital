# 2단계: 직원용 웹 설계

> 근거 문서: `고객요구사항.txt` 3절(병원 직원용 웹 프로그램)
> 전체 프로젝트 5단계 중 **2단계**. 1단계 스펙(`2026-07-27-foundation-auth-data-model-design.md`)과 구현계획(`2026-07-27-foundation-auth-data-model.md`)이 이미 존재하며, 이 문서는 그 위에 쌓는 프론트엔드 + 일부 추가 백엔드 설계다.

## 범위

다룬다: 3.1(로그인/권한, 화면 관점), 3.2(오늘의 현황), 3.3(예약 캘린더), 3.4(도착·대기 관리), 3.5(환자 정보), 3.6(의사 진료 화면), 3.7(진료과·의사 일정 관리), 3.10(운영 통계, 상담봇 수치 제외), 4.3 취소요청 처리(섹션 10 — 3단계 스펙이 2단계 몫으로 남겨둔 항목)

다루지 않는다 (문서 하단 참고): 3.8(상담봇 지식관리), 3.9(상담 문의 관리) → 4단계

## 기술 스택 (2단계 추가분)

| 영역 | 선택 |
|---|---|
| 프레임워크 | React + TypeScript |
| 캘린더 | FullCalendar (`@fullcalendar/react`) |
| 서버 상태 관리 | React Query |
| 실시간 동기화 | Supabase Realtime (appointments, appointment_status_history 구독) |
| 인증 | Supabase JS 클라이언트 (1단계 Supabase Auth 그대로 사용) |

## 섹션 1: 아키텍처

- 단일 React 앱, 로그인한 `staff.role`에 따라 사이드바 메뉴와 라우트가 달라짐
- 라우트: `/today`, `/calendar`, `/queue`, `/patients`, `/patients/:id`, `/doctor/console`, `/admin/staff`, `/admin/schedule`, `/admin/stats`
- 서버 상태는 React Query로 캐싱/재검증, 여러 직원이 동시에 보는 화면(대기목록/오늘현황/캘린더)은 Supabase Realtime 구독으로 실시간 갱신
- 1단계 백엔드 API를 그대로 호출, 이번 단계에서 필요해진 신규 API는 아래 "2단계에서 추가되는 백엔드" 참고

## 섹션 2: 오늘의 현황 (`/today`)

- 로그인 후 기본 진입 화면
- 상단 "지금 처리할 것" — 있을 때만 표시되는 카드:
  - 오래 대기 환자(`hospital_settings.long_wait_threshold_minutes`, 기본 30분↑)
  - 응급/주의 표시된 환자
  - 확인 필요 상담 문의 — 2단계에서는 항상 "0건" 고정(4단계에서 실제 데이터 연결)
  - 일정변경으로 확인 필요한 예약 N건 (섹션 3 참고)
- 하단 "오늘 요약" — 통계 타일 그리드(전체예약/도착/대기/진료중/완료/취소·부도, 의사별 대기인원), 클릭 시 조건별 필터링된 목록으로 이동

## 섹션 3: 예약 캘린더 (`/calendar`)

- FullCalendar 주간/일간 뷰
- 상단 필터: 진료과 드롭다운, 의사 다중 선택
- 슬롯 색+텍스트: 빈시간(흰색), 예약됨(파란색+환자명), 휴진(회색 빗금) — 요구사항 7절 "색뿐 아니라 글자로도 구분"
- 빈 슬롯 클릭 → 전화예약 등록 모달(기존환자 조회/신규등록 → 방문이유 → 저장)
- 예약 슬롯 클릭 → 상세 사이드패널(변경/취소, 사유 입력)
- 당일 급한 환자를 기존 슬롯 사이에 추가 시 저장 전 경고 팝업
- 의사 일정변경 저장 시, 영향받는 예약이 있으면 저장 전 목록(체크박스, 기본 전체선택) 표시 → 저장 확정 시 체크된 환자의 이름·연락처·기존시간이 화면에 표시되어 접수직원이 전화 안내 가능
- **영향받는 예약은 저장 모달을 닫아도 사라지지 않는다** — "취소되지 않은 예약인데 시간이 방금 등록된 휴진/변경 기간과 겹치는 경우"를 매번 조회해서 판별(별도 상태 테이블 없이 계산). 실제로 재예약/취소 처리해야만 사라짐
- 영향받는 예약은 캘린더에서 원래 자리에 그대로 표시(파란색 "예약됨")되되, 모서리에 노란 경고 아이콘(⚠)이 추가로 붙어 "확인 필요"임을 알림
- 재예약 처리 시 같은 `appointment_id`를 유지한 채 슬롯만 교체(신규 예약 생성 아님) — 새로 예약된 슬롯은 경고 아이콘 없이 평범하게 표시, 기존 슬롯은 빈시간(또는 그 날짜가 휴진이면 휴진)으로 반납

## 섹션 4: 대기 목록 (`/queue`)

- 오늘 예약 환자를 상태별(도착/대기/진료중/완료)로 리스트업, 워크인 등록 버튼 포함
- 각 행: 순번, 환자명(생년월일), 대기시간, 진료과/의사, 응급표시 아이콘, 상태 변경 버튼(유효한 다음 상태만 노출)
- 대기 순서: **드래그앤드롭**으로 변경 → 드롭 시 사유 입력 모달(필수) → 확인 시 저장, **취소 시 드래그 이전 순서로 원위치**
- 응급표시 토글 → "의학적 응급도 판정 아님" 확인 팝업 → 활성화 시 행 강조 + 대기목록/의사화면/오늘의현황 3곳에 반영

## 섹션 4.5: 환자 검색 (`/patients`)

- 사이드바 메뉴에서 진입하는 전역 환자 검색 화면. 이름 + 생년월일(선택)로 검색 → 결과 목록(이름/생년월일/전화번호, 목록 마스킹 규칙 적용)을 표시
- 결과가 여러 건(동명이인)이면 목록에서 바로 구분 가능하도록 생년월일·전화번호를 함께 노출
- 결과 목록에서 환자를 선택하는 시점에 동명이인 재확인 팝업(다른 접수직원 화면과 동일한 컴포넌트 — 적용 범위는 아래 "동명이인 재확인은 접수직원 화면(...)에만 적용" 문단 참고)을 띄워 이름·생년월일 재확인 후 `/patients/:id`로 이동 (요구사항 3.5 "저장 전 이름·생년월일 재확인"을 검색 진입 경로에도 동일 적용)
- 접수직원·관리자가 사용하는 화면 — 접근 권한은 섹션 5(환자 상세)와 동일
- 빠른 입력 UX 필요(예: 자동완성, 단축키, Enter로 다음 필드 이동 등) — 세부 규칙은 지금 못박지 않고 구현 단계에서 확정 (요구사항 7 "직원용 웹" "접수 직원이 빠르게 사용할 수 있도록 검색과 키보드 입력이 편해야 합니다")

## 섹션 5: 환자 상세 화면 (`/patients/:id`)

- 상단: 기본정보(이름/생년월일/연락처/성별), 본인-가족 관계
- 탭: "예약·방문 이력" / "사전문진" / "진료기록"(완료된 과거 기록) / "내부 메모"
- 화면 진입 시 조용히(화면 표시 없이) `access_audit_log`에 열람 기록 (1단계 `audit_service.log_access` 재사용)
- 목록에서는 전화번호/생년월일 일부 마스킹, 이 화면에서는 전체 노출
- "상담봇 문의 중 직원에게 전달된 내용" 탭은 4단계에서 추가 (아래 "다루지 않는 것" 참고)

## 섹션 6: 의사의 진료 화면 (`/doctor/console`)

- 3단 레이아웃: 왼쪽 오늘 대기 환자 목록(응급표시 포함) / 가운데 환자정보+예약이유+사전문진 / 오른쪽 과거 진료기록+하단 작성란
- 작성란: 증상/진단/처치 + 환자 공개용 안내문(`patient_visible_notes`, 완료 시 환자 앱 방문 이력에 노출, 요구사항 4.6) + "문구 불러오기"(의사 개인별 저장, 신규 테이블 `doctor_quick_phrases`) + 임시저장/완료 버튼
- **동명이인 재확인 팝업은 이 화면에는 없음** — 대기 목록 항목은 이미 접수 시점에 신원이 확정된 appointment이므로 재검색 위험이 구조적으로 없음. 완료 버튼은 일반 확인 팝업만("완료 후에는 사유 입력 없이 수정 불가")
- 완료 후 수정: "수정" 버튼 → 사유 입력 필수(1단계 `revise_record`) → 저장 후 "최근 수정: 날짜/작성자/사유" 표시 + 이전 내용 이력 보기 링크
- 날짜 선택기로 과거 환자 조회

**동명이인 재확인은 접수직원 화면(캘린더의 전화예약 등록 모달, 대기목록의 워크인 등록, 섹션 4.5 전역 환자검색)에만 적용**: 환자 검색 결과에서 선택하는 시점 1회 + 예약을 확정하는 시점 1회.

## 섹션 7: 진료과·의사 일정 관리 (`/admin/schedule`, 관리자 전용)

- 탭: "진료과 관리"(추가/수정/사용중지) / "의사별 스케줄"(요일별 시간·슬롯단위·점심시간·하루최대인원·예약마감 폼 + "정기 휴진" 체크박스 — 체크 시 그 요일 나머지 필드 비활성화, `doctor_schedule_rules.is_day_off`, 요구사항 3.7) / "특정일 예외"(캘린더에서 날짜 클릭 → 휴진/시간변경, 비반복 단발 예외 전용)
- 저장 시 영향받는 예약이 있으면 섹션 3과 동일한 경고+선택 컴포넌트 재사용
- 의사 계정 자체를 새로 만드는 것은 이 화면이 아니라 `/admin/staff`(1단계 직원 초대 API 사용)

## 섹션 8: 운영 통계 (`/admin/stats`, 관리자 전용)

- 기간 선택기, 예약/취소/부도/방문 건수, 진료과·의사별 현황, 시간대별 방문, 평균 대기시간, **기준시간(`hospital_settings.long_wait_threshold_minutes`, 기본 30분) 초과 대기 사례 건수**(요구사항 3.10 — "오래 기다린 사례"의 기간별 집계, 실시간 화면인 섹션 2 "오래 대기 환자" 카드와 별개), 앱예약 vs 직원등록 비율 — 표+막대그래프
- 숫자 클릭 시 해당 목록으로 이동, CSV 다운로드 버튼
- 상담봇 관련 통계는 4단계에서 추가 (아래 참고)

## 섹션 9: 오류 처리 & 동시성 (프론트엔드)

- 409(낙관적 잠금 충돌) 시 한글 배너("다른 직원이 먼저 수정했습니다. 최신 내용을 불러옵니다") + 자동 재조회
- 저장/제출 버튼은 진행 중 비활성화(중복 클릭 방지)
- 실시간 동기화: Supabase Realtime 구독(대기목록/오늘현황/캘린더)
- 네트워크 오류 시 "저장에 실패했습니다. 다시 시도해주세요" 명확히 표시, 조용히 무시하지 않음

## 섹션 10: 취소요청 대기열 (`/cancellation-requests`)

> 배경: 3단계(환자 앱) 스펙에서 "예약 마감 시간이 지난 뒤 환자가 취소를 요청하면 `appointments.cancellation_requested_at`을 채우고, 직원이 승인/반려하는 화면은 2단계 몫"이라고 설계했으나, 2단계 스펙에 반영되지 않았던 항목. 이번에 이 화면을 추가한다.
>
> **요구사항 4.3과의 관계**: 4.3("병원이 정한 시간 이후에는 앱에서 직접 취소하지 못하고 상담으로 연결")을 완결하는 것은 이 대기열 화면 하나가 아니다. 마감 후 취소 요청은 입구 채널이 무엇이든(앱 취소 버튼 → 4단계 챗봇 화면 리다이렉트, 웹 상담창, 앱 내 챗봇 등) 전부 4단계 챗봇의 `예약취소_카드보내기` 도구를 거쳐 동일한 백엔드 `cancel_appointment` API를 호출하고, 동일한 `appointments.cancellation_requested_at` 필드에 기록된다 — 이 채널 무관성은 그 설계 자체에서 이미 보장된다. 이 대기열 화면은 그렇게 모인 요청들이 마지막으로 처리되는 단계(직원 승인/반려)를 담당할 뿐, 4.3을 완결하는 유일한 지점이 아니다.

- **접근 권한**: 접수직원 + 관리자 (`require_role(["receptionist", "admin"])`). 의사는 접근 불가 — 다른 직원 전용 메뉴와 동일한 원칙.
- **`/today`(오늘의 현황)**: 기존 "확인 필요 상담 문의" 카드와 같은 자리에 "취소 요청 확인 N건" 카드 추가. `cancellation_requested_at is not null`인 예약이 0건이면 카드 자체가 보이지 않음(기존 카드 패턴과 동일). 클릭 시 `/cancellation-requests`로 이동.
- **`/cancellation-requests` 목록 페이지**: `cancellation_requested_at`이 채워진 예약을 전부 표로 표시 — 환자명(생년월일), 예약 일시, 진료과/의사, 취소 요청 시각, 환자가 남긴 사유(`appointment_status_history`에서 해당 예약의 최신 행 중 `from_status = to_status`인 요청 시점 기록의 `reason`). 각 행에 `[승인]` `[반려]` 버튼.
  - **승인**: 예약 상태를 `환자취소`로 전환 + 슬롯 반납(`release_slot`, 슬롯이 있는 예약만) + `cancellation_requested_at` 비움 + `appointment_status_history`에 기록(직원이 승인 처리했음을 남김). 환자에게 별도 알림은 발송하지 않음(본인이 요청한 취소이므로).
  - **반려**: `cancellation_requested_at`만 비움(상태는 그대로 유지) + `appointment_status_history`에 반려 사유 기록 + 환자에게 "취소 요청이 반려되었습니다" 알림 발송(3단계 스펙에서 이미 정한 문구, 알림 발송 자체는 3단계 `notification_service.notify_patient` 재사용).
  - **동시성**: 다른 직원이 먼저 처리했거나 환자가 그 사이 마감 전 시간대로 예약이 옮겨져 요청이 무의미해진 경우, "이미 처리되었거나 취소 요청이 존재하지 않는 예약입니다" 한글 안내 후 목록 새로고침(6.2 원칙 재사용).

## 2단계에서 추가되는 백엔드 (1단계 스펙 이후 발견된 항목)

1단계는 이미 스펙·계획 문서가 확정되어 있어 그 문서를 고치지 않고, 이번 단계에서 새로 필요해진 것만 추가한다.

- `hospital_settings.long_wait_threshold_minutes` 컬럼 추가 (기본값 30)
- `doctor_quick_phrases` 테이블 신규: `id, doctor_id, text, created_at`, RLS는 본인 의사만 CRUD, 다른 직원은 읽기만
- `appointment_service.reschedule_appointment(appointment_id, new_slot_id, staff, reason)` 신규 서비스: 기존 슬롯 반납 + 새 슬롯 예약을 하나의 트랜잭션으로 처리(1단계 `book_slot` 재사용), `appointment_status_history`에 기록
- "영향받는 예약" 조회: 새 테이블 없이, 취소되지 않은 예약 상태 + `doctor_schedule_exceptions`를 조인하는 쿼리로 계산
- `appointment_service.list_cancellation_requests(staff) -> list[dict]`, `approve_cancellation_request(appointment_id, staff) -> None`, `reject_cancellation_request(appointment_id, staff) -> None` 신규 서비스 (섹션 10). 3단계가 만든 `cancellation_requested_at` 필드와 3단계 `notification_service.notify_patient`(반려 알림용)를 재사용
