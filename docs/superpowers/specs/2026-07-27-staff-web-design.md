# 2단계: 직원용 웹 설계 (재작성판)

> 근거 문서: `고객요구사항.txt` 3절(병원 직원용 웹 프로그램)
> 전체 프로젝트 5단계 중 **2단계**. 1단계 스펙(`2026-07-27-foundation-auth-data-model-design.md`)과 구현계획이 이미 존재하며, 이 문서는 그 위에 쌓는 프론트엔드 + 일부 추가 백엔드 설계다.
>
> ⚠️ **이 문서는 설계 결정이 모두 확정된 뒤의 재작성판이다.** 결정 근거는 결정로그(`docs/superpowers/specs/2026-07-31-ui-design-decisions.md`), 화면 동작 규칙은 `docs/design/screen-behaviors.md`, 반영 범위·추적성은 `docs/design/spec-index/SPECINDEX-staff-web.md`(Part A 기존 화면 + Part B 신규 15화면·상담봇 접점)가 원본이다. 이 스펙은 **"화면에 안 보이는 계약"**(테이블·API·상태 전이·오류·권한)을 확정하고, 화면 규칙 전수(`test('[규칙ID] …')`)는 **플랜 재작성(⑤단계)**이 맡는다.
> **여러 단계가 공유하는 데이터 모델**(발송 원장 `notification_log`·알림 설정표·예약 발송 큐·`support_requested_at`/`request_type`·`phone_reveal` 감사·Twilio 도달)은 **1단계 스펙 섹션 4 「`00010_` 이후 공용 데이터 모델」**이 단일 원본이며, 이 문서는 그것을 **참조**한다. DB 반영은 실제 적용 최신 `00009` 다음 **`00010_*.sql`부터** 순차 파일로 한다.
> **상담봇 직원·관리자 화면**(티켓함·전체 상담 기록·오답 신고·지식·미해결·품질·통계)은 사이드바 `상담봇` 4번째 그룹으로, **4단계 상담봇 스펙**이 주담당이다. 이 문서는 직원 웹 셸의 링크·배지·소비 계약만 기록한다.

## 범위

**다룬다**: 3.1(로그인/권한), 3.2(오늘의 현황), 3.3(예약 캘린더), 3.4(도착·대기 관리), 3.5(환자 정보·검색·상세·병합), 3.6(의사 진료 화면), 3.7(진료과·의사 일정 관리·운영시간 단일 소스), 3.10(운영 통계), 그리고 후반 설계에서 추가된 신규 화면군(직원 로그인·QR 접수·직원/의사 관리·접근 기록·문진 관리·병합 이력·오류 화면·안내 보내기·병원 설정).

**다루지 않는다**: 3.8(상담봇 지식 관리)·3.9(상담 문의 관리)의 화면 본체 → 4단계. 단 직원 웹 셸에서 그 그룹으로 가는 링크·배지, `/today`의 상담 문의 행 소비 계약은 여기서 다룬다.

## 섹션 1: 아키텍처와 셸·권한

- 단일 React 앱, 로그인한 `staff.role`에 따라 사이드바 메뉴와 라우트가 달라짐.
- **사이드바 = 의사 진료화면 단독 + `업무`·`기록`·`설정`·`상담봇` 4그룹**(옛 3그룹 IA는 MR2-07에서 폐기·교체). 240px, 접지 않음(결정로그 `:5086`, 규칙 `screen-behaviors.md:77-103`).
- **역할별 접근(서버에서 강제)**: UI 숨김만으로는 직접 URL/API 접근을 못 막으므로 route guard + Supabase RLS + API 403 + 버튼 노출을 **같은 역할표**로 관리한다.
  - **receptionist**: 업무 그룹(today/queue/checkin/calendar/patient search/ticket inbox/all chat history/messages).
  - **doctor**: 진료 화면 + 환자 검색 2개만. today/queue/messages 미노출.
  - **admin**: doctor console을 제외한 4그룹 전부. 직원·설정·감사·병합·오류·통계 관리.
  - **관리자 ⊇ 접수직원**(접수직원 권한은 관리자에게 자동), **관리자 ⊉ 의사**(진료기록 쓰기는 의사 본인만). `ROLE-*`(결정로그 `:3627-3633`, 갭 #114·#79).
- **실시간 배지**: 헤더·내비 배지는 서버 상태를 반영하고 연결 복구·재조회로 정합성을 회복.
- **개인정보 마스킹**: 목록은 전화번호·생년월일 마스킹, reveal은 역할·확인·감사(1단계 섹션 4 ⑥의 `phone_reveal`)를 거침.
- **세션**: 무활동 **30분** 자동 로그아웃(절대 30분이 아니라 무활동 기준), 재인증, 로그아웃 감사. 공용 접수 PC에서 세션 만료 시 환자 정보가 남지 않아야 함(요구사항 `:71-82`).
- 1단계 백엔드 API를 그대로 호출, 신규 API는 "2단계에서 추가되는 백엔드" 참고.

## 섹션 2: 직원 로그인·복구·세션 (`/login`, 신규) — 갭 #79·#25·#26·#27

- **관리자 초대 이메일 + 비밀번호**로 계정 생성(직원 자가입 불가, 1단계 원칙). 매 로그인 OTP·직원번호·관리자 대행은 쓰지 않는다.
- **셀프 비밀번호 복구**: 자기 이메일로 재설정 링크(토큰 만료·시도 제한). 비밀번호 변경 시 다른 세션 종료.
- **무활동 30분** 타이머·감사·세션 종료. reset/세션 만료/재인증 화면 변형 포함.
- 근거: 결정로그 `:3115-3130`; 규칙 `screen-behaviors.md:2292-2351`.

## 섹션 3: 오늘의 현황 (`/today`)

- 로그인 후 기본 진입 화면. 당일 업무를 **문제 우선**으로 표시.
- 상단 "지금 처리할 것"(있을 때만 카드): 오래 대기 환자(`hospital_settings.long_wait_threshold_minutes`, 기본 30분↑) · 응급/주의 환자 · **확인 필요 상담 문의**(4단계 상담봇의 pending 티켓 실제 건수 — 옛 "항상 0건 고정" 하드코딩 폐기) · **일정변경으로 확인 필요한 예약** · **미확정 경과 예약**(`예약신청`인데 시각 지남, 갭 #69).
- ⭐ **별도 취소·변경 수치 카드는 만들지 않는다**(D4). 마감 후 취소·변경 상담은 **`확인 필요한 예약` 카드의 환자별 행**으로 합류하고, 행에서 티켓/예약으로 **양방향 이동**한다. 근거: 결정로그 `:5041-5067`, 규칙 `screen-behaviors.md:5421-5433`.
- **지원 요청 조회**: today 요약은 예약과 지원 요청(`support_requested_at`/`request_type`, 1단계 섹션 4 ①)을 **함께 반환**한다. `get_today_summary`의 `pending_inquiries_count: 0` **하드코딩을 실제 query로 교체**한다(갭 D4).
- **일정변경 영향 예약 처리의 주 화면**: 관리자 schedule 화면은 영향 건수·시간만 보고, **예약 선택·처리는 여기서**. schedule에서 자동 취소·checkbox 일괄 확정하지 않는다(섹션 8·규칙 `screen-behaviors.md:1420-1467`).
- **자정 경계**(#37): 서버 기준일·timezone으로 전일 미완료 건을 분리·보존·배지.
- 하단 "오늘 요약": 통계 타일(전체예약/도착/대기/진료중/완료/취소·부도, 의사별 대기인원). 클릭 시 `/queue`의 해당 탭으로.

## 섹션 4: 예약 캘린더 (`/calendar`)

- FullCalendar 주간/일간 뷰. 상단 필터: 진료과 드롭다운, 의사 다중 선택.
- 슬롯 색+텍스트: 빈시간(흰색)/예약됨(파란색+환자명)/휴진(회색 빗금) — 색뿐 아니라 글자로도 구분(요구사항 7절). **의사별 색상은 안정적 palette/index**로 관리(index 변경 시 기존 기록 보존, 대비 확보, 갭 #83).
- 빈 슬롯 클릭 → 전화예약 등록 모달(기존환자 조회/신규등록 → 방문이유 → 저장). **동명이인 재확인 팝업** 적용.
- 예약 슬롯 클릭 → 상세 사이드패널(변경/취소, 사유 입력).
- **재예약(reschedule)**: 같은 `appointment_id`를 유지한 채 슬롯만 교체(신규 생성 아님). 기존 슬롯은 빈시간(또는 휴진)으로 반납. `reschedule_appointment`는 반납+예약을 한 트랜잭션으로.
- **영향받는 예약**: 별도 상태 테이블 없이 "취소되지 않은 예약이 방금 등록된 휴진/변경 기간과 겹치는가"를 매번 계산. 캘린더 원자리에 파란색으로 두되 모서리에 ⚠ 아이콘. **캘린더에서 "전체 선택" checkbox로 자동 취소하지 않는다**(폐기) → 선택·처리는 `/today`로 연결.
- **시간 기준 3분리**(#45·#84·#85): 예약 가능 여부(`booking_deadline`)·표시용 시간·실제 시작/종료를 다른 필드·상태로 구분.
- **동시 편집 충돌(race)**: 이중 예약을 "경고만"으로 끝내지 않고 충돌 정보·복구·재조회 경로를 제공(optimistic update 후 서버 검증, `CAL-RACE-*`).

## 섹션 5: 대기 목록 (`/queue`)

- 오늘 예약 환자를 **상태 탭 7개**(전체 / 아직 안 옴 / 도착 / 진료 대기 / 진료 중 / 진료 완료 / 취소·부도)로 표시(한 번에 한 상태). 워크인 등록 포함.
- 각 행: 순번(진료 대기 탭만) · 환자명(생년월일 마스킹) · 대기시간 · 진료과/의사 · 응급표시 · **그 상태에서 할 수 있는 버튼**. `진료중` 전이는 **의사가 환자를 여는 순간 자동**이라 접수직원용 `[진료 시작]` 버튼은 없다(`DOCTOR-START-01`).
- **대기 순서**: 드래그앤드롭 → 드롭 시 **사유 입력 모달(필수)** → 저장, 취소 시 원위치. 순서 변경은 `appointment_status_history`에 사유와 함께 기록(요구사항 `:134`).
- **응급표시 토글** → "의학적 응급도 판정 아님" 확인 팝업 → 대기목록/의사화면/오늘의현황 3곳 반영.
- **워크인**: 목록 안 임의 버튼이 아니라 공통 start action과 연결. 초기 상태·다음 가능 시간을 서버 결과로 표시(#86·#87).
- **번호 reveal·필터·undo·같은 appointment id 보존** 포함. **잘못 연 경우 되돌리기**(`waiting→in_progress` 역전이, 사유 필수, 감사, 갭 #36·#82).
- **티켓함·`claim_ticket` 본체는 4단계(상담봇)** — 여기서는 셸 링크와 unread 배지 소비 계약만.

## 섹션 6: 환자 검색 (`/patients`)

- 사이드바에서 진입하는 전역 환자 검색. **이름 + 생년월일(선택)**로 검색 → 결과(이름/생년월일/전화번호, 목록 마스킹).
- 동명이인이면 생년월일·전화번호로 구분. 선택 시 **동명이인 재확인 팝업** → `/patients/:id`(요구사항 3.5).
- 접수직원·관리자 사용. 빠른 입력 UX(자동완성·단축키·Enter 이동)는 구현 단계 확정.
- **검색 실행은 감사에 남긴다**(개인을 겨냥한 순간부터, 1단계 섹션 4 ⑥ 확장 — `access_audit_log`에 search 사건).

## 섹션 7: 환자 상세 (`/patients/:id`, 신규 재작성) — 갭 #2·#19·#123·D4

- **헤더 요약 + 2열 섹션 + anchor**(탭으로 숨기지 않는다). 방문·가족·문진·기록·**지원 문의**·내부 메모·액션을 한 화면에서 로드.
- 화면 진입 시 조용히 `access_audit_log`에 열람 기록(1단계 `audit_service.log_access`). 목록은 마스킹, 이 화면은 전체 노출(번호 reveal은 별도 감사).
- **환자 기본정보 수정**(#19): 이름·생년월일·성별은 직원 액션. **전화번호는 직접 저장 금지** — 새 번호는 **OTP 후 Supabase Auth·환자 연락처를 함께 갱신**(전화번호가 계정 식별자). before/after·누가·언제 변경 이력.
- **가족 연결·해제·관계 수정**(#2·#3): 접수직원·관리자가 수행. **가족(B) 번호 OTP가 기본**, 번호 없을 때만 대면/서류 예외, 완료 시 B에게 통보·이의제기. `family_link`/`family_unlink` 감사.
- **문자 실패 표식**(#123): 1단계 섹션 4 ⑤의 `sms_dead`를 읽어 `⚠️ 이 번호로 문자가 가지 않습니다 (날짜 확인)`. 서비스 장애(system error)와 분리.
- **지원 문의 section**(D4): 상담봇 티켓과 `support_requested_at`을 단일 키로 연결. 취소·변경 상담은 `/today`의 행으로도 보임.

## 섹션 8: QR/예약번호 접수 (`/checkin`, 신규) — 갭 #5·#6

- **QR 1순위, 6자리 예약코드 2순위**. 같은 결과 카드에서 `[도착 처리]`. 성공 뒤 화면 유지·`도착`으로 갱신(`예약확정→도착`).
- **중복 스캔**은 첫 callback을 중복 처리하지 않는다(서버 멱등). 카메라 실패 fallback.

## 섹션 9: 의사의 진료 화면 (`/doctor/console`) — 갭 #8·#30·#7·#9

## 섹션 10: 진료과·의사 일정 관리 (`/admin/schedule`, 관리자) — 갭 #33·#88~#97·#105·#106

- **영향 예약 계산과 저장 분리**(#88~#91): 저장 완료 후 affected를 계산(버전 부여). **0건이면 팝업 안 열림**. 관리자는 **건수·예상 재조정 시간만** 확인, 선택·처리는 직원 `/today`. `needs_rescheduling`를 단순 boolean flag로 쓰지 않고 계산 version + `processed` actor/time 저장.

## 섹션 19: 오류 처리 & 동시성 (프론트엔드)

- **409(낙관적 잠금 충돌)**: 한글 배너("다른 직원이 먼저 수정했습니다. 최신 내용을 불러옵니다") + 자동 재조회.
- **지원 요청 원자 배정**(`claim_ticket`): 두 직원이 `/today`·문의함·calendar에서 같은 건을 동시에 열 수 있어, `pending→in_progress` 승패와 담당자를 반환. 경쟁 패자는 목록 유지 + 충돌 안내(본체는 4단계).
- **되돌리기(undo)**: 운영 mutation별로 제한 시간·동시성·감사·가역성을 구분(이미 환자에게 전달된 결과·진료는 무조건 되살리지 않음). 새 이벤트인지 원본 역전인지 명시.
- 저장/제출 버튼 진행 중 비활성화. Realtime 구독(대기목록/오늘현황/캘린더). 네트워크 오류 시 명확히 표시, 조용히 무시 금지.
