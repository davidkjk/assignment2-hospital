# 3단계: 환자용 모바일 앱 설계

> 근거 문서: `고객요구사항.txt` 4장(환자용 모바일 앱), 6장(공통 규칙)
> 전체 5단계 중 **3단계**의 설계입니다.
>
> 1. 기반: 인증/권한 + 예약·진료상태·수정이력 데이터 모델 (완료)
> 2. 직원용 웹 (React) (완료)
> 3. **환자 모바일 앱 (Flutter) (이 문서)**
> 4. AI 상담봇
> 5. 통합 테스트 & 배포

## 기술 스택 (3단계 추가분)

| 영역 | 선택 |
|---|---|
| 프레임워크 | Flutter |
| 상태관리/데이터 계층 | Riverpod (AsyncNotifier로 서버 상태 관리) |
| 백엔드 호출 | 1단계 FastAPI를 직접 호출 (2단계 직원용 웹과 동일 원칙) |
| 인증 | Supabase Auth phone 프로바이더 — 전화번호+비밀번호 로그인, OTP는 가입/비밀번호 찾기 시에만 사용 |
| SMS 발송 | Twilio 실연동 (OTP + 알림 SMS 백업 공용 계정) |
| 실시간 동기화 | Supabase Realtime — 본인 예약(`appointments`) 상태 구독 |
| 푸시 알림 | Firebase Cloud Messaging 실연동 |

## 섹션 1: 아키텍처

- 1단계 백엔드 API를 그대로 호출하고, 이번 단계에서 필요해진 신규 API는 아래 "3단계에서 추가되는 백엔드" 참고
- 직원 웹과 달리 환자 앱은 1인 사용 화면이 대부분이라, Realtime은 "내 예약 상태"(대기 인원, 진료중/완료 전환) 구독에만 사용
- 라우트: `/login`(가입/로그인) `/home`(가장 가까운 예약) `/booking/*`(예약 플로우) `/family` `/appointments/:id` `/history` `/settings`

## 섹션 2: 인증과 회원가입 (요구사항 4.1)

- **가입**: 전화번호 입력 → SMS OTP(Twilio) 인증 → 비밀번호 설정 + 이름/생년월일/성별 입력 → `patients` 레코드 생성(`account_patient_id` = 본인)
- **로그인**: 전화번호 + 비밀번호 (Supabase Auth phone 프로바이더의 password 로그인 사용)
- **비밀번호를 잊은 경우**: 전화번호 입력 → SMS OTP로 본인확인 → 새 비밀번호 설정 (요구사항 "비밀번호나 로그인 정보를 잊었을 때 다시 찾을 수 있어야" 충족)
- **로그아웃**: 세션 종료
- **회원 탈퇴**: 확인 팝업 → `patients.is_active=false` 소프트 삭제(1단계 원칙 재사용) + Supabase Auth 계정 비활성화
- **민감 화면 재인증**: 가족관리·계정설정/탈퇴 화면 진입 시, 무활동 5분 경과 후 재진입이면 비밀번호 재입력 요구. 방문이력·내 예약처럼 자주 쓰는 화면은 제외

## 섹션 3: 가족 등록 (요구사항 4.2)

- `patient_family_links` 재사용: 가족 이름/생년월일/관계 입력 → 별도 `patients` 레코드 생성(로그인 계정 없음, 예약용 프로필만)
- 가족 정보 수정 및 연결 해제 가능(해제는 소프트 삭제, 과거 예약 이력은 남음)
- 가족의 전체 진료기록은 열람 불가 — 예약 목록과 병원이 공개한 방문 후 안내(`medical_records.patient_visible_notes`)만 조회 가능

## 섹션 4: 진료 예약 (요구사항 4.3)

- 8단계 플로우: 본인/가족 선택 → 진료과 → 의사 → 날짜 → 시간 → 방문이유 → 최종확인 → 신청/확정
- 슬롯 조회: 2단계에서 계획된 `/calendar-slots` 엔드포인트를 환자용으로 확장(예약 가능한 슬롯만 노출)
- 예약 생성 시 1단계 동시성 제어(조건부 UPDATE `appointment_slots`)를 그대로 사용 — 다른 사람이 먼저 선택한 시간은 실패 응답, "이미 선택된 시간입니다, 다른 시간을 선택해주세요" 안내 후 화면 새로고침
- 중복 클릭 방지: 버튼 disable(1차 방어) + 서버 조건부 업데이트 실패 시 자동 거부(근본 방어, 1단계 원칙 재사용)
- 앱 예약은 기본 `예약신청` 상태. 즉시확정/직원확인후확정 여부는 `hospital_settings`의 정책 플래그로 관리(2단계 관리자 설정과 연동)
- **변경**: 기존 슬롯 반납 + 새 슬롯 예약(취소 후 재예약과 동일 처리)
- **취소**: 취소는 되돌릴 수 없는 동작이므로 앱 화면에서 "정말 취소하시겠습니까?" 확인 다이얼로그를 통과해야 진행된다(요구사항 7절, 실수 방지). 예약 변경(reschedule)은 이미 날짜→시간 두 단계 선택을 거치므로 별도 확인창은 생략한다.
  - 마감 전: 확인 다이얼로그 통과 후 즉시 `환자취소` 상태로 전환
  - 마감 후: "마감이 지나 상담으로 연결해드립니다" 안내 후 AI 상담 화면(4단계 챗봇)으로 이동. 앱은 화면 전환만 담당하며, 실제 `cancellation_requested_at` 기록과 인계 티켓(`support_tickets`, 사유 `late_cancellation`) 생성은 4단계 챗봇 도구 `예약취소_카드보내기`가 담당. `status`는 그대로 유지하고, 앱에는 예약 상태와 별도로 "상담 연결됨 · 직원 확인 중" 배지를 표시(❌ "취소 요청됨" — 자동 접수로 오해할 수 있는 표현 금지, 4단계와 동일 원칙). 직원이 처리하면 `환자취소`로 전환, 반려하면 필드를 비우고 "취소 요청이 반려되었습니다" 알림 발송(직원의 실제 검토가 끝난 뒤의 사후 통보이므로 유지)

## 섹션 5: 사전문진 (요구사항 4.4)

- `questionnaire_templates`(진료과별 질문 세트) + `questionnaire_responses`(1단계 모델 재사용)
- 예약 완료 화면에서 "사전문진 작성하기" 유도, "나의 예약" 목록에서도 작성 여부 배지 표시
- 방문(도착 처리) 전까지 자유롭게 수정 가능, 도착 이후엔 읽기 전용으로 전환(의사가 이미 확인 중일 수 있어 혼선 방지)
- 상담봇 대화 중 수집된 내용의 사전문진 반영(요구사항 원문 언급)은 4단계 상담봇 구현 시 처리. **[해결됨, 2026-07-30 재정정]** 4단계 챗봇 도구 `사전문진_카드보내기`가 대화 전체에서 파악한 내용을 채팅 카드(`QuestionnaireCard`)로 보여주고, 환자가 직접 고쳐서 [저장]까지 눌러야 반영되는 방식으로 완결(웹 상담창·앱 챗봇 어느 채널이든 동일). 앱의 사전문진 화면은 조회·직접 작성용으로 그대로 유지되며, 챗봇이 저장한 값도 이 화면에 항상 최신값으로 표시됨(화면이 저장 시점마다 다시 불러오므로). "방문(도착 처리) 전까지 자유롭게 수정 가능, 도착 이후엔 읽기 전용" 규칙은 챗봇 도구에도 동일하게 적용된다(우회 경로 없음).

## 섹션 6: 나의 예약과 방문 상태 (요구사항 4.5)

- 홈 화면: 가장 가까운 예약 카드(일시/진료과/의사/병원위치/확정여부/사전문진 작성여부/QR·예약번호/**변경·취소 버튼**)
- 변경·취소 버튼은 홈 카드의 빠른 실행(shortcut)이며, 누르면 `/appointments/:id` 상세화면으로 이동해 실제 변경·취소 절차(확인 다이얼로그 포함, 섹션 4)를 이어간다 — 홈 카드와 상세화면은 배타적이지 않다(요구사항 4.5)
- QR·예약번호: `appointments.id` 기반 예약번호 텍스트 + 클라이언트에서 생성하는 QR 이미지(서버 별도 발급 불필요). 접수 직원이 웹에서 이 번호로 검색해 접수 처리
- 병원 도착 후 상태(도착확인/대기/내앞대기인원/진료중/진료완료)는 Supabase Realtime으로 `appointments` 구독, 상태 변경 시 자동 갱신
- "예상 대기시간은 변동될 수 있습니다" 문구 고정 표시

## 섹션 7: 방문 이력 (요구사항 4.6)

- 과거 방문일/진료과/담당의사/`medical_records.patient_visible_notes`만 조회 — 내부 진료기록(`symptoms`/`diagnosis`/`treatment`)은 노출 안 함(1단계에서 이미 필드 분리)
- 진료기록이 의사에 의해 수정되어도 환자는 최신 `patient_visible_notes`만 확인(내부 수정이력은 직원 전용)

## 섹션 8: 알림 (요구사항 4.7)

- `device_tokens`(신규) — 환자별 FCM 토큰 등록/해제
- 푸시: FCM 실연동
- 문자 백업: Twilio 실연동(OTP와 같은 계정 재사용), 앱 미설치 또는 필요 시 발송
- 발송 대상: 예약 신청/확정, 전날·당일 리마인더, 변경/병원취소, 사전문진 미작성 안내, 진료완료 후 병원안내. ("직원 상담 답변 도착"은 4단계 상담봇 완성 후 연동)
- 1단계 원칙 재사용: 알림 발송은 예약/진료기록 저장과 분리된 별도 처리(best-effort) — 실패해도 핵심 기능(예약, 진료기록)은 유지

## 섹션 9: 접근성과 오류 처리 (요구사항 4.8, 6.4)

- 큰 글씨/버튼, 화면당 핵심 행동 1개, 한글 오류 안내(1단계 공통 원칙 재사용)
- 오프라인 감지: 네트워크 끊김 시 저장 버튼 비활성화 + "인터넷 연결을 확인해주세요" 배너 — 저장된 것처럼 보이는 상태 금지
- 중복 클릭 방지: 예약/취소/사전문진 저장 버튼 공통 처리

## 3단계에서 추가되는 백엔드

- 신규 테이블: `device_tokens`(FCM 토큰)
- `appointments`에 `cancellation_requested_at` 필드 추가
- 신규/확장 API: 환자용 슬롯 조회, 예약 생성/변경/취소(마감전후 분기), 가족 CRUD, 사전문진 제출/조회, 방문이력 조회, 알림 토큰 등록

## 다른 단계에 미치는 영향

- **2단계(직원용 웹)**: "취소요청 대기열" 화면이 추가로 필요함(마감 후 취소 요청을 직원이 확인/승인·반려). **[해결됨]** `staff-web-design.md` 섹션 10 + `staff-web.md` Task 16으로 반영 완료(정합성 검토 중 발견된 갭 보완, 2026-07-28).

## 이번 단계에서 다루지 않는 것 (4단계에서 다룸)

- AI 상담봇 관련 전체 기능(5장): 상담봇을 통한 예약, 진료과 선택 도움, 직원 이관
- 상담봇 대화 중 수집한 사전문진 내용의 자동 반영
- "직원 상담 답변 도착" 알림(상담봇 이관 이후 발생하는 알림)
