# 3단계: 환자용 모바일 앱 설계 (재작성판)

> 근거 문서: `고객요구사항.txt` 4장(환자용 모바일 앱), 6장(공통 규칙)
> 전체 5단계 중 **3단계**의 설계입니다.
>
> 1. 기반: 인증/권한 + 예약·진료상태·수정이력 데이터 모델 (완료)
> 2. 직원용 웹 (React)
> 3. **환자 모바일 앱 (Flutter) (이 문서)**
> 4. AI 상담봇
> 5. 통합 테스트 & 배포
>
> ⚠️ **이 문서는 설계 결정이 모두 확정된 뒤의 재작성판이다.** 결정의 이유는 결정로그(`docs/superpowers/specs/2026-07-31-ui-design-decisions.md`), 화면 동작 규칙은 `docs/design/screen-behaviors.md`(환자 앱 묶음 0~8, `:2538~4749`), 반영 범위·추적성은 `docs/design/spec-index/SPECINDEX-patient-app.md`가 원본이다. 이 스펙은 **"화면에 안 보이는 계약"**(테이블·API·상태 전이·오류·권한)을 확정하고, 화면 규칙 전수(`test('[규칙ID] …')`)는 **플랜 재작성(⑤단계)**이 맡는다.
> **여러 단계가 공유하는 데이터 모델**(발송 원장·알림 선호도·알림 설정표·마감 후 지원 요청·Twilio 도달)은 **1단계 스펙 섹션 4 「`00010_` 이후 공용 데이터 모델」**이 단일 원본이며, 이 문서는 그것을 **참조**한다. DB 반영은 실제 적용 최신인 `00009` 다음 **`00010_*.sql`부터** 순차 파일로 한다(옛 플랜의 `00200~00204` 번호대는 폐기·재번호).

## 기술 스택 (3단계 추가분)

| 영역 | 선택 |
|---|---|
| 프레임워크 | Flutter |
| 상태관리/데이터 계층 | Riverpod (AsyncNotifier로 서버 상태 관리) |
| 백엔드 호출 | 1단계 FastAPI를 직접 호출 (2단계 직원용 웹과 동일 원칙) |
| 인증 | Supabase Auth phone 프로바이더 — 전화번호+비밀번호 로그인, OTP는 **가입·비밀번호 찾기 시에만** 사용 |
| SMS 발송 | Twilio 실연동 (OTP + 알림 SMS 백업 공용 계정) |
| 실시간 동기화 | Supabase Realtime — 본인 예약(`appointments`) 상태 구독 |
| 푸시 알림 | Firebase Cloud Messaging 실연동 |
| 로컬 저장 | 다가오는 예약 캐시(오프라인 읽기 전용) — 앱 전용 영역 |

## 섹션 1: 아키텍처

- 1단계 백엔드 API를 그대로 호출하고, 이번 단계에서 필요해진 신규 API는 "3단계에서 추가되는 백엔드" 참고.
- 직원 웹과 달리 환자 앱은 1인 사용 화면이 대부분이라, Realtime은 **"내 예약 상태"**(대기 인원, 진료중/완료 전환) 구독에만 사용.
- **로컬 캐시 + 오프라인 읽기 전용**: 다가오는 예약 전체와 저장 시각을 앱 전용 영역에 보관한다. 오프라인에서는 QR/예약번호·카드만 읽고 변경·취소·저장은 막는다. 지하 등에서 예약을 잃지 않으면서 개인정보 캐시 범위를 늘리지 않는다. 로그아웃·탈퇴 시 삭제(갭 #13/#38, 결정로그 `:435~477`).
- **오프라인과 세션 만료 분리**: 네트워크 단절에서는 보관본을 유지하고, **온라인 상태에서 401이 올 때만** 로그아웃한다. `session == null`만으로 로그아웃 판정하지 않는다(결정로그 `:1014~1050`).
- 라우트: `/login`(가입/로그인) · `/home`(가장 가까운 예약) · `/booking/*`(예약 플로우) · `/family` · `/appointments/:id` · `/history` · `/list`(나의 예약) · `/notifications`(받은 알림함) · `/settings`(+ 하위 `/settings/notifications`, `/settings/password`, `/settings/withdraw`) · `/hospital`(병원 정보) · `/chat/*`(상담방 — 4단계 연동).

## 섹션 2: 인증과 회원가입 (요구사항 4.1) — 갭 #25·#27·#39~#44·#108

- **가입은 4단계**: ① **동의**(섹션 3) → ② 전화번호 입력 → ③ SMS OTP 인증 → ④ 비밀번호 설정 + 이름/생년월일/성별 입력 → `patients` 레코드 생성(`account_patient_id` = 본인).
- **로그인**: 전화번호 + 비밀번호 (Supabase Auth phone 프로바이더의 password 로그인). 평소 로그인은 OTP가 아니라 비밀번호다.
- **OTP 정책을 서버와 앱에서 통일**: 유효 5분 · 재발송 최소 30초(429로 남은 초 강제) · **한글** 문구. **가입만 `shouldCreateUser=true`**, 비밀번호 찾기는 `shouldCreateUser=false`(존재하지 않는 번호로 계정이 생기지 않게). `supabase/config.toml`의 만료·쿨다운 값을 이 정책에 맞춘다(결정로그 `:3363~3387`, `:3467~3497`).
- **비밀번호**: 8자 이상 + 영문/숫자 포함을 서버·앱에서 동일하게 검증. 비밀번호 변경 시 타 세션 종료(결정로그 `:3479~3497`).
- **비밀번호 찾기**: 전화번호 입력 → SMS OTP 본인확인 → 새 비밀번호 설정.
- **가입 미완료 라우팅**: OTP는 통과했으나 비밀번호/기본정보를 못 채운 중간 상태를 판별해 마지막 지점으로 돌려보낸다(개인정보 열거 방지 — 맞든 틀리든 같은 화면).
- **전화번호 변경**: 앱에서 스스로 바꾸지 않는다. 병원 본인확인·직원 수정 절차로 처리(아이디(ID) 로그인 도입안은 폐기, 결정로그 `:987~1012`).
- **로그아웃**: 세션 종료 + 로컬 캐시 삭제.
- **회원 탈퇴**: `확인 팝업` 단독이 아니라 **설정 하위 전용 화면**(`/settings/withdraw`) — **예약이 남아 있으면 차단** + **진료기록 법정 보관 고지** + 가족 연결 해제 고지. `patients.is_active=false` 소프트 삭제 + Supabase Auth 계정 비활성화 + 로컬 캐시 삭제(결정로그 `:792~800`).
- **민감 화면 재인증**: 가족관리·계정설정/탈퇴 진입 시, 무활동 5분 경과 후 재진입이면 비밀번호 재입력. 방문이력·내 예약처럼 자주 쓰는 화면은 제외.

## 섹션 3: 가입 동의 (요구사항 4.1, 6장) — 갭 #108

- 가입 **1단계**(전화번호 받기 전)에 둔다. 붙일 그릇 자체가 없어 신설한다(가입 3→4단계).
- **줄 넷을 분리**해 받는다 — 민감정보 동의는 **별도**(묶으면 무효). **「전체 동의」는 필수 3개만** 켜고 광고는 별도.
- **필수 3 + 광고 선택**. 알림/광고 발송은 서버에서 `transactional`(안내)/`marketing`(광고)로 구분한다(정보통신망법 — 사전동의·`(광고)`표기·야간금지·수신거부, 갭 #104).
- **신규 테이블 `consent`**(환자 앱 전용): 동의 항목·동의 여부·동의 시각을 남긴다. "동의했다"(기록)와 발송 원장의 "그래서 보냈다"(1단계 섹션 4 ②의 `notification_log`)가 함께 있어야 분쟁에 답할 수 있다.
- 근거: 결정로그 `:2238~2300`; 규칙 `screen-behaviors.md:2777~2805`.

## 섹션 4: 가족 등록 (요구사항 4.2) — 갭 #2·#3·#58~#64

- `patient_family_links` 재사용. **두 갈래**: 신규 가족 프로필 생성 / 기존 환자를 OTP로 연결.
- **신규 가족은 `patients.phone`을 nullable로** 만들어 전화번호 없이 추가(비면 보호자 번호를 조인해 마스킹 표시). `add_family_member`에 `phone: str | None` 인자(갭 #3).
- **기존 환자 연결**: OTP 본인확인 + **계정 열거 방지**(존재 여부를 화면으로 알리지 않음) + **본인 연결·중복 연결 거절**. 해제는 soft delete, **재연결은 기존 unique 행을 활성화**(새 행 만들지 않음), 접근 목록에는 **활성 링크만** 포함, **최대 10명**.
- 가족의 전체 진료기록은 열람 불가 — 예약 목록과 병원이 공개한 방문 후 안내(`medical_records.patient_visible_notes`)만.
- **연결 해제 차단**: 예약이 있으면 막고, 정보 수정 안쪽에서 확인. `has_visit_history`는 서버가 판정.
- **성별 필수·F/M 표준화**.
- 근거: 결정로그 `:355~376`, `:1332~1397`, `:3963~3999`.

## 섹션 5: 진료 예약 (요구사항 4.3) — 갭 #8·#9·#15·#21·#45~#47

- **8단계**: 본인/가족 → 진료과 → 의사 → 날짜 → 시간 → 방문이유 → 최종확인 → 신청/확정.
- **예약 시간 판정은 단일 서버 함수**로. `booking_deadline`, 현재 시각, 당일 최소 30분 여유, 8주 예약 범위를 앱이 하드코딩하지 않는다. 앱·직원·챗봇이 **같은 슬롯/대기 계산 결과**를 쓴다. `estimated_wait_minutes`(예상 대기)와 `schedule_summary`(진료요일 요약)를 서버 한 곳에서 생성(갭 #21·#45~#47, 결정로그 `:603~684`, `:1180~1246`).
- **슬롯 조회**: 2단계 `/calendar-slots`를 환자용으로 확장(예약 가능한 슬롯만, 마감/지난 시각/기간 판정 반영).
- **동시성**: 1단계 조건부 UPDATE(`appointment_slots`) 그대로 사용. 먼저 선택된 시간은 실패 응답 → "이미 선택된 시간입니다" 안내 후 시간 격자로 복귀.
- **예약 생성 멱등성**: 클라이언트 UUID를 저장하고 **동일 UUID 재요청은 기존 예약을 반환**. 버튼 disable은 보조 방어일 뿐 네트워크 재시도까지 막지 못한다(갭 #15, 결정로그 `:510~570`). 요청 ID는 `00010_` 마이그레이션.
- **자동확정 기본값 켬**: `hospital_settings.auto_confirm_app_bookings` 기본값을 **`true`**로 한다(무설정 병원의 `예약신청` 고착 방지). 직원 확인 방식은 명시적으로 선택한 병원만(AD-051, 결정로그 `:3179` — 옛 플랜의 default false를 폐기·교체).
- **변경**: 기존 슬롯 반납 + 새 슬롯 예약. **변경도 확인창을 둔다**(변경 전→후 확인 — 옛 "변경은 확인창 생략"을 폐기·교체, 결정로그 `:4762~4810`).
- **낙관적 잠금**: 상세의 `updated_at`을 다시 보내 서버 조건부 비교 후 **409**. 충돌 시 최신 상태를 함께 반환하고 재시도 유도 문구는 쓰지 않는다(결정로그 `:593~599`).
- **취소**(되돌릴 수 없는 동작 — 확인 다이얼로그 필수):
  - **마감 전**: 확인 다이얼로그 통과 후 즉시 `환자취소`.
  - **마감 후**: "마감이 지나 상담으로 연결해드립니다" 안내 팝업 → `[상담 채팅 연결]`. **누른 즉시** 공통 `appointments.support_requested_at` + `request_type`(`취소`) 기록(1단계 섹션 4 ①). 앱에는 예약 상태와 별도로 **"상담 연결됨 · 직원 확인 중"** 배지(❌ "취소 요청됨" 등 자동 접수 오해 표현 금지). `status`는 유지, 실제 취소/변경은 직원 상담 후 전이. 폼 제출·전용 대기열은 되살리지 않는다(결정로그 `:4170~4260`).
- **마감 후 변경**도 취소와 동일하게 상담 연결로 보낸다(`request_type`=`변경`). 마감 후 [시간 변경]을 그대로 두면 마감 규칙이 우회되므로 분기한다. **희망 일시는 저장하지 않는다**(결정로그 `:4176~4191`).

## 섹션 6: 사전문진 (요구사항 4.4) — 갭 #4·#17·#50~#57·#77

- `questionnaire_templates` + `questionnaire_responses`(1단계) 확장.
- **작성 중/완료 분리**: 문항 1개씩 **자동 저장(부분 upsert)**과 최종 제출을 분리한다. 완료 시각·진행률을 서버에서 계산(자동 저장을 완료로 오인하지 않게). 부분 저장·진행 상태 조회 API 추가(갭 #4).
- **문항 계보 보존**: 고유 문항 ID + **당시 질문 스냅샷** + 설명 + `target_gender`(노출 성별)를 함께 저장해 양식이 나중에 바뀌어도 과거 답을 재현. 30문항 상한, 성별 F/M 표준화(갭 #17·#50~#57).
- **수정 가능 시점**: 옛 "**도착 이후** 읽기 전용"을 **"진료 시작 이후 읽기 전용"**으로 폐기·교체한다. 도착·대기 중에는 수정 허용(결정로그 `:4762~4800`, 규칙 `QNR-LIVE-*`).
- 읽기 전용에서도 **답 있음/미작성/미표시**를 구분한다.
- **의사 문진 열람은 담당 의사에게만** — `assigned_doctor_can_read_responses`에서 **관리자 예외를 제거**한다(AD-050, 결정로그 `:3178`, 규칙 `screen-behaviors.md:1585~1593`). DB/RLS·의사 화면은 직원 웹 담당.
- **상담봇 연동**(4단계): 챗봇 도구 `사전문진_카드보내기`가 대화에서 파악한 내용을 `QuestionnaireCard`로 보여주고, 환자가 직접 고쳐 [저장]해야 반영. 앱 문진 화면은 항상 최신값 표시(저장 시점마다 다시 불러옴). "진료 시작 전까지 수정" 규칙은 챗봇 도구에도 동일 적용(우회 경로 없음).

## 섹션 7: 나의 예약과 방문 상태 (요구사항 4.5) — 갭 #11·#12·#18·#22·#23·#29·#69·#74·#81

- **홈 화면**: 가장 가까운 하루치 예약을 **본인+가족 목록**으로. 카드에 일시/진료과/의사/병원위치/확정여부/사전문진 작성여부/QR·예약번호/변경·취소 버튼(10종 상태 카드).
- **실제 상태·주체·시각 응답**: `appointment_status_history`에서 취소/완료 **주체와 시각**을 반환한다. "취소되었거나 완료" **한 문장으로 합치는 것을 금지**해 앱 카드가 구분하도록 한다(갭 #11, 결정로그 `:572~599`).
- 변경·취소 버튼은 홈 카드의 빠른 실행이며, 누르면 `/appointments/:id` 상세로 이동해 실제 절차(확인 다이얼로그, 섹션 5)를 이어간다.
- **QR·예약번호**: `appointments.id` 기반 텍스트 + 클라이언트 생성 QR 이미지(서버 별도 발급 불필요). QR 전체화면·밝기 올림. 오프라인에서도 읽힘.
- **도착 후 상태**(도착확인/대기/내앞대기인원/진료중/진료완료): Supabase Realtime으로 `appointments` 구독, 자동 갱신. "예상 대기시간은 변동될 수 있습니다" 고정 표시.
- **알림함**(`/notifications`): 받은 알림 목록·읽음 상태(열면 읽음). 저장소는 1단계 섹션 4 ②·③(끈 알림은 여기에도 남기지 않음).
- **병원 변경 확인 기록**: 병원발 변경 안내를 환자가 `[확인]`하면 서버에 `patient_change_acknowledged_at`을 남긴다(갭 #74). 알림을 놓쳐도 앱을 열면 카드 위에 변경 안내+`[확인]`이 뜬다(갭 #17).

## 섹션 8: 나의 예약 목록 (요구사항 4.5) — 갭 #71·#75·#76

- **20건 커서 페이지**, 안정 정렬. 목록 조회 실패 시 기존 줄을 보존하고 20건 자동 이어받기.

## 섹션 9: 방문 이력 (요구사항 4.6) — 갭 #23·#24·#28·#29·#70

- 과거 방문일/진료과/담당의사/`medical_records.patient_visible_notes`만 조회 — 내부기록(`symptoms`/`diagnosis`/`treatment`) 비노출.
- **상태 모델 확장**: `진료완료`만이 아니라 **취소·부도(no-show)·미확정**을 포함한다. 문진 요약/연결, 확인 이력(`patient_change_acknowledged_at`). **20건 커서·안정 정렬**. 부도 생성은 직원/배치(직원 웹 담당).
- 진료기록이 수정돼도 환자는 최신 `patient_visible_notes`만 확인(내부 수정이력은 직원 전용).

## 섹션 10: 알림 (요구사항 4.7) — 갭 #5·#22·#72·#81·#99~#100·#103~#104·#109~#111·#125~#126

- **`device_tokens`**(환자 앱 전용, 신규): `(id, patient_id, fcm_token, created_at)` — FCM 토큰 등록/해제. `00010_` 마이그레이션(옛 `00202` 재번호).
- **알림 선호도는 발송 직전 서버 검사**: `notification_preferences`(1단계 섹션 4 ③)에 환자별 종류 on/off·문자 여부. **FCM 토큰은 삭제하지 않는다**. 끈 알림은 푸시·문자·알림함 어디에도 생성하지 않는다.
- **발송은 공용 dispatcher 한 곳에서**: 문구·채널·죽은 토큰·도달 반영을 **`notify_patient` 한 함수**가 만진다(1단계 섹션 4 ②④⑧). 선호도·병원 문자정책(`HSET-SMS-*`)·안내/광고 구분·야간·자유문구·날짜/시각 토큰·죽은 토큰을 **한 번만** 판정한다. 채널 상수(`'push'`) 박기 금지, 문자로 폴백해도 병원 문자 설정을 본다(#111·#120).
- **발송 대상**: 예약 신청/확정, 전날·당일 리마인더(날짜·시각 포함, #125), 변경/병원취소, 사전문진 미작성 안내, 진료완료 후 병원안내. ("직원 상담 답변 도착"은 4단계 상담봇 연동.)
- 알림 발송은 예약/진료기록 저장과 분리된 best-effort(1단계 원칙). 실패해도 핵심 기능 유지. 실패·재시도·도달은 `notification_log`에 남는다(#119·#121·#122).

## 섹션 11: 병원 정보와 설정 (요구사항 4.6, 4.8) — 갭 #26·#48·#49·#70

- **병원 정보**(`/hospital`): 주소 문자열을 지도 앱에 전달, 전화는 `tel:` 링크. 병원 정보 API 재사용.
- **설정 하위 화면**: `/settings/notifications`(알림 종류별 on/off·문자 여부) · `/settings/password`(비밀번호 변경) · `/settings/withdraw`(탈퇴 — 섹션 2). placeholder였던 `/settings`를 실제 하위 화면으로 채운다. 민감 화면 재인증 적용.
- **당일 생성 예약 취소 예외**: 생성 후 30분 이내는 기본 마감에 걸려도 취소 허용(#48).
- 예약 상세에 `reason`/장소/상태/병원 정보 표시(#49).

## 섹션 12: 접근성과 오류 처리 (요구사항 4.8, 6.4) — 갭 #13·#14·#38

- 큰 글씨/버튼, 화면당 핵심 행동 1개, 한글 오류 안내.
- **예외 원문 비노출**: `AppError(str(exc), …)`로 Python 예외 원문이 환자 화면에 뜨던 4곳을 **예외별 한글 문장 매핑**으로 바꾼다. 미분류 예외는 정형 문장, 원문은 로그에만(갭 #14, 결정로그 `:480~509`).
- **오프라인 감지**: 네트워크 끊김 시 저장 버튼 비활성화 + "인터넷 연결을 확인해주세요" 배너. 저장된 것처럼 보이는 상태 금지. 오프라인 캐시는 읽기 전용(섹션 1).
- 조회 실패만 `[다시 시도]`, 저장 변경 버튼은 Busy 상태.
- 중복 클릭 방지: 예약/취소/사전문진 저장 버튼 공통 처리.

## 섹션 13: 상담봇 앱 연동에서 소비하는 정본 (4단계 상담봇이 주담당, 앱은 계약 소비자)

- **상담방(같은 상담방 루트)**: 앱·웹 상담은 같은 상담방 시간순 기록(`chat_threads`·`chat_messages` — 상담봇 스펙). 카드 payload/상태/실행결과, 예약-티켓 FK(`support_tickets.appointment_id`), AI 세션 30분 경계, 직원 답변 알림 배칭을 보존(3-A, 결정로그 `:4278~4760`).
- **MR2-02 이전 상담**: 상담방 상단 `이전 상담` → `CHAT-HISTORY`, 뒤로가기는 상담방(`NAV-CHATAPP-10`). 규칙 `screen-behaviors.md:5003~5052`.
- **MR2-03 인증 복귀 재확인 카드**: 인증 완료 뒤 예약/취소를 자동 실행하지 않는다. 최신 대상·슬롯을 재검증하는 카드에서 환자가 `[신청]`/`[취소]`를 확정한다(앱·웹 공통 멱등/최신성 계약, 공용 예약/취소 API 소비).
- **MR2-04 예약 3단계 카드**: 예약 3단계에서 환자 맥락은 낮추고 **의사 선택 카드를 강조**, `다음 가능 시간`은 제거. 앱 예약 3단계 UI 우선순위와 챗봇 카드가 같은 선택 대상을 표현(규칙 `screen-behaviors.md:3446~3459`).
- **역대조-1 긴급 안내**: 긴급 분류 실패는 `안내` 제목 + 119/응급실 확정 문구. 앱이 일반 예약을 계속하거나 연결 완료를 거짓 표시하지 않는다(`CHAT-URGENT-EXC-01`).
- **역대조-6 late-flow 잠금**: 상담 연결 처리 중 닫기/연결 버튼을 잠그고, 실패 시 재활성화(`LATEFLOW-POP-*`).
- **MR2-01**(폐기): 익명 웹의 다른 기기 이어보기는 만들지 않는다 — 환자 앱 로그인 상담 이력과 혼동하지 않는다.

## 3단계에서 추가되는 백엔드

- **공용 데이터 모델은 1단계 섹션 4를 참조**(발송 원장 `notification_log` 확장·`notification_preferences`·알림 설정표·예약 발송 큐·`appointments`의 `support_requested_at`/`request_type`·`patients` 문자 실패 표식·`access_audit_log` `phone_reveal`·Twilio 도달). 여기서 새로 정의하지 않는다.
- **환자 앱 전용 신규 테이블**: `device_tokens`(FCM 토큰) · `consent`(가입 동의) · 예약 생성 요청 UUID 저장(멱등성).
- **신규/확장 API**: 환자용 슬롯 조회(마감/기간/대기 판정), 예약 생성(멱등 UUID)/변경/취소(마감 전후 분기·409 낙관적 잠금), 가족 CRUD(phone nullable·OTP 재연결), 사전문진 부분 저장/진행률/제출, 방문이력(상태 확장·커서), 받은 알림함/읽음, 알림 선호도 저장, 병원 정보 조회.
- **마이그레이션**: `00010_*.sql`부터 순차. support 요청·문진 완료/ID·notification preferences/log·SMS 실패·알림 종류 설정·환자 확인 시각·멱등 키·consent·device_tokens를 논리 단위로 묶고 RLS/부분 unique/상태 전이를 명시한다. 상담봇 3-A의 `notification_log`·예약-티켓 FK와 충돌하지 않는지 확인한다.

## 다른 단계에 미치는 영향

- **2단계(직원용 웹)**: 마감 후 취소·변경은 전용 `/cancellation-requests` 대기열이 아니라 `/today`의 확인 필요 행·예약 캘린더 ⚠·상담 문의함의 공용 흐름을 쓴다(결정 #25로 전용 대기열 폐기). 가족 연결·해제·관계 수정 UI, 기본정보 수정(본인확인·변경 이력), 문자 실패 표식 표시, 알림 종류별 설정 편집, 제1문 「안내 보내기」·발송 결과 조회가 직원 웹에 필요.
- **4단계(상담봇)**: 섹션 13의 상담방·카드·late-flow·긴급 안내 계약을 소비.

## 이번 단계에서 다루지 않는 것 (4단계에서 다룸)

- AI 상담봇 관련 전체 기능(5장): 상담봇을 통한 예약, 진료과 선택 도움, 직원 이관 — 앱은 상담방 화면과 소비 계약만.
- 상담봇 대화 중 수집한 사전문진 내용의 저장 로직(도구 `사전문진_카드보내기`).
- "직원 상담 답변 도착" 알림(상담봇 이관 이후 발생).
