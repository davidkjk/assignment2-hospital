# 4단계: AI 상담봇 설계

> 근거 문서: `고객요구사항.txt` (특히 1.5, 5장, 6장)
> 이 문서는 전체 프로젝트를 5단계로 나눈 것 중 **4단계**의 설계입니다.
>
> 1. 기반: 인증/권한 + 예약·진료상태·수정이력 데이터 모델 (완료)
> 2. 직원용 웹 (React) (스펙 완료)
> 3. 환자 모바일 앱 (Flutter) (스펙·계획 완료)
> 4. **AI 상담봇 (이 문서)**
> 5. 통합 테스트 & 배포

## 범위와 핵심 결정

| 결정 사항 | 선택 | 이유 |
|---|---|---|
| 등장 위치 | 앱 `AI 상담` 메뉴 + 병원 홈페이지 웹 상담창 **둘 다** | 요구사항 5.1(모바일·웹 두 곳 모두 등장) 전체 구현 |
| 답변 근거 방식 | **RAG** (pgvector + OpenAI `text-embedding-3-small`) | 병원 안내자료가 실제 운영 중 수백 항목까지 늘어날 것을 가정해 검색 정확도를 미리 검증 |
| AI 프레임워크 | **LangChain** (LCEL 체인 + `RunnableBranch` 라우터 + `AgentExecutor`) | 질문 종류에 따라 서로 다른 처리 기술(단순 검색형 RAG / 구조화된 문진형 / 도구 실행형 에이전트)을 명시적으로 분기하기 위해 채택. 모델 호출은 `langchain-anthropic`으로 Claude Sonnet을 그대로 사용 |
| 질문 처리 라우팅 | 매 메시지마다 **① 응급 표현 검사(규칙 기반, 최우선) → ② 인계 감시(6가지 조건, 항상 동작) → ③ 라우터가 3갈래 중 하나로 분류**: 안내형(RAG 체인) / 진료과 추천형(문진 체인) / 행동형(에이전트 체인) | 요구사항 5.2(안내)·5.3(진료과 추천)·5.4(예약)·5.5(인계)가 원래 서로 다른 규칙을 가진 별개 기능인데, 하나의 에이전트에 다 맡기면 진단 금지·인계 조건 같은 안전장치가 "AI의 그때그때 판단"에만 의존하게 됨. 감시·분류를 코드 단계로 분리해 놓치는 경우를 구조적으로 줄임 |
| 대화 모델 | Claude Sonnet | 성능·비용 균형 |
| 직원 인계 | **티켓 방식** + 같은 대화창에서 직원 답변 (라이브 채팅 전용 장치는 미구현) | Supabase Realtime 재사용으로 실시간 반영은 확보 |
| 웹 상담창 사용자 | 기본 익명, 필요 시 **로그인/가입** (전화번호+비밀번호, 3단계와 동일 계정) | 요구사항 5.2/5.4의 "로그인한 환자" 조건을 웹에서도 충족 |
| 웹 가입 | 포함 — 채팅창이 아닌 **별도 페이지(모달)** 방식 | 좁은 채팅창 UX 회피, 앱 가입 화면 흐름 재사용 |
| 실제 예약 실행 | **봇의 도구가 아님** — 확인 카드의 버튼 → 3단계 예약 API 직행 | "봇이 몰래 예약하지 않는다"(5.4)를 구조로 보장 |
| 상담 내용 검토·수정·업그레이드 | 관리자 화면에 **5개 화면으로 이뤄진 사이클** — 미해결 질문 모아보기·오답 신고 처리함·상담 품질 리포트(검토) → 병원 안내자료 관리(수정) → 승인 시 자동 재임베딩(업그레이드) → 참고 예시 관리(누적). 상세는 섹션 4 "관리자 화면" 참고 | 상담봇 답변은 한 번 배포하고 끝이 아니라, 실제 오답·미해결 질문이 계속 쌓이는 것을 전제로 지속 개선 구조를 요구사항 3.8/3.9/3.10에서 이미 요구함 |

## 섹션 1: 전체 구조

```
[환자 앱 (Flutter)]   [병원 홈페이지 웹 상담창 (React)]
        │                     │
        └────────┬────────────┘
                 ▼
        [백엔드 API (FastAPI) — 상담봇 두뇌, LangChain 기반]
          ⓪ 응급 표현 검사 (규칙 기반 키워드, AI 호출 없이 즉시 판정 — 최우선)
             └─ 감지 시: 119/응급실 안내 후 종료 (아래 단계 전부 건너뜀)
          ① 인계 감시 (요구사항 5.5의 6가지 조건을 매 턴 검사 — 라우팅과 무관하게 항상 동작)
             └─ 감지 시: 인계 체인으로 강제 전환 (③의 어느 갈래에 있었든 중단)
          ② 라우터 (`RunnableBranch`): 질문을 3갈래로 분류
             ├─ 안내형 → RAG 체인 (pgvector 검색 → LCEL 프롬프트)
             ├─ 진료과 추천형 → 문진 체인 (구조화된 순차 질문, 진단 금지 가드레일 강화)
             └─ 행동형 → 에이전트 체인 (`AgentExecutor`, 도구 실행)
                 ▼
        [Supabase (Postgres + pgvector)]
          대화방·메시지·지식베이스·티켓·품질피드백 저장
                 ▼
        [직원 웹 상담 관리 화면 (React, 2단계 확장)]
```

- **장애 격리** (요구사항 6.4): 상담봇은 예약 시스템과 분리된 별도 기능. Claude/OpenAI 중단 시에도 예약·진료기록은 정상 동작. 봇 장애 시 상담창은 "문의 남기기"(봇 없이 티켓 생성)로 전환.
- **긴급 표현 대응** (5.3): 위 ⓪단계 — 규칙 기반이라 AI가 실수로 놓칠 위험이 없음. 심한 흉통·호흡곤란·의식 저하 등 긴급 표현 시 예약 진행을 멈추고 119/응급실 안내. 진단·약 추천·확정적 표현 금지. 긴급 판단을 완벽 보장한다고 표현하지 않음.
- **인계는 독립된 질문 유형이 아니라 감시 장치** (5.5): 답을 찾지 못함 / 의료진 판단 필요 / 환자가 👎 선택 / 예약정보-병원정보 불일치 / 불만·사고·개인정보·비용분쟁 / 같은 질문 반복 미해결 — 이 6가지는 라우터가 고른 갈래(②)와 무관하게 매 턴 별도로 검사하고, 걸리면 지금 진행 중이던 처리를 즉시 멈추고 인계로 전환한다. 에이전트의 "인계할지 말지 판단"에만 맡기지 않는 것이 핵심.
- **환자 인증**: 앱·웹 동일 — 전화번호+비밀번호 로그인, OTP는 가입·비밀번호 찾기 시에만 (3단계 스펙 그대로). 같은 Supabase Auth 계정이므로 앱/웹 어디서든 같은 환자로 인식.

## 섹션 2: 데이터 구조 (신규 테이블)

### `chat_conversations` — 상담방

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | UUID | 상담방 고유번호 |
| `patient_id` | UUID, null 허용 | 환자. 익명 웹 상담이면 null, 로그인 시 채워짐 |
| `anon_session_token` | 문자열, null 허용 | 익명 사용자 재방문용 세션 토큰 (브라우저 localStorage 보관) |
| `channel` | `app` / `web` | 상담 채널 |
| `status` | `bot` / `handed_over` / `closed` | 봇 응대중 / 직원 인계됨 / 종료 |
| `created_at` | 시각 | 시작 시각 |
| `last_message_at` | 시각 | 마지막 발언 시각 (목록 정렬용) |

### `chat_messages` — 메시지 (발언 1개 = 1행)

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | UUID | 메시지 고유번호 |
| `conversation_id` | UUID | 소속 상담방 |
| `sender` | `patient` / `bot` / `staff` | 발신 주체 |
| `staff_id` | UUID, null 허용 | 직원 발언 시 직원 |
| `content` | text | 내용 |
| `source_chunk_ids` | UUID[], null 허용 | 봇 답변의 근거 자료 조각 목록 (요구사항 5.6 근거 추적) |
| `message_type` | `text` / `slot_options` / `booking_confirm` / `booking_done` / `cancellation_confirm` / `questionnaire` | 일반 텍스트 / 시간 선택 카드 / 예약 확인 카드 / 예약 완료 카드 / 예약취소 확인 카드(A-5) / 사전문진 카드(A-1) |
| `route_taken` | `emergency` / `rag` / `department_guide` / `agent` / `handoff`, null 허용(직원·환자 발언은 null) | 봇 답변이 어느 갈래로 처리됐는지 기록 — 관리자가 라우팅이 잘 됐는지 확인하거나, 사후 품질 검토 시 갈래별로 필터링하는 데 사용 |
| `question_embedding` | vector(1536), null 허용 | `sender=patient` 메시지에만 저장되는 질문 임베딩. 답변 성공/실패와 무관하게 환자가 보낸 모든 질문에 채워진다 — "가장 많이 들어온 질문 TOP N" 통계(요구사항 3.10)용. `support_tickets.question_embedding`(답 못 찾은 질문만 대상)과는 별도 용도 |
| `created_at` | 시각 | 발신 시각 |

### `kb_documents` — 병원 안내자료 원본 (관리자 관리 단위)

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | UUID | 자료 고유번호 |
| `title` | 문자열 | 제목 (예: "주차 안내") |
| `category` | 문자열 | 분류 (진료시간/위치·주차/예약규칙/검사준비/**진료과·의사소개**/**자주묻는질문**/기타) |
| `content` | text | 본문 |
| `status` | `draft` / `approved` / `archived` | **approved만 검색 대상** |
| `is_restricted` | boolean, 기본 false | true면 상담봇이 이 내용을 근거로 답변을 새로 생성하지 않고, `content`를 그대로(수정 없이) 보여준다. 요구사항 3.8 "상담봇이 답하면 안 되는 내용"을 관리자가 직접 등록하는 방법 — 병원마다 다른 정책 문구(예: "정신과 상담은 전화로만 안내합니다")를 위한 것이며, 진단·처방 금지 같은 보편 규칙은 이미 각 체인의 하드코딩된 안전규칙(SAFETY_RULES 등)이 별도로 지킨다 |
| `created_by` / `approved_by` | UUID | 작성자 / 승인 관리자 |
| `updated_at` / `approved_at` | 시각 | 수정·승인 시각 |

### `kb_chunks` — 자료 조각 (RAG 검색 단위)

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | UUID | 조각 고유번호 |
| `document_id` | UUID | 원본 자료 |
| `chunk_index` | int | 원본 내 순서 |
| `content` | text | 조각 텍스트 (문단 단위) |
| `embedding` | vector(1536) | OpenAI 임베딩. pgvector 유사도 검색용 |

- 원본 승인·수정 시 해당 조각을 전부 삭제 후 재생성(재청킹+재임베딩). 원본-조각 불일치 방지.
- 원본/조각 분리 이유: 원본은 사람(관리자)의 관리 단위, 조각은 검색 정확도·비용을 위한 기계의 검색 단위.

### `kb_document_revisions` — 안내자료 수정이력 (요구사항 3.8)

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | UUID | 이력 고유번호 |
| `document_id` | UUID | 대상 자료 |
| `previous_title` / `previous_category` / `previous_content` | 문자열/문자열/text | **수정 직전** 상태의 스냅샷 |
| `changed_by` | UUID | 수정한 관리자 |
| `changed_at` | 시각 | 수정 시각 |

- `kb_documents`를 수정(`update_document`)할 때마다, 덮어쓰기 전 값을 이 테이블에 먼저 저장한다. 1단계에서 진료기록 수정에 쓴 `medical_record_revisions`와 같은 패턴("바뀌기 전 내용을 별도 테이블에 남기고, 원본은 최신 상태만 유지")을 안내자료에도 그대로 적용한 것이다.
- "이전 내용과 수정 이력도 남겨주세요"(3.8)라는 요구를 만족: 관리자 화면에서 자료별 과거 버전을 시간순으로 조회 가능(섹션 4).

### `support_tickets` — 직원 인계 티켓

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | UUID | 티켓 번호 (환자 안내용 접수번호 역할) |
| `conversation_id` | UUID | 원본 상담방 |
| `patient_id` | UUID, null 허용 | 로그인 환자 |
| `contact_name` / `contact_phone` | 문자열, null 허용 | 익명 사용자가 남긴 연락처 (SMS 알림용) |
| `summary_question` | text | 환자가 궁금해한 내용 |
| `summary_confirmed` | text | 상담봇이 확인한 정보 |
| `summary_guided` | text | 이미 안내한 내용 |
| `summary_unresolved` | text | 해결되지 않은 이유 |
| `summary_staff_todo` | text | 직원이 확인할 사항 |
| `reason` | `no_answer` / `medical_judgment` / `unhelpful` / `data_mismatch` / `complaint` / `repeated` / `late_cancellation` | 인계 사유 (요구사항 5.5). `late_cancellation`은 마감 후 취소 요청 접수 시 `예약취소_카드보내기` 도구가 생성(요구사항 4.3) — 나머지 6개와 달리 "인계 감시" 로직이 아니라 도구 실행이 직접 생성한다 |
| `status` | `pending` / `in_progress` / `answered` | **새 문의 / 처리 중 / 답변완료** (요구사항 3.9의 3단계 상태) |
| `assigned_staff_id` | UUID, null 허용 | 담당 직원 — `in_progress` 전환 시 배정, 의료진 판단이 필요하면 다른 직원(담당 의사 등)으로 재배정 가능 |
| `question_embedding` | vector(1536), null 허용 | `summary_question`의 임베딩 — "자주 들어오지만 답하지 못한 질문" 모아보기용 (요구사항 3.9/3.10). 임베딩 실패 시 null로 남고 클러스터링에서만 제외될 뿐 티켓 생성 자체는 막지 않음 |
| `created_at` / `answered_at` | 시각 | 접수·답변 시각 |

- `reason`의 6개 값(`late_cancellation` 제외)이 곧 "인계 감시" 로직이 매 턴 검사하는 6가지 조건이다(요구사항 5.5: 답을 찾지 못함/의료판단 필요/👎 선택/정보 불일치/불만·사고·개인정보·비용분쟁/반복 미해결). 라우터가 어느 갈래를 골랐는지와 무관하게 이 감시가 항상 함께 동작하며, 걸리면 진행 중이던 처리를 멈추고 이 테이블에 티켓을 생성한다. `late_cancellation`은 이 감시 로직이 아니라 `예약취소_카드보내기` 도구가 마감 후 취소 시 직접 생성하는 별도 경로다(요구사항 4.3) — 갈래(②)의 진행을 중단시키지 않고, 도구 실행 결과로서 티켓이 함께 만들어지는 차이가 있다.
- **티켓 처리 흐름과 재배정** (요구사항 3.9): 티켓은 생성 시 `pending`(새 문의, 미배정)으로 시작 → 직원이 티켓을 열람하면 `in_progress`(처리 중)로 전환되며 그 직원이 `assigned_staff_id`에 배정된다 → 접수 직원이 처리하다가 `reason=medical_judgment`처럼 의료진 판단이 필요하다고 판단되면, 본인이 임의로 답하지 않고 **다른 직원(담당 의사·관리자)에게 재배정**할 수 있다(`assigned_staff_id`만 교체, 상태는 `in_progress` 유지) → 답변을 남기면 `answered`로 종료. "누가 지금 이 티켓을 보고 있는가"가 항상 드러나므로 여러 직원이 같은 티켓에 동시에 손대는 것도 자연히 줄어든다.

### `qa_example_bank` — 챗봇 품질 개선 사이클의 축적 예시 (신규)

상담 내역을 관리자가 사후에 검토해서 남긴 교정이 "그 자리에서 한 번 고치고 끝"이 아니라 **앞으로의 답변 품질에 실제로 반영되도록** 만드는 테이블이다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | UUID | 예시 고유번호 |
| `source_feedback_id` | UUID | 근거가 된 `answer_feedback` (관리자가 `반영` 처리하며 `add_to_example_bank`를 체크한 것만 생성) |
| `question_text` | text | 환자의 원래 질문 |
| `corrected_answer_text` | text | 관리자가 승인한 올바른 답변 |
| `question_embedding` | vector(1536) | 질문 임베딩 — 이후 유사 질문이 들어오면 검색용 |
| `category` | 문자열 | `route_taken`과 동일한 갈래(안내형/진료과추천형/행동형) — 어느 체인의 프롬프트에 넣을지 구분 |
| `is_active` | boolean, 기본 true | 관리자가 더 이상 참고하지 않길 원하면 비활성화(삭제 대신 숨김 — 요구사항 6.3) |

- **작동 방식**: 챗봇이 답변을 생성하기 직전, 환자 질문과 유사한(임베딩 유사도 상위 1~2개) 활성 예시를 `qa_example_bank`에서 찾아 "참고할 올바른 답변 스타일" 형태로 프롬프트에 함께 넣는다. 즉 과거에 관리자가 고쳐준 사례가 쌓일수록, 비슷한 질문에 챗봇이 더 정확하게 답하게 된다.
- 오답신고를 KB 문서 자체 수정으로 반영하는 기존 흐름(`applied_document_id`)과는 별개로 동작한다 — 문서로 만들기엔 애매한 "말투·표현 교정"까지 이 테이블로 커버한다.

## 섹션 3: 대화 처리 흐름과 도구

### 메시지 처리 순서

1. 환자 메시지를 `chat_messages`에 저장
2. **⓪ 응급 표현 검사** (규칙 기반 키워드 매칭 — LangChain/모델 호출 이전에 코드가 직접 검사): 걸리면 119/응급실 안내 메시지를 `route_taken=emergency`로 저장하고 즉시 종료 (아래 단계 전부 건너뜀)
3. **① 인계 감시** (`support_tickets.reason`의 6개 조건을 매 턴 검사 — 라우팅 이전에, 라우팅과 무관하게 항상 동작): 걸리면 아래 "인계 체인"으로 즉시 전환하고 라우터(②)는 건너뜀
4. **② 라우터** (`RunnableBranch`): ⓪·①을 통과한 메시지만 분류 — 안내형 / 진료과 추천형 / 행동형
5. 분류된 갈래의 체인 실행 (아래 각 체인 설명)
6. 봇 답변을 `source_chunk_ids`, `route_taken`과 함께 저장 → Realtime으로 환자 화면 반영

### 갈래 ①: RAG 체인 — 안내형 (요구사항 5.2)

- 질문 임베딩 → pgvector로 `kb_chunks`에서 유사 조각 3~5개 검색(approved 자료만) → LCEL 프롬프트(검색 조각 + 질문)로 Claude 호출 → 답변
- **도구를 쓰지 않는다** — 순수 "검색 후 생성"이라 가장 빠르고 저렴
- 검색 1위 결과가 `is_restricted` 자료면 Claude를 호출하지 않고 그 자료의 `content`를 그대로 답으로 반환한다 — 관리자가 등록한 "답하면 안 되는 내용" 문구를 AI가 바꿔 말하지 않도록 보장 (요구사항 3.8)
- 처리 대상: 진료시간·휴진일, 진료과·의사 안내, 위치·주차, 대중교통, 예약 방법(절차), 예약/변경·취소 규칙, 검사 전 준비물, 병원 이용 안내 등 (요구사항 5.2의 9개 항목 중 정적 안내성 7개 — 나머지 2개 "현재 예약 확인"·"가능한 예약시간 조회"는 로그인·실시간 조회가 필요해 행동형 에이전트 체인의 도구가 처리, 아래 갈래③ 참고)
- **검색 실패 시 행동형 1회 재시도**: 검색된 조각의 유사도가 매우 낮으면(관련 자료를 못 찾은 것으로 판단) 인계로 넘기기 전에 **코드가 직접** 행동형(에이전트 체인)으로 한 번만 전환해 재시도한다. 라우터가 다시 분류하는 것이 아니라 하드코딩된 흐름이라 무한루프가 생기지 않는다. 행동형 체인이 이미 RAG 검색을 포함하는 상위호환 갈래이므로, 행동형에서 다시 안내형으로 되돌아가는 반대 방향 로직은 두지 않는다. 재시도에서도 답을 찾지 못하면 인계 감시(①)의 `no_answer` 조건으로 처리된다.
- **대기 순번은 도구화하지 않는다**: 실시간 대기 순번은 이미 앱에 표시되므로(요구사항 4.5) 중복 기능을 만들지 않는다. 관련 질문이 오면 "실시간 대기 순번은 앱에서 확인할 수 있습니다" 안내를 하는 KB 문서로 처리한다.

### 갈래 ②: 문진 체인 — 진료과 추천형 (요구사항 5.3)

- 자유 대화가 아니라 **정해진 순서의 구조화된 질문**을 순차로 진행: 불편한 증상 → 시작 시점 → 동반 증상 → (필요 시) 방문 목적
- 이 체인 전용 시스템 프롬프트에서 RAG 체인보다 안전 규칙을 더 강하게 명시: 병명 언급 금지, "~병입니다" 같은 확정적 표현 금지, 약·치료법 추천 금지
- 마지막 단계에서 `진료과의사_조회` 도구로 실제 운영 중인 진료과를 확인한 뒤, 가능한 진료과 1~2개를 안내하고 "최종 선택은 환자 확인"으로 마무리
- 대화 도중 응급 표현이 나오면 ⓪단계가 매 턴 먼저 검사하므로 이 체인이 별도로 처리할 필요 없음

### 갈래 ③: 에이전트 체인 — 행동형 (요구사항 5.4)

`AgentExecutor` + 도구 7개 (기존 6개에서 `직원에게_인계`는 "인계 감시" 로직으로 분리했고, `진료과의사_조회`는 문진 체인과 공유. `예약취소_카드보내기`·`사전문진_카드보내기` 신규 추가):

| 도구 | 하는 일 | 로그인 |
|---|---|---|
| `병원자료_추가검색` | 대화 중 새 주제로 지식베이스 재검색 | ✕ |
| `진료과의사_조회` | 운영 중 진료과, 의사, 진료 요일·시간, 휴진일을 실 DB에서 조회 (문진 체인과 공유) | ✕ |
| `예약가능시간_조회` | 실제 빈 시간 조회 (지어내기 차단) | ✕ |
| `내예약_확인` | 본인·가족(대리 등록된 환자 포함)의 현재 예약 조회 | ✅ |
| `예약제안_카드보내기` | 환자(본인 또는 가족)·진료과·의사·날짜·시간 확인 카드를 채팅에 표시 | ✅ |
| `예약취소_카드보내기` | 취소 대상 예약(본인·가족 공통) 확인 카드 표시, 마감 전후 자동 분기 | ✅ |
| `사전문진_카드보내기` | 사전문진 내용을 채팅 카드로 보여주고 저장·수정 | ✅ |

- **가족 도구 확장 원칙**: `내예약_확인`·`예약제안_카드보내기`·`예약취소_카드보내기` 3개 도구는 모두 로그인 계정 본인뿐 아니라 가족(대리 등록된 환자)까지 다룰 수 있다. 새 데이터 모델을 만들지 않고 1단계에서 이미 정의된 `patient_family_links`, `patient_owns()`, `account_patient_id`/`for_patient_id`를 그대로 재사용한다(정합성 검토 P0 R5-01, P2 R5-02 근거). 대상이 여러 명(본인+가족)일 수 있는 도구는 먼저 "누구의 예약인가요?"를 확인한 뒤 진행한다.

### 도구화 원칙과 KB 문서 작성 원칙

- **도구화 원칙**: 조회성 동작이나 "확인 버튼을 누르면 그대로 실행되는" 동작만 도구로 만든다. 개인정보를 새로 생성하는 일(회원가입, 가족 신규 등록), 본인이 아닌 타인의 정보를 다루는 일, 되돌리기 어려운 행동은 도구화하지 않고 앱/모달 화면으로 안내한다.
- **KB 문서 작성 원칙**: 이미 도구로 처리되고 있는 동작(예: 예약 확인, 예약 취소)에 대해서는 경쟁하는 안내 문서를 별도로 만들지 않는다. 같은 질문에 도구와 KB 문서가 동시에 답할 수 있으면 RAG가 도구 대신 KB 문서로 오답할 위험이 생기기 때문이다(도구가 존재하는 한 그 주제는 KB 문서의 서술 대상이 아니다).
  - **예외(하이브리드) — "진료과·의사소개" 카테고리**: `진료과의사_조회` 도구와 주제(진료과·의사)는 겹치지만 다루는 정보 종류가 다르다. **자주 바뀌는 실시간 값**(오늘 진료 여부, 남은 예약 슬롯, 스케줄 변경 등)은 지금처럼 도구가 DB를 그대로 조회해 답한다(변경 없음). **거의 안 바뀌는 소개성 정보**(의사 전공·경력·인사말, 진료과 소개 문구처럼 글로 쓰는 게 자연스러운 내용)만 이 카테고리로 KB에 등록해 관리자가 직접 작성·승인한다. 두 정보가 서로 다른 질문 의도(운영 현황 확인 vs 소개 읽기)에 답하므로 도구-KB 경쟁 문제가 생기지 않는다.

### `예약취소_카드보내기` — 마감 전후 자동 분기 (요구사항 4.3, 5.4)

- 환자(본인·가족 공통)가 취소하려는 예약을 확인 카드로 보여주고, `이 예약 취소` 버튼을 누르면 **Claude를 거치지 않고** 3단계 `cancel_appointment` API를 직행 호출한다(예약 실행과 동일한 패턴).
- `cancel_appointment`는 이미 마감 전/후 분기 로직을 갖고 있다(3단계 계획 Task 2) — 이 도구는 새 백엔드 로직을 만들지 않고 그대로 재사용한다.
  - **마감 전**: 즉시 취소 확정.
  - **마감 후**: `cancellation_requested_at`을 채워 취소 요청을 접수함과 **동시에**, 인계 티켓(`support_tickets`)을 생성한다. 사유는 신규 값 `late_cancellation`(아래 참고). 티켓 요약에는 대화에서 파악된 취소 사유 등 맥락을 담고, `summary_staff_todo`에는 "취소요청 대기열에서 승인/반려 처리 필요"를 명시한다. 채널(앱 취소 버튼 리다이렉트든, 웹 상담창이든)에 상관없이 같은 대기열(2단계 직원 웹, 요구사항 4.3)로 모인다.
- **환자 노출 문구 원칙**: 요구사항 원문은 "상담으로 연결"이지 "취소 요청 접수"가 아니다. 봇이 환자에게 "취소 요청이 접수/등록됐다"는 표현을 쓰면 "자동으로 곧 취소되겠지"라고 오해할 수 있어 금지한다. 반드시 "상담(직원 확인)으로 연결됐다"는 사실만 전달한다.
  - 예시: "상담으로 연결해 드렸습니다. 담당 직원이 내용을 확인한 후 안내해 드립니다(영업시간 외엔 다음 영업일)." (❌ "취소를 요청해 두었습니다", ❌ "취소 요청이 접수되었습니다")

### `사전문진_카드보내기` — 채팅 카드로 저장·수정 (요구사항 4.4)

- **호출 시점**: (a) 예약 신청(`create_booking`) 완료 시 코드가 무조건 1회 자동 호출(LLM의 자율 판단이 아니라 하드코딩 — 반복 호출·누락 방지), (b) 이후 환자가 "사전문진 확인/수정하고 싶어요" 등으로 요청하면 다른 대화 세션이어도 언제든 재호출(`for_patient_id`/`appointment_id` 기준 조회). 대상 예약이 여러 건(본인+가족)이면 가족 도구와 같은 패턴으로 먼저 "누구의 예약인가요?"를 확인한다.
- **수집 범위**: 문진 체인(진료과 추천형) 태그 여부와 무관하게 **대화 전체**에서 파악되는 증상·시작 시점·복용약·알레르기. 파악하지 못한 항목은 빈칸으로 두고 지어내지 않는다.
- **UI**: 신규 채팅 카드 컴포넌트 `QuestionnaireCard`(`예약제안_카드보내기`와 같은 패턴 — 채팅창 안에서 바로 입력 가능한 폼). 파악된 값 또는 기존 저장값이 각 필드에 미리 채워지고, 환자가 자유롭게 직접 고쳐 쓸 수 있다. 버튼: `저장`(누르면 즉시 반영, 앱·웹 채널 무관 동일 동작) / `나중에 할게요`(저장하지 않고 다음에 이어서).
- **로그인 필요**.
- **잠금 규칙**: 3단계 스펙의 "병원 도착 처리 전까지 자유롭게 수정 가능, 도착 이후엔 읽기 전용" 규칙이 이 도구에도 동일하게 적용된다 — 환자가 병원에 도착 처리된 뒤에는 이 도구도 저장을 거부한다(앱과 동일한 잠금 규칙, 우회 구멍 방지).
- **대체하는 이전 설계**: 기존 계획에 있던 문진 프리필 API(대화 중 `field_key` 태그가 붙은 메시지 앞뒤 1개씩만 보는 방식, 앱 사전문진 화면에서만 결과를 보여줄 수 있어 웹 상담창 전용 사용자는 사전문진을 아예 못 쓰던 방식, 예약 신청 시 1회성이라 이후 수정 경로가 없던 방식)는 이 도구로 완전히 대체된다.

### 예약 실행 (봇 권한 밖)

- 확인 카드의 `이 내용으로 예약` 버튼 → **Claude를 거치지 않고** 3단계 예약 API 직행
- 효과: 봇의 임의 예약이 구조적으로 불가능(5.4), 일반 예약과 동일한 중복 방지·상태 관리(6.1), 충돌 시 예약 API가 거절 → 봇이 다른 시간 재안내(5.4)
- 성공 시 예약번호 + `사전문진 작성하기` 버튼 표시(5.4)

### 인계 체인 — 감시(①)가 발동했을 때 실행

- 별도 LLM 호출로 요약 5항목(환자가 궁금해한 내용 / 상담봇이 확인한 정보 / 이미 안내한 내용 / 해결되지 않은 이유 / 직원이 확인할 사항) 작성 → `support_tickets` 생성(감지된 조건을 `reason`에 기록) → 상담방 `handed_over` 전환
- **기존 설계와의 차이**: 이전에는 에이전트가 대화 중 "지금 인계할지 말지"를 스스로 판단해서 도구를 선택하는 구조였다. 이제는 감시 로직이 6가지 조건 중 하나를 감지하면 **에이전트의 판단과 무관하게 무조건 실행**된다 — 놓치는 경우를 줄이기 위함

### 인계 이후 동작 규칙

- `handed_over` 상태에서는 봇이 응답하지 않음 (환자 메시지는 저장만)
- 티켓 상세와 환자 채팅방은 같은 `chat_messages`를 공유 — Realtime 덕에 양쪽이 접속 중이면 사실상 실시간 대화 가능 (상주 배정·입력중 표시 등 라이브 채팅 전용 장치만 미구현)
- 직원이 `답변 완료` 처리 → 티켓 닫힘, 상담방은 봇 응대 상태로 복귀
- 업무시간 밖: "다음 영업일 답변" 안내 후 티켓은 `pending`으로 대기. 익명 웹 사용자는 인계 시 이름·연락처를 받아 답변 시 SMS 알림. 앱 사용자는 푸시 알림
- 익명 웹 대화 이어보기: `anon_session_token`으로 같은 브라우저 재방문 시 복원. 다른 기기는 미지원(봇이 앱 로그인 안내)

## 섹션 4: 화면 구성

### 환자 앱 `AI 상담` (Flutter)

- 채팅 화면: 말풍선 + 봇 답변에 `👍/👎` — 👎는 인계 감시가 즉시 감지해 인계로 전환 (요구사항 5.5 "도움이 되지 않았다고 선택")
- 카드형 메시지: 시간 선택지 / 예약 확인(주요 버튼 1개) / 예약 완료(예약번호+사전문진 버튼)
- 문진 체인(진료과 추천형) 진행 중에는 상단에 "진단이 아니라 진료과 안내입니다" 고정 배너 표시 — 요구사항 7절 "지금 무엇을 안내하고 있는지 알 수 있어야" + 5.3 안전 원칙을 화면에서도 드러냄
- 봇 답변 말풍선은 내용 성격에 따라 시각적으로 구분한다: **의료적 내용**(검사 전 준비사항, 문진 관련 안내 등)은 별도 아이콘·배경색으로, **일반 병원 안내**(진료시간·위치·주차 등)는 기본 스타일로 표시 — 요구사항 7절 "의료 안내와 일반 병원 안내를 시각적으로 구분"
- 인계(`handed_over`) 이후에는 채팅 상단에 티켓 상태 배지를 표시한다: **대기중**(`pending`)/**직원 확인중**(`in_progress`)/**답변완료**(`answered`) — `support_tickets.status`를 그대로 노출(요구사항 "상담봇" 절 "직원 연결 상태 표시"). 배지 아래에 예상 답변시간 문구를 함께 표시: 업무시간 내엔 "곧 확인 후 답변드리겠습니다", 업무시간 외엔 "다음 영업일에 답변드립니다"
- 이전 상담 목록, 직원 답변 푸시 알림 → 해당 방으로 이동

### 웹 상담창 (React)

- 홈페이지 우하단 말풍선 버튼 → 채팅 위젯. 기능은 앱과 동일(같은 API)
- 로그인 필요 시점(내 예약 확인·예약 실행)에 로그인/가입 모달 — 가입은 별도 페이지 방식(전화번호 OTP 본인확인 → 비밀번호·기본정보 → 완료), 3단계 백엔드·Twilio 재사용
- 익명 인계 시 이름·연락처 입력 폼
- 앱과 동일하게 답변 성격별 시각 구분, 인계 후 티켓 상태 배지·예상 답변시간 문구를 적용한다(위 앱 항목과 동일 규칙, 같은 API 응답 재사용)

### 직원 웹 — 상담 관리 (2단계 확장)

- 문의 티켓함: **새 문의(`pending`) / 처리 중(`in_progress`) / 답변완료(`answered`)** 3개 탭, 각 탭 접수순 정렬, Realtime 갱신
- 티켓 상세: 요약 5항목 + 원본 대화 전체 + 답변 입력 (답변은 환자 채팅방에 직원 말풍선으로 전송 + 알림). 열람 시 자동으로 `pending → in_progress` 전환 + 본인 배정. `medical_judgment` 사유 티켓에는 "담당 의사에게 전달" 버튼(직원 선택 후 재배정 — 요구사항 3.9)이 강조 표시됨
- 전체 상담 기록: 앱·웹 통합 목록(`channel`, `route_taken` 필터) — 요구사항 5.1 "같은 상담 관리 화면". 봇 답변 클릭 시 근거 자료 표시(5.6)
- 오답 신고: 봇 답변에 `잘못된 답변` 표시 + 올바른 안내 작성(`source=realtime_report`로 저장) + "향후 유사 질문 예시로도 사용" 체크박스
- **2단계가 이 단계로 넘긴 항목 마무리**(정합성 검토에서 발견 — 2단계 스펙 "다루지 않는 것"에 "4단계에서 다룸"으로만 적혀 있었고 실제로 여기에 반영되지 않았던 것을 보완):
  - 환자 상세화면(`/patients/:id`)에 "상담 문의" 섹션 추가 — 해당 환자의 `support_tickets` 목록(질문·안내내용·상태) 표시 (요구사항 3.5)
  - "오늘의 현황"의 "확인 필요 상담 문의" 카드를 `pending` 상태 티켓 건수에 실제로 연결 (요구사항 3.2, 2단계에서는 항상 0건 고정이었음)

### 관리자 화면 (2단계 관리자 메뉴 확장)

#### 상담봇 콘텐츠 검토·수정·업그레이드 사이클

아래 다섯 화면이 하나의 사이클을 이룬다: **②③④에서 답변 품질 문제를 찾아 검토 → ①에서 안내자료를 고침(수정) → [승인]하는 순간 자동 재임베딩으로 상담봇 답변에 바로 반영(업그레이드)**. ⑤는 이 사이클에서 나온 교정 결과를 상담봇이 계속 참고하도록 쌓아두는 저장소다.

| # | 화면 | 역할 | 무엇을 새로 만드는가 |
|---|---|---|---|
| ① | **병원 안내자료 관리** | 안내문 목록·작성·수정 | 기존 화면 확장 |
| ② | **미해결 질문 모아보기** | 답 못 찾은 질문을 유사도로 자동 클러스터링 | 신규 |
| ③ | **오답 신고 처리함** | 환자 신고(👎)로 들어온 오답을 반영/반려 | 기존 화면 확장 |
| ④ | **상담 품질 리포트** | 신고 여부와 무관하게 대화를 열어 정기 점검 | 신규 |
| ⑤ | **참고 예시 관리** | 교정된 질문·답변 예시 저장소 관리 | 기존 화면 확장 |
| ⑥ | **전체 질문 순위** | 답변 성공 여부와 무관하게 가장 많이 들어온 질문 TOP N 집계 | 신규 |

**① 병원 안내자료 관리**
목록(분류·상태 필터), 작성/수정(**"상담봇이 직접 답변하지 않고 이 문구만 그대로 보여줍니다" 체크박스** 포함 — 요구사항 3.8 "답하면 안 되는 내용", `is_restricted`), `승인`(승인 시 자동 청킹+임베딩), 자료별 `수정이력 보기`(`kb_document_revisions`를 시간 역순으로 표시 — 요구사항 3.8)

**② 미해결 질문 모아보기** (신규 — 요구사항 3.9/3.10)
기간을 선택하면 그 기간의 `no_answer`/`repeated` 티켓들을 질문 임베딩 유사도로 자동으로 묶어, "대표 질문 문구 + N건" 형태로 개수 내림차순 표시. 예: "야간 진료 하나요?" 계열 5건, "주차장 몇 시까지?" 계열 2건. 화면에는 "비슷한 질문끼리 자동으로 묶어본 결과이며 실제로 다른 질문이 섞여 있을 수 있다"는 안내를 함께 표시 — 클러스터링은 확정적 분류가 아니라 관리자가 눈으로 훑어볼 **보조 정리 도구**이기 때문. 행을 열면 묶인 티켓 목록을 확인할 수 있어, "이 질문을 안내자료에 추가해야겠다"는 판단을 돕는다. `medical_judgment`/`unhelpful`/`data_mismatch`/`complaint` 사유는 "답을 못 찾은 질문"이 아니라 별도 성격의 인계이므로 집계 대상에서 제외

**③ 오답 신고 처리함**
`반영`(자료 수정 연결, `add_to_example_bank` 체크 시 `qa_example_bank`에도 등록) / `반려`

**④ 상담 품질 리포트** (신규 — 품질 개선 사이클)
기간을 선택하면 해당 기간 상담 목록(`route_taken`·인계 여부·오답신고 여부 표시)이 뜨고, 신고 여부와 무관하게 아무 대화나 열어 그 자리에서 교정을 남길 수 있음(`source=periodic_review`로 저장, 이후 처리는 오답 신고와 동일하게 `반영`/`반려`)

**⑤ 참고 예시 관리**
`qa_example_bank` 목록(질문·교정답변·갈래 표시), 더 이상 참고하지 않을 예시는 `비활성화`(삭제 대신 숨김)

**⑥ 전체 질문 순위** (신규 — 요구사항 3.10)
기간을 선택하면 그 기간 `chat_messages`(`sender=patient`) 전체를 대상으로 질문 임베딩 유사도로 자동 클러스터링해 "대표 질문 문구 + N건"을 건수 내림차순으로 표시한다. ②(미해결 질문 모아보기)와 클러스터링 방식은 동일하지만, ②는 `no_answer`/`repeated`로 인계된 질문만 대상인 데 비해 ⑥은 **답변 성공 여부와 무관하게 모든 질문**을 대상으로 한다는 점이 다르다. 답을 잘한 질문이라도 반복해서 많이 들어오면 여기서 드러나며, 이 결과를 보고 관리자가 "자주묻는질문" KB 카테고리(아래 섹션 2 참고)에 안내문을 직접 등록하는 흐름으로 이어진다.

#### 그 외 관리자 화면

- 상담봇 처리 현황(1.4): 기간별 상담 수(앱/웹), 갈래별 분포(안내형/진료과추천형/행동형/인계), 인계 건수·사유 분포, 오답 신고 수. `/admin/stats`(2단계)와 동일한 상호작용 패턴을 적용한다: **CSV 다운로드** 버튼으로 확인한 기간의 통계를 내려받을 수 있고, 각 숫자 카드를 클릭하면 해당 항목의 상세 목록(예: 인계 건수 클릭 → 해당 티켓 목록)으로 이동한다(시나리오10 대조 결과 반영)

## 섹션 5: 오류 처리·보안·테스트

### 오류 처리 (6.4)

- AI 장애 시 예약·진료기록 무영향(구조 분리). 상담창은 한글 안내 + 문의 남기기(봇 없이 티켓 생성)
- 개발자용 오류문 노출 금지 — 전부 한글 안내로 변환
- 메시지 전송 상태 표시, 실패 시 재전송 버튼 (실패를 성공처럼 보이지 않게)
- 상담봇 오류는 시간·기능과 함께 기록, 관리자 확인 가능 (기존 오류 기록 방식 재사용)

### 보안 (5.6, 6.5)

- RLS: 상담방·메시지는 본인(또는 익명 토큰 소유자)만, 티켓·전체 기록은 직원만, KB 승인은 관리자만
- 봇 접근 제한: 전체 환자·진료기록 조회 도구를 주지 않음 — `내예약_확인`은 본인 것만 (서버 강제 + RLS 이중)
- API 키(Claude/OpenAI/Twilio)는 서버 환경변수에만. 웹 상담창도 반드시 백엔드 경유
- 익명 웹 사용자 시간당 메시지 수 제한 (rate limiting, 비용 남용 방지)
- 테스트는 가짜 환자·가짜 자료만 사용

### 테스트

- 자동 테스트 (Claude는 모킹): 승인 자료만 검색 / 수정 시 재임베딩 / 도구별 권한 규칙 / 인계 요약 5항목 생성·인계 후 봇 침묵 / 확인 카드→예약 성공·충돌 재안내
- **티켓 처리 흐름(3.9)**: 티켓 열람 시 `pending→in_progress` 자동 전환 + 배정 확인 / 재배정(`assigned_staff_id` 교체, 상태는 `in_progress` 유지) / 답변 시 `answered` 전환
- **KB 수정이력(3.8)**: 자료 수정 시 수정 전 내용이 `kb_document_revisions`에 그대로 남는지, 관리자 화면에서 시간순으로 조회되는지 확인
- **미해결 질문 클러스터링(3.9/3.10)**: 유사한 질문 여러 건이 한 그룹으로 묶이는지, 무관한 질문은 분리되는지, `medical_judgment` 등 다른 인계 사유는 집계에서 빠지는지 확인
- **전체 질문 순위(3.10)**: 환자 메시지 저장 시 답변 성공/실패와 무관하게 `question_embedding`이 채워지는지, 답을 잘한 질문도 미해결 질문과 별개로 순위에 집계되는지 확인
- **응급 표현 검사(⓪)**: 규칙 기반이므로 골든 문구 목록 전체가 100% 걸리는지 검증(확률적 판단이 아니라 결정적 필터라 "일부만 통과"는 실패로 간주)
- **인계 감시(①) 6가지 조건**: `no_answer`/`medical_judgment`/`unhelpful`(👎)/`data_mismatch`/`complaint`/`repeated` 각각을 유발하는 대화를 만들어 실제로 감지·인계되는지 6개 케이스 전부 개별 테스트
- **라우터(②) 분류 정확도**: 안내형/진료과추천형/행동형 예시 질문 세트로 분류가 의도한 갈래로 가는지 확인. 애매한 질문은 안전하게 행동형(도구 있는 쪽)으로 가는지도 확인
- **RAG 품질 평가**: 골든 질문 세트 30~50개(질문→정답 자료 매핑)로 검색 적중률 측정. 청크 크기 실험 포함 — 검색 정확도를 좌우하는 핵심 실험
- **품질 개선 사이클 검증**: `qa_example_bank`에 교정 예시를 등록한 뒤, 같은 질문을 다시 물었을 때 프롬프트에 해당 예시가 포함되고 답변이 교정 내용을 반영하는지 확인
- **RAG 실패 시 행동형 재시도**: 유사도가 매우 낮은 질문을 넣어 인계로 바로 가지 않고 행동형으로 1회 전환되는지, 재시도에도 실패하면 `no_answer`로 인계되는지, 무한루프가 없는지 확인
- **가족 도구 3종**: `내예약_확인`/`예약제안_카드보내기`/`예약취소_카드보내기`를 가족 대상으로 호출해 `patient_family_links` 범위 밖 환자는 조회·예약·취소되지 않는지, 대상이 여러 명일 때 먼저 "누구의 예약인가요"를 확인하는지 검증
- **`예약취소_카드보내기` 마감 전후 분기**: 마감 전 호출 시 즉시 취소 확정(티켓 미생성), 마감 후 호출 시 `cancellation_requested_at` 기록과 `late_cancellation` 인계 티켓 생성이 함께 일어나는지, 환자에게 "취소 요청 접수" 문구가 절대 노출되지 않고 "상담 연결" 문구만 쓰이는지 확인
- **`사전문진_카드보내기`**: 예약 신청 완료 시 자동 1회 호출되는지 / 이후 재요청 시 다른 세션에서도 재호출되는지 / 기존 저장값이 프리필되는지 / 환자가 직접 고쳐서 저장하면 반영되는지 / 병원 도착 처리 후에는 저장이 거부되는지(잠금 규칙) 확인
- 손 테스트: 긴급 표현→119 안내, 진단 요구→거절+진료과 안내, 야간 인계→익일 답변→알림 확인
