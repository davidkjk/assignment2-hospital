# 4단계: AI 상담봇 설계

> 근거 문서: `고객요구사항.txt` (특히 1.5, 5장, 6장)
> 이 문서는 전체 프로젝트를 5단계로 나눈 것 중 **4단계**의 설계입니다.
>
> 1. 기반: 인증/권한 + 예약·진료상태·수정이력 데이터 모델 (완료)
> 2. 직원용 웹 (React) (스펙 완료)
> 3. 환자 모바일 앱 (Flutter) (스펙·계획 완료)
> 4. **AI 상담봇 (이 문서)**
> 5. 통합 테스트 & 배포

## 범위와 핵심 결정

| 결정 사항 | 선택 | 이유 |
|---|---|---|
| 등장 위치 | 앱 `AI 상담` 메뉴 + 병원 홈페이지 웹 상담창 **둘 다** | 요구사항 5.1(모바일·웹 두 곳 모두 등장) 전체 구현 |
| 답변 근거 방식 | **RAG** (pgvector + OpenAI `text-embedding-3-small`) | 병원 안내자료가 실제 운영 중 수백 항목까지 늘어날 것을 가정해 검색 정확도를 미리 검증 |
| AI 프레임워크 | **LangChain** (LCEL 체인 + `RunnableBranch` 라우터 + `AgentExecutor`) | 질문 종류에 따라 서로 다른 처리 기술(단순 검색형 RAG / 구조화된 문진형 / 도구 실행형 에이전트)을 명시적으로 분기하기 위해 채택. 모델 호출은 `langchain-anthropic`으로 Claude Sonnet을 그대로 사용 |
| 질문 처리 라우팅 | 매 메시지마다 **① 응급 표현 검사(규칙 기반, 최우선) → ② 인계 감시(6가지 조건, 항상 동작) → ③ 라우터가 3갈래 중 하나로 분류**: 안내형(RAG 체인) / 진료과 추천형(문진 체인) / 행동형(에이전트 체인) | 요구사항 5.2(안내)·5.3(진료과 추천)·5.4(예약)·5.5(인계)가 원래 서로 다른 규칙을 가진 별개 기능인데, 하나의 에이전트에 다 맡기면 진단 금지·인계 조건 같은 안전장치가 "AI의 그때그때 판단"에만 의존하게 됨. 감시·분류를 코드 단계로 분리해 놓치는 경우를 구조적으로 줄임 |
| 대화 모델 | Claude Sonnet | 성능·비용 균형 |
| 직원 인계 | **티켓 방식** + 같은 대화창에서 직원 답변 (라이브 채팅 전용 장치는 미구현) | Supabase Realtime 재사용으로 실시간 반영은 확보 |
| 웹 상담창 사용자 | 기본 익명, 필요 시 **로그인/가입** (전화번호+비밀번호, 3단계와 동일 계정) | 요구사항 5.2/5.4의 "로그인한 환자" 조건을 웹에서도 충족 |
| 웹 가입 | 포함 — 채팅창이 아닌 **별도 페이지(모달)** 방식 | 좁은 채팅창 UX 회피, 앱 가입 화면 흐름 재사용 |
| 실제 예약 실행 | **봇의 도구가 아님** — 확인 카드의 버튼 → 3단계 예약 API 직행 | "봇이 몰래 예약하지 않는다"(5.4)를 구조로 보장 |

## 섹션 1: 전체 구조

```
[환자 앱 (Flutter)]   [병원 홈페이지 웹 상담창 (React)]
        │                     │
        └────────┬────────────┘
                 ▼
        [백엔드 API (FastAPI) — 상담봇 두뇌, LangChain 기반]
          ⓪ 응급 표현 검사 (규칙 기반 키워드, AI 호출 없이 즉시 판정 — 최우선)
             └─ 감지 시: 119/응급실 안내 후 종료 (아래 단계 전부 건너뜀)
          ① 인계 감시 (요구사항 5.5의 6가지 조건을 매 턴 검사 — 라우팅과 무관하게 항상 동작)
             └─ 감지 시: 인계 체인으로 강제 전환 (③의 어느 갈래에 있었든 중단)
          ② 라우터 (`RunnableBranch`): 질문을 3갈래로 분류
             ├─ 안내형 → RAG 체인 (pgvector 검색 → LCEL 프롬프트)
             ├─ 진료과 추천형 → 문진 체인 (구조화된 순차 질문, 진단 금지 가드레일 강화)
             └─ 행동형 → 에이전트 체인 (`AgentExecutor`, 도구 실행)
                 ▼
        [Supabase (Postgres + pgvector)]
          대화방·메시지·지식베이스·티켓·품질피드백 저장
                 ▼
        [직원 웹 상담 관리 화면 (React, 2단계 확장)]
```

- **장애 격리** (요구사항 6.4): 상담봇은 예약 시스템과 분리된 별도 기능. Claude/OpenAI 중단 시에도 예약·진료기록은 정상 동작. 봇 장애 시 상담창은 "문의 남기기"(봇 없이 티켓 생성)로 전환.
- **긴급 표현 대응** (5.3): 위 ⓪단계 — 규칙 기반이라 AI가 실수로 놓칠 위험이 없음. 심한 흉통·호흡곤란·의식 저하 등 긴급 표현 시 예약 진행을 멈추고 119/응급실 안내. 진단·약 추천·확정적 표현 금지. 긴급 판단을 완벽 보장한다고 표현하지 않음.
- **인계는 독립된 질문 유형이 아니라 감시 장치** (5.5): 답을 찾지 못함 / 의료진 판단 필요 / 환자가 👎 선택 / 예약정보-병원정보 불일치 / 불만·사고·개인정보·비용분쟁 / 같은 질문 반복 미해결 — 이 6가지는 라우터가 고른 갈래(②)와 무관하게 매 턴 별도로 검사하고, 걸리면 지금 진행 중이던 처리를 즉시 멈추고 인계로 전환한다. 에이전트의 "인계할지 말지 판단"에만 맡기지 않는 것이 핵심.
- **환자 인증**: 앱·웹 동일 — 전화번호+비밀번호 로그인, OTP는 가입·비밀번호 찾기 시에만 (3단계 스펙 그대로). 같은 Supabase Auth 계정이므로 앱/웹 어디서든 같은 환자로 인식.

| 컬럼 | 타입 | 설명 |

| `id` | UUID | 조각 고유번호 |

### `kb_document_revisions` — 안내자료 수정이력 (요구사항 3.8)

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | UUID | 이력 고유번호 |
| `document_id` | UUID | 대상 자료 |
| `previous_title` / `previous_category` / `previous_content` | 문자열/문자열/text | **수정 직전** 상태의 스냅샷 |
| `changed_by` | UUID | 수정한 관리자 |
| `changed_at` | 시각 | 수정 시각 |

- `kb_documents`를 수정(`update_document`)할 때마다, 덮어쓰기 전 값을 이 테이블에 먼저 저장한다. 1단계에서 진료기록 수정에 쓴 `medical_record_revisions`와 같은 패턴("바뀌기 전 내용을 별도 테이블에 남기고, 원본은 최신 상태만 유지")을 안내자료에도 그대로 적용한 것이다.
- "이전 내용과 수정 이력도 남겨주세요"(3.8)라는 요구를 만족: 관리자 화면에서 자료별 과거 버전을 시간순으로 조회 가능(섹션 4).

### `support_tickets` — 직원 인계 티켓

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | UUID | 티켓 번호 (환자 안내용 접수번호 역할) |
| `conversation_id` | UUID | 원본 상담방 |
| `patient_id` | UUID, null 허용 | 로그인 환자 |
| `contact_name` / `contact_phone` | 문자열, null 허용 | 익명 사용자가 남긴 연락처 (SMS 알림용) |
| `summary_question` | text | 환자가 궁금해한 내용 |
| `summary_confirmed` | text | 상담봇이 확인한 정보 |
| `summary_guided` | text | 이미 안내한 내용 |
| `summary_unresolved` | text | 해결되지 않은 이유 |
| `summary_staff_todo` | text | 직원이 확인할 사항 |
| `reason` | `no_answer` / `medical_judgment` / `unhelpful` / `data_mismatch` / `complaint` / `repeated` | 인계 사유 (요구사항 5.5) |
| `status` | `pending` / `in_progress` / `answered` | **새 문의 / 처리 중 / 답변완료** (요구사항 3.9의 3단계 상태) |
| `assigned_staff_id` | UUID, null 허용 | 담당 직원 — `in_progress` 전환 시 배정, 의료진 판단이 필요하면 다른 직원(담당 의사 등)으로 재배정 가능 |
| `question_embedding` | vector(1536), null 허용 | `summary_question`의 임베딩 — "자주 들어오지만 답하지 못한 질문" 모아보기용 (요구사항 3.9/3.10). 임베딩 실패 시 null로 남고 클러스터링에서만 제외될 뿐 티켓 생성 자체는 막지 않음 |
| `created_at` / `answered_at` | 시각 | 접수·답변 시각 |

- `reason`의 6개 값이 곧 "인계 감시" 로직이 매 턴 검사하는 6가지 조건이다(요구사항 5.5: 답을 찾지 못함/의료판단 필요/👎 선택/정보 불일치/불만·사고·개인정보·비용분쟁/반복 미해결). 라우터가 어느 갈래를 골랐는지와 무관하게 이 감시가 항상 함께 동작하며, 걸리면 진행 중이던 처리를 멈추고 이 테이블에 티켓을 생성한다.
- **티켓 처리 흐름과 재배정** (요구사항 3.9): 티켓은 생성 시 `pending`(새 문의, 미배정)으로 시작 → 직원이 티켓을 열람하면 `in_progress`(처리 중)로 전환되며 그 직원이 `assigned_staff_id`에 배정된다 → 접수 직원이 처리하다가 `reason=medical_judgment`처럼 의료진 판단이 필요하다고 판단되면, 본인이 임의로 답하지 않고 **다른 직원(담당 의사·관리자)에게 재배정**할 수 있다(`assigned_staff_id`만 교체, 상태는 `in_progress` 유지) → 답변을 남기면 `answered`로 종료. "누가 지금 이 티켓을 보고 있는가"가 항상 드러나므로 여러 직원이 같은 티켓에 동시에 손대는 것도 자연히 줄어든다.

### `qa_example_bank` — 챗봇 품질 개선 사이클의 축적 예시 (신규)

상담 내역을 관리자가 사후에 검토해서 남긴 교정이 "그 자리에서 한 번 고치고 끝"이 아니라 **앞으로의 답변 품질에 실제로 반영되도록** 만드는 테이블이다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | UUID | 예시 고유번호 |
| `source_feedback_id` | UUID | 근거가 된 `answer_feedback` (관리자가 `반영` 처리하며 `add_to_example_bank`를 체크한 것만 생성) |
| `question_text` | text | 환자의 원래 질문 |
| `corrected_answer_text` | text | 관리자가 승인한 올바른 답변 |
| `question_embedding` | vector(1536) | 질문 임베딩 — 이후 유사 질문이 들어오면 검색용 |
| `category` | 문자열 | `route_taken`과 동일한 갈래(안내형/진료과추천형/행동형) — 어느 체인의 프롬프트에 넣을지 구분 |
| `is_active` | boolean, 기본 true | 관리자가 더 이상 참고하지 않길 원하면 비활성화(삭제 대신 숨김 — 요구사항 6.3) |
| `created_at` | 시각 | 등록 시각 |

- **작동 방식**: 챗봇이 답변을 생성하기 직전, 환자 질문과 유사한(임베딩 유사도 상위 1~2개) 활성 예시를 `qa_example_bank`에서 찾아 "참고할 올바른 답변 스타일" 형태로 프롬프트에 함께 넣는다. 즉 과거에 관리자가 고쳐준 사례가 쌓일수록, 비슷한 질문에 챗봇이 더 정확하게 답하게 된다.
- 오답신고를 KB 문서 자체 수정으로 반영하는 기존 흐름(`applied_document_id`)과는 별개로 동작한다 — 문서로 만들기엔 애매한 "말투·표현 교정"까지 이 테이블로 커버한다.

## 섹션 3: 대화 처리 흐름과 도구

### 메시지 처리 순서

1. 환자 메시지를 `chat_messages`에 저장
2. **⓪ 응급 표현 검사** (규칙 기반 키워드 매칭 — LangChain/모델 호출 이전에 코드가 직접 검사): 걸리면 119/응급실 안내 메시지를 `route_taken=emergency`로 저장하고 즉시 종료 (아래 단계 전부 건너뜀)
3. **① 인계 감시** (`support_tickets.reason`의 6개 조건을 매 턴 검사 — 라우팅 이전에, 라우팅과 무관하게 항상 동작): 걸리면 아래 "인계 체인"으로 즉시 전환하고 라우터(②)는 건너뜀
4. **② 라우터** (`RunnableBranch`): ⓪·①을 통과한 메시지만 분류 — 안내형 / 진료과 추천형 / 행동형
5. 분류된 갈래의 체인 실행 (아래 각 체인 설명)
6. 봇 답변을 `source_chunk_ids`, `route_taken`과 함께 저장 → Realtime으로 환자 화면 반영

### 갈래 ①: RAG 체인 — 안내형 (요구사항 5.2)

- 질문 임베딩 → pgvector로 `kb_chunks`에서 유사 조각 3~5개 검색(approved 자료만) → LCEL 프롬프트(검색 조각 + 질문)로 Claude 호출 → 답변
- **도구를 쓰지 않는다** — 순수 "검색 후 생성"이라 가장 빠르고 저렴
- 처리 대상: 진료시간·휴진일, 위치·주차, 예약/변경·취소 규칙, 검사 전 준비사항 등

### 갈래 ②: 문진 체인 — 진료과 추천형 (요구사항 5.3)

- 자유 대화가 아니라 **정해진 순서의 구조화된 질문**을 순차로 진행: 불편한 증상 → 시작 시점 → 동반 증상 → (필요 시) 방문 목적
- 이 체인 전용 시스템 프롬프트에서 RAG 체인보다 안전 규칙을 더 강하게 명시: 병명 언급 금지, "~병입니다" 같은 확정적 표현 금지, 약·치료법 추천 금지
- 마지막 단계에서 `진료과의사_조회` 도구로 실제 운영 중인 진료과를 확인한 뒤, 가능한 진료과 1~2개를 안내하고 "최종 선택은 환자 확인"으로 마무리
- 대화 도중 응급 표현이 나오면 ⓪단계가 매 턴 먼저 검사하므로 이 체인이 별도로 처리할 필요 없음

### 갈래 ③: 에이전트 체인 — 행동형 (요구사항 5.4)

`AgentExecutor` + 도구 5개 (기존 6개에서 `직원에게_인계`는 "인계 감시" 로직으로 분리했고, `진료과의사_조회`는 문진 체인과 공유):

| 도구 | 하는 일 | 로그인 |
|---|---|---|
| `병원자료_추가검색` | 대화 중 새 주제로 지식베이스 재검색 | ✕ |
| `진료과의사_조회` | 운영 중 진료과, 의사, 진료 요일·시간, 휴진일을 실 DB에서 조회 (문진 체인과 공유) | ✕ |
| `예약가능시간_조회` | 실제 빈 시간 조회 (지어내기 차단) | ✕ |
| `내예약_확인` | 본인의 현재 예약만 조회 | ✅ |
| `예약제안_카드보내기` | 환자·진료과·의사·날짜·시간 확인 카드를 채팅에 표시 | ✅ |

### 예약 실행 (봇 권한 밖)

- 확인 카드의 `이 내용으로 예약` 버튼 → **Claude를 거치지 않고** 3단계 예약 API 직행
- 효과: 봇의 임의 예약이 구조적으로 불가능(5.4), 일반 예약과 동일한 중복 방지·상태 관리(6.1), 충돌 시 예약 API가 거절 → 봇이 다른 시간 재안내(5.4)
- 성공 시 예약번호 + `사전문진 작성하기` 버튼 표시(5.4)

### 인계 체인 — 감시(①)가 발동했을 때 실행

- 별도 LLM 호출로 요약 5항목(환자가 궁금해한 내용 / 상담봇이 확인한 정보 / 이미 안내한 내용 / 해결되지 않은 이유 / 직원이 확인할 사항) 작성 → `support_tickets` 생성(감지된 조건을 `reason`에 기록) → 상담방 `handed_over` 전환
- **기존 설계와의 차이**: 이전에는 에이전트가 대화 중 "지금 인계할지 말지"를 스스로 판단해서 도구를 선택하는 구조였다. 이제는 감시 로직이 6가지 조건 중 하나를 감지하면 **에이전트의 판단과 무관하게 무조건 실행**된다 — 놓치는 경우를 줄이기 위함

### 인계 이후 동작 규칙

- `handed_over` 상태에서는 봇이 응답하지 않음 (환자 메시지는 저장만)
- 티켓 상세와 환자 채팅방은 같은 `chat_messages`를 공유 — Realtime 덕에 양쪽이 접속 중이면 사실상 실시간 대화 가능 (상주 배정·입력중 표시 등 라이브 채팅 전용 장치만 미구현)
- 직원이 `답변 완료` 처리 → 티켓 닫힘, 상담방은 봇 응대 상태로 복귀
- 업무시간 밖: "다음 영업일 답변" 안내 후 티켓은 `pending`으로 대기. 익명 웹 사용자는 인계 시 이름·연락처를 받아 답변 시 SMS 알림. 앱 사용자는 푸시 알림
- 익명 웹 대화 이어보기: `anon_session_token`으로 같은 브라우저 재방문 시 복원. 다른 기기는 미지원(봇이 앱 로그인 안내)

## 섹션 4: 화면 구성

### 환자 앱 `AI 상담` (Flutter)

- 채팅 화면: 말풍선 + 봇 답변에 `👍/👎` — 👎는 인계 감시가 즉시 감지해 인계로 전환 (요구사항 5.5 "도움이 되지 않았다고 선택")
- 카드형 메시지: 시간 선택지 / 예약 확인(주요 버튼 1개) / 예약 완료(예약번호+사전문진 버튼)
- 문진 체인(진료과 추천형) 진행 중에는 상단에 "진단이 아니라 진료과 안내입니다" 고정 배너 표시 — 요구사항 7절 "지금 무엇을 안내하고 있는지 알 수 있어야" + 5.3 안전 원칙을 화면에서도 드러냄
- 이전 상담 목록, 직원 답변 푸시 알림 → 해당 방으로 이동

### 웹 상담창 (React)

- 홈페이지 우하단 말풍선 버튼 → 채팅 위젯. 기능은 앱과 동일(같은 API)
- 로그인 필요 시점(내 예약 확인·예약 실행)에 로그인/가입 모달 — 가입은 별도 페이지 방식(전화번호 OTP 본인확인 → 비밀번호·기본정보 → 완료), 3단계 백엔드·Twilio 재사용
- 익명 인계 시 이름·연락처 입력 폼

### 직원 웹 — 상담 관리 (2단계 확장)

- 문의 티켓함: **새 문의(`pending`) / 처리 중(`in_progress`) / 답변완료(`answered`)** 3개 탭, 각 탭 접수순 정렬, Realtime 갱신
- 티켓 상세: 요약 5항목 + 원본 대화 전체 + 답변 입력 (답변은 환자 채팅방에 직원 말풍선으로 전송 + 알림). 열람 시 자동으로 `pending → in_progress` 전환 + 본인 배정. `medical_judgment` 사유 티켓에는 "담당 의사에게 전달" 버튼(직원 선택 후 재배정 — 요구사항 3.9)이 강조 표시됨
- 전체 상담 기록: 앱·웹 통합 목록(`channel`, `route_taken` 필터) — 요구사항 5.1 "같은 상담 관리 화면". 봇 답변 클릭 시 근거 자료 표시(5.6)
- 오답 신고: 봇 답변에 `잘못된 답변` 표시 + 올바른 안내 작성(`source=realtime_report`로 저장) + "향후 유사 질문 예시로도 사용" 체크박스

### 관리자 화면 (2단계 관리자 메뉴 확장)

- 병원 안내자료 관리: 목록(분류·상태 필터), 작성/수정, `승인`(승인 시 자동 청킹+임베딩), 자료별 `수정이력 보기`(`kb_document_revisions`를 시간 역순으로 표시 — 요구사항 3.8)
- **미해결 질문 모아보기(신규 — 요구사항 3.9/3.10)**: 기간을 선택하면 그 기간의 `no_answer`/`repeated` 티켓들을 질문 임베딩 유사도로 자동으로 묶어, "대표 질문 문구 + N건" 형태로 개수 내림차순 표시. 예: "야간 진료 하나요?" 계열 5건, "주차장 몇 시까지?" 계열 2건. 화면에는 "비슷한 질문끼리 자동으로 묶어본 결과이며 실제로 다른 질문이 섞여 있을 수 있다"는 안내를 함께 표시 — 클러스터링은 확정적 분류가 아니라 관리자가 눈으로 훑어볼 **보조 정리 도구**이기 때문. 행을 열면 묶인 티켓 목록을 확인할 수 있어, "이 질문을 안내자료에 추가해야겠다"는 판단을 돕는다. `medical_judgment`/`unhelpful`/`data_mismatch`/`complaint` 사유는 "답을 못 찾은 질문"이 아니라 별도 성격의 인계이므로 집계 대상에서 제외
- 오답 신고 처리함: `반영`(자료 수정 연결, `add_to_example_bank` 체크 시 `qa_example_bank`에도 등록) / `반려`
- **상담 품질 리포트 (신규 — 품질 개선 사이클)**: 기간을 선택하면 해당 기간 상담 목록(`route_taken`·인계 여부·오답신고 여부 표시)이 뜨고, 신고 여부와 무관하게 아무 대화나 열어 그 자리에서 교정을 남길 수 있음(`source=periodic_review`로 저장, 이후 처리는 오답 신고와 동일하게 `반영`/`반려`)
- 참고 예시 관리: `qa_example_bank` 목록(질문·교정답변·갈래 표시), 더 이상 참고하지 않을 예시는 `비활성화`(삭제 대신 숨김)
- 상담봇 처리 현황(1.4): 기간별 상담 수(앱/웹), 갈래별 분포(안내형/진료과추천형/행동형/인계), 인계 건수·사유 분포, 오답 신고 수 — 숫자 카드 수준

## 섹션 5: 오류 처리·보안·테스트

### 오류 처리 (6.4)

- AI 장애 시 예약·진료기록 무영향(구조 분리). 상담창은 한글 안내 + 문의 남기기(봇 없이 티켓 생성)
- 개발자용 오류문 노출 금지 — 전부 한글 안내로 변환
- 메시지 전송 상태 표시, 실패 시 재전송 버튼 (실패를 성공처럼 보이지 않게)
- 상담봇 오류는 시간·기능과 함께 기록, 관리자 확인 가능 (기존 오류 기록 방식 재사용)

### 보안 (5.6, 6.5)

- RLS: 상담방·메시지는 본인(또는 익명 토큰 소유자)만, 티켓·전체 기록은 직원만, KB 승인은 관리자만
- 봇 접근 제한: 전체 환자·진료기록 조회 도구를 주지 않음 — `내예약_확인`은 본인 것만 (서버 강제 + RLS 이중)
- API 키(Claude/OpenAI/Twilio)는 서버 환경변수에만. 웹 상담창도 반드시 백엔드 경유
- 익명 웹 사용자 시간당 메시지 수 제한 (rate limiting, 비용 남용 방지)
- 테스트는 가짜 환자·가짜 자료만 사용

### 테스트

- 자동 테스트 (Claude는 모킹): 승인 자료만 검색 / 수정 시 재임베딩 / 도구별 권한 규칙 / 인계 요약 5항목 생성·인계 후 봇 침묵 / 확인 카드→예약 성공·충돌 재안내
- **티켓 처리 흐름(3.9)**: 티켓 열람 시 `pending→in_progress` 자동 전환 + 배정 확인 / 재배정(`assigned_staff_id` 교체, 상태는 `in_progress` 유지) / 답변 시 `answered` 전환
- **KB 수정이력(3.8)**: 자료 수정 시 수정 전 내용이 `kb_document_revisions`에 그대로 남는지, 관리자 화면에서 시간순으로 조회되는지 확인
- **미해결 질문 클러스터링(3.9/3.10)**: 유사한 질문 여러 건이 한 그룹으로 묶이는지, 무관한 질문은 분리되는지, `medical_judgment` 등 다른 인계 사유는 집계에서 빠지는지 확인
- **응급 표현 검사(⓪)**: 규칙 기반이므로 골든 문구 목록 전체가 100% 걸리는지 검증(확률적 판단이 아니라 결정적 필터라 "일부만 통과"는 실패로 간주)
- **인계 감시(①) 6가지 조건**: `no_answer`/`medical_judgment`/`unhelpful`(👎)/`data_mismatch`/`complaint`/`repeated` 각각을 유발하는 대화를 만들어 실제로 감지·인계되는지 6개 케이스 전부 개별 테스트
- **라우터(②) 분류 정확도**: 안내형/진료과추천형/행동형 예시 질문 세트로 분류가 의도한 갈래로 가는지 확인. 애매한 질문은 안전하게 행동형(도구 있는 쪽)으로 가는지도 확인
- **RAG 품질 평가**: 골든 질문 세트 30~50개(질문→정답 자료 매핑)로 검색 적중률 측정. 청크 크기 실험 포함 — 검색 정확도를 좌우하는 핵심 실험
- **품질 개선 사이클 검증**: `qa_example_bank`에 교정 예시를 등록한 뒤, 같은 질문을 다시 물었을 때 프롬프트에 해당 예시가 포함되고 답변이 교정 내용을 반영하는지 확인
- 손 테스트: 긴급 표현→119 안내, 진단 요구→거절+진료과 안내, 야간 인계→익일 답변→알림 확인
