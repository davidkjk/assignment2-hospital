## 0. 확정 전제 (2026-08-26)

> ⭐ **개정 II (2026-08-26, 비용·감시 정정 — 아래 상세와 충돌 시 이 배너 우선)**
> 1. **노력 전부 `high`.** xhigh/max 폐기(§실행플랜 §4). 비가역(21·26)은 코디 리뷰를 더 꼼꼼히 볼 뿐 별도 적대리뷰 에이전트 없음.
> 2. **워커 모델 = 1M 유지(`claude-b/claude-opus-4-8[1m]`), 단 각 워커는 200k 안(≈20%)에서 끝낸다.** 200k 밑에선 1M/200k 비용 동일하고, 1M은 넘쳐도 안 죽고 할증만(200k 모델은 벽) → **1M + "200k 근처면 GREEN에서 멈추고 보고"**가 정답. 비용은 창 크기가 아니라 **실제 읽은 토큰**으로 정해진다 → 적게 읽을수록 싸고 품질도 좋다.
> 3. **병렬 축소 → 한 번에 하나씩.** 단일 Max 계정에선 병렬이 처리량을 못 늘리고(코디 리뷰가 직렬 병목), **중간 한도컷 시 두 워커 다 콜드 재읽기 낭비**가 난다. 하나씩 하면 한도가 바닥나도 **커밋 직후(깨끗한 지점)**에서 멈춘다.
> 4. **컷오프 복구 = 같은 워커 재개(`send_agent_prompt`), 재생성 금지.** 재개는 캐시 reload(식었어도 전액 1회)뿐, 재생성은 "다시 읽고 다시 추론"까지라 더 비싸다. (예외: 워커가 거의 아무것도 안 한 시점 컷오프면 재생성이 더 깨끗.)
> 5. **provider 문자열은 `claude-b/claude-opus-4-8[1m]`**(계정=claude-b Max), 기계작업 `claude-b/claude-sonnet-5`. (옛 `claude/...` 표기 정정.)

- **모델 = 거의 전부 Opus 4.8** (`claude-opus-4-8[1m]`, 문맥 100만). 이 프로젝트는 여러 정본(behaviors·결정로그·플랜)을 **맞춰 조합**해야 구현이 되는데, 낮은 모델은 그 조합을 다 못 챙긴다(데모 실측). 백엔드든 프론트든 구현·검증은 Opus 4.8.
  - **Sonnet 5**(`claude-sonnet-5`)는 **판단이 거의 없는 기계적 일에만** — 대량 파일검색·죽은참조 스캔·단순 반복 치환 등. 노력(thinkingOptionId)은 지휘자가 태스크별로 고른다.
  - **테스트는 따로 떼지 않는다.** TDD 테스트는 구현 워커(Opus 4.8) 브리프 **안에서 같이** 쓴다. 테스트만 별도 워커로 떼면 콜드스타트·브리프 비용이 더 커 손해다.
- **계정 상황(중요)**: 사용자는 **Max 계정 1개 + Pro 계정 1개**. paseo에서 `claude-b` = **Max(이 창, 지금 유일하게 가용)**, `claude-c` = **Pro(세션 리밋, 내일 저녁 이후 가용)**.
  - **오늘**: Max 한 계정으로 지휘 1창 + 병렬 워커 몇 개. paseo는 한 계정 안에서 여러 에이전트를 동시에 띄운다(Orca가 하던 것과 동일). **다만 창을 늘려도 쿼터는 안 늘고 Max 사용량 창을 모두가 나눠 쓴다** — 병렬은 ①문맥 분리 ②창 죽음 대비를 위한 것이지 한도 뻥튀기가 아니다. 그래서 심박·한도 감시가 필요하다.
  - **내일 저녁 이후**: Pro(`claude-c`)가 열리면 진짜 2계정(지휘 바통 + 쿼터 여유)으로 확장.
- **문서는 통째로 안 읽는다**: 플랜(수십만 바이트)·behaviors(6000줄+)를 다 읽으면 지휘 창 문맥이 터진다. **spec-index(색인)로 어느 규칙ID·결정번호를 볼지 찾고 그 줄범위만** 편다.
- **1단계 기반은 초록불**. 백엔드 테스트 통과 위에 직원웹을 얹는다. 로컬 supabase 필요(`supabase status`, DB_URL `…54322`).

## 1. 왜 별도 창(paseo 워커)인가

| | 이 세션 안의 서브에이전트(Agent 도구) | **paseo 워커(`create_agent`)** |
|---|---|---|
| 실행 위치 | 내 세션 **안** | **paseo 데몬이 관리하는 별도 에이전트** |
| 세션 끊기면 | 미커밋 작업 **소실** | 내가 죽어도 **계속 돌고, 커밋된 건 생존** |
| 내 문맥 | 워커 작업이 **내 context를 태움** | 워커는 **자기 context**, 내 창은 안 참 |
| 완료 통지 | — | `notifyOnFinish`로 **끝나면 알림이 옴**(폴링 불필요) |

→ **무거운 다파일 구현·긴 작업 = paseo 워커.** 이 세션 안의 `Agent` 서브에이전트는 **몇 초 내 끝나는 읽기 전용 검색 팬아웃**에만(사용자가 명시 요청할 때).

**하드 규칙**:
- **모델은 브리프 보낸 뒤 안 바꾼다.** 태스크 난도가 예상보다 높아지면 가장 가까운 GREEN에서 멈추고, 남은 범위를 새 워커로 다시 배정한다(같은 창 임의 상향 금지).
- **자기 코드는 자기가 리뷰하지 않는다** — 별도 fresh 창이 본다(자기 코드는 눈이 먼다).
- **독립 검증 PASS 전 완료·병합 금지.** findings가 오면 구현 워커가 고치고 새 리뷰를 다시 받는다.
- **비가역·보안·동시성·개인정보·DB 고위험**(예: 환자 병합 Task 21·26)은 Opus 4.8 max로 구현 + **별도 fresh Opus 4.8 high 적대리뷰**(반례 찾기)를 붙인다.

## 3. paseo 스폰 메커니즘 (정확한 인자)

> paseo MCP 도구. 상세는 `paseo` 스킬. **한 태스크 = 새 워커 하나**(기존 워커에 새 일 얹지 않음 = "항상 클리어하고 새로 시작").

**격리 워크트리 만들기**(병렬·코드 변경 — 서로 다른 체크아웃):
```
create_workspace(isolation="worktree", mode="branch-off",
                 baseBranch="merge/design-integration", branchName="t<N>-<slug>")
  → workspaceId
```
- 같은 체크아웃에서 파일만 나눠 병렬할 수도 있으나, worktree 격리가 충돌 위험이 없어 기본이다.
- ⚠️ 격리 워크트리엔 `.venv`·`node_modules` 없음 → 브리프에 **`python -m venv .venv && .venv/bin/pip install -r backend/requirements.txt` / `cd frontend && npm install` 먼저**를 반드시 넣는다.
- ⚠️ **DB는 공유다**(로컬 supabase 하나). 워크트리를 나눠도 DB는 하나 → 워커 `supabase db reset` 절대 금지(남의 데이터 날림).

**워커 띄우기**:
```
create_agent(
  title="T<N> <slug>",
  provider="claude/claude-opus-4-8[1m]",        # 기계작업만 claude/claude-sonnet-5
  workspaceId=<위 workspaceId>,                  # 생략하면 현재 워크스페이스
  settings={ modeId: "acceptEdits",              # 자율이면 bypassPermissions(신중히)
             thinkingOptionId: "high" },         # off/low/medium/high/xhigh/max/ultracode
  labels=["task-<N>","worker"],
  initialPrompt="<자체완결 브리프 — §5>",
  notifyOnFinish=true )
  → agentId
```
- **후속 지시**: `send_agent_prompt(agentId, prompt)` — 단, **같은 태스크의 이어가기에만**. 새 태스크는 새 `create_agent`.
- **모델·노력 바꾸기**: `update_agent(agentId, settings={ model, thinkingOptionId })` — 원칙상 태스크 중엔 안 바꾼다.
- **끄기**: `archive_agent(agentId)`(실행 중이면 중단).
- **컷오프 재개(개정 II)**: 워커가 한도로 도중에 끊기면 **archive 하지 말고**, 리셋 후 같은 agentId에 `send_agent_prompt(agentId, "이어서 계속")`로 **재개**한다(콜드 재읽기 낭비 회피). 단 산출물이 거의 없던 초기 컷오프면 재생성이 더 깨끗.
- **완료 대기**: 폴링(`list_agents`/`get_agent_status`) 금지. `notifyOnFinish` 알림이 온다. 알림 오면 **①산출물 파일 ②git diff ③보고절** 세 겹으로 완료를 판정한다(신호 하나만 믿지 않는다).

## 4. 컨텍스트 40/50 상한 + 지휘 바통 (사용자 하드 규칙)

> **목적**: 최대 창을 끝까지 채우지 않고 품질 좋은 앞 구간만 쓴다. 대화창은 휘발성 작업대이고, `git`·이 문서·`HANDOFF.md`·`STAFF-WEB-EXECUTION-PLAN.md` 진행 로그가 영속 기억이다.
> **측정 명령**: Claude Code는 **`/context`**(Codex의 `/status` 아님). 사용률 = `Tokens N / 1M`의 퍼센트, 또는 `100 − Free space%`.

### A. 강제 게이트

| `/context` 사용률 | 상태 | 허용 동작 |
|---|---|---|
| `0~39%` | GREEN | 태스크 착수·진행. 플랜은 해당 절·가리킨 규칙만 읽는다. |
| `40~49%` | HANDOFF | 새 태스크·큰 문서·새 dispatch 금지. 현재 태스크를 안전한 GREEN/커밋까지 닫고 인계 준비만. |
| `50%+` | STOP | 절대 상한. 구현·리뷰·탐색 중단. 상태 저장·실행 중 워커 회수·바통 인계만. |

각 태스크 순서: 해당 `## Task N` 절 + 규칙 ID만 읽음 → 구현·리뷰·focused 검증·커밋 → 심박 갱신.
⭐ **지휘 창은 자기 `/context`를 스스로 못 읽는다**(`/context`는 사용자 CLI 명령이라 자기에게 보내면 이번 턴 뒤에야 실행되고 밖에서 읽어줄 주체가 없다). 그래서:
- **자가측정 대체 = 감시 창이 잰다(개정 II).** 감시 창(코덱스/STANDBY)이 **몇 태스크마다** 지휘 창에 `send_agent_prompt(coordAgentId, "/context")`를 보내고 그 출력의 %를 읽어(`get_agent_status`의 lastMessage 또는 `capture_terminal`) 40% 넘으면 지휘 창에 교대 신호. 숫자 하나 읽는 일이라 코덱스도 신뢰 가능(브리프 저작과 다름).
- **감시 창이 없으면**, 지휘 창은 보수적으로 「많이 읽었다」 싶으면 미리 §4-B 자가 교대(fresh 클로드 코디 기동, 브리프=`HANDOFF.md`).
- **워커도 200k(≈20%) 안에서 끝낸다**(브리프에 명시) — 넘칠 것 같으면 가장 가까운 GREEN에서 멈추고 남은 범위 보고.

### B. 바통 교대 (단일 계정에서도 성립)

두 지휘자가 동시에 지휘하면 안 된다. **ACTIVE만** 태스크 생성·dispatch·병합·커밋한다.

- **바통 시점** = 태스크/웨이브 경계 **이며 활성 dispatch가 0**인 때.
- **자기는 자기를 못 비운다.** 40~50%에 닿으면 상태를 파일에 남기고 **fresh 지휘 창**에 넘긴다. paseo에서 fresh 지휘 창은:
  - **오늘(단일 Max)**: 이 창이 50%에 닿으면 상태를 `HANDOFF.md`·진행 로그에 남기고, **`create_agent`로 fresh Opus 4.8 지휘 에이전트**를 띄워 아래 인계 캡슐을 `initialPrompt`로 준다. 그 에이전트가 새 ACTIVE가 되어 워커를 이어 스폰한다. 이 창은 dispatch·커밋을 즉시 멈춘다.
  - **내일 이후(2계정)**: claude-c STANDBY가 대기하다 ACK 후 이어받는다.
- **인계 캡슐 최소 필드**:
```
ownerEpoch: <N>          # 매 교대마다 +1
currentTask: <완료한 Task>
nextAction: <다음 한 가지>
head: <commit hash>
dirtyFiles: <없음 또는 정확한 목록>
activeDispatches: 0
tests: <명령 + 결과>
decisions: <미결로 스스로 판단한 것 또는 없음>
context: <old 종료%, new 시작%>
```
- 새 창은 **이 플레이북 → `STAFF-WEB-EXECUTION-PLAN.md` → `HANDOFF.md` 최상단 → 해당 Task 절** 순으로만 읽는다. 이전 대화 전체를 다시 주입하지 않는다.

1. **코디가 스스로 잰다·스스로 게이트한다**(검증 2026-08-26: 코디가 `get_agent_status(자기ID).lastUsage.contextWindowUsedTokens ÷ contextWindowMaxTokens`로 자기 %를 직접 읽음. `/context` 슬래시 불필요). ⭐ **왜 코디가 재나**: 외부 감시는 코디의 안전 경계를 모른다 — 코디는 워커를 띄우고 결과를 기다릴 때도 `idle`이라, 감시가 그때 클리어하면 **작업 중인데 날려버린다**(사용자 지적 2026-08-26). 코디만 「지금 안전한가」를 안다.
2. **폐루프(코디 주도)**: ACTIVE 코디는 **태스크마다** 「구현·검증·커밋 → HANDOFF 심박 갱신 → **커밋 직후(=워커 없음·트리 클린 안전경계)에 자기 %를 잰다**」. **<40%=바로 다음 태스크**(코덱스 불필요). **≥40%=핸드오프(아래 3)**.
3. **⭐ 핸드오프 = 제자리 `/clear`, 코디가 직접·명시 요청**: ≥40%면 코디가 ①HANDOFF를 fresh-read 가능하게 완결(+심박에 `CLEAR-REQUESTED` 백업표식) ②**일회용 코덱스 창을 직접 스폰**해 지시를 통째로 넘긴다: `create_agent(provider="codex/gpt-5.6-luna", cwd=위, initialPrompt="너는 일회용 클리어 실행기다. 지휘 코디 <coordId>가 안전 경계에서 클리어를 요청했고 곧 idle이 된다. ①get_agent_status(<coordId>)로 idle 확인(아니면 20~30초 뒤 재확인) ②send_agent_prompt(<coordId>,'/clear') ③이어서 send_agent_prompt(<coordId>,'너는 병원 직원웹 지휘 코디다(클리어됨). HANDOFF.md 최상단→IMPL-ORCHESTRATION-PLAYBOOK.md §5→STAFF-WEB-EXECUTION-PLAN.md §9·§4 읽고 이어서 진행하라') ④한 줄 보고 후 종료. ⛔ 코드·파일 수정 금지.")` ③idle. ⭐ **재점화 프롬프트를 요청에 함께 실어** 클리어 후 방치를 막는다. `/clear`는 같은 agentId·새 세션·usage 0로 리셋(검증). **코덱스가 클리어 실행기**인 이유: 코디는 자기를 못 비운다. **왜 직접 스폰**: 즉시·명시적·재점화 보장(공용 30분 스케줄 `366642db`의 표식-클리어는 **백업**으로만; run_schedule_once는 즉시 실행이나 직접 스폰이 더 튼튼). 코디 창 하나 영구 유지·주기적 비움, 상태 원본=HANDOFF·git·§9. ⛔ **「fresh 코디 창 매번 스폰」 폐기**(트리 깊어짐). 새 코디 `create_agent`는 창이 **진짜 죽었을 때만** 최후수단(감시 §3).
4. **⚠️ 워커 스폰 provider는 반드시 `claude-b/claude-opus-4-8[1m]`**(교훈: epoch3 `3bb4d2f7`가 워커를 provider `claude`(잘못)로 만들어 4회 즉사 → 은퇴. 성공 워커는 전부 `claude-b`. **OAuth·계보 문제가 아니라 provider 문자열 오류였다.**) 코디로 세우기 전 첫 스폰으로 확인. **HANDOFF는 ACTIVE 한 창만 편집**(동시편집 충돌 방지).

### A. 매 사이클 심박 (활성 창이 남긴다)

ACTIVE는 태스크 시작·GREEN 커밋·종료 때 **`HANDOFF.md` 최상단 한 줄**을 갱신한다:
```
심박: 2026-08-26 17:20 KST · epoch 3 · ACTIVE 지휘 · Task 4 GREEN · ctx 31% · head abc1234
```
- 심박은 "결과"가 아니라 **지금 누가 지휘하고 마지막 안전 체크포인트가 어디인지**다. 결정 상세를 HANDOFF에 복사하지 않는다.

### B. 워커 생존/완료 감시

- 워커 완료 = paseo **`notifyOnFinish` 알림**으로 온다. 폴링하지 않는다.
- 워커가 오래 조용하면 알림을 기다리되, 필요 시 `get_agent_status(agentId)` 1회로 확인한다(keepalive 프롬프트 금지).

### C. 지휘 창 생존 감시 (2계정 모드)

- STANDBY가 60분마다 `HANDOFF.md` 심박 시각만 본다(`/watch-on`·`/watch-tick`·`/watch-off` 명령). 심박이 60분 넘게 낡고 활성 창이 응답 불가면 §4-B 복구로 이어받는다. **애매하면 이어받지 않는다**(살아 있는데 뺏는 게 더 나쁘다).
- **오늘(단일 Max 계정)에도 STANDBY 지휘 창을 하나 더 띄울 수 있다**(`create_agent`, 쿼터는 ACTIVE와 공유). STANDBY가 watch-*로 감시하다 40~50%에서 이어받는다. STANDBY를 안 띄운다면, 이 창이 스스로 45~50% 전에 §4-B로 fresh 지휘 창에 넘기고, 무인 장기 실행은 `ScheduleWakeup`(이 하네스) 또는 paseo `create_heartbeat`로 재개 시점을 건다.

### ⭐ 코덱스 감시-되살림 창 (개정 II, 2026-08-26 — 단일 Max 계정의 핵심 안전장치)

**왜 코덱스인가**: 우리 병목은 컨텍스트가 아니라 **한도(quota)**다. **같은 Max 계정의 STANDBY는 한도가 터지면 같이 죽어** 못 되살린다. 코덱스는 **다른 계정(OpenAI)**이라 클로드 한도가 죽어도 살아 있어, **리셋을 기다렸다 지휘를 되살릴 수 있는 유일한 창**이다. 그리고 감시는 토큰을 거의 안 태운다.

**코덱스 감시 창이 하는 것 (「재고 · 알리고 · 켜기」만 — 코디를 대신하지 않는다)**:
1. **컨텍스트 측정**: 몇 태스크마다(또는 N분마다) 지휘 창에 `send_agent_prompt(coordId, "/context")` → 출력 % 읽기 → **40% 넘으면** 지휘 창에 "HANDOFF 쓰고 교대해라" 신호(또는 텔레그램).
2. **심박 감시·되살리기 (⭐ 기존 우선, 새 창 최후 — 2026-08-26 정정)**: `HANDOFF.md` 최상단 심박이 60분 넘게 낡으면 바로 새 창을 만들지 않는다. 순서:
   - ① `get_agent_status(coordId)` — **running이면 오탐**(작업 중 심박 갱신 잊음), 되살리지도 알리지도 마라. **idle이면** `send_agent_prompt(coordId, "심박 낡음, 살아있으면 심박 갱신하고 이어가라")`로 **먼저 되살린다**(살아있는 코디를 두고 새 창 만들면 중복·낭비). 무응답/closed일 때만 ②.
   - ② **새 클로드 지휘 창**(`create_agent`, claude-b) 기동 — 단 **한도창이 아닐 때만**.
   - **한도컷 구분**: 심박 줄에 「Max 한도컷·리셋 <시각>」이 있으면 — **리셋 전엔 claude-b가 다 막혀 `create_agent`·`send_agent_prompt` 모두 실패**하니 **되살리지 말고 대기**(알림 1회). **리셋 후**에야 ①→② 되살리기. (감시자는 codex라 그 자신은 claude-b 한도와 무관 = 그래서 되살릴 수 있다.)
3. ⛔ **브리프를 절대 스스로 쓰지 않는다** — 새 지휘 창의 브리프는 항상 `HANDOFF.md`(파일). 코덱스는 "그 파일 읽고 복구해라" 한 줄만 준다. (코덱스 산출물 불신 — 감시·트리거 전용.)
- 세운 뒤 **1회 실측**: 코덱스가 지휘 창 `/context` 출력을 깔끔히 읽는지 확인(안 되면 `capture_terminal` 방식으로 조정).
- 설정: 코덱스 agent를 `create_agent(provider="codex/...")`로 띄우고, 주기 기상은 paseo `create_schedule`/`create_heartbeat` 또는 코덱스 자체 루프. 알림은 `.claude/orchestration/notify.sh`.
- **텔레그램은 "막혔을 때만" 확인**한다(§E). 상시 폴링은 리소스·토큰을 축내므로 하지 않는다. 평소 사용자 실시간 창구는 paseo 앱이다.

### D. 세션 한도 소진 대응

- 한도에 닿으면 **새 창으로 우회하지 않는다**(같은 계정 공유). GREEN/커밋·`HANDOFF.md`·진행 로그·paseo 워커 상태를 저장하고 **reset까지 대기**한다.
- ⭐ **한도컷 시 심박 관례(2026-08-26 신설)**: 한도컷을 만나면 지휘 창이 (아직 응답 가능하면) `HANDOFF.md` 최상단 심박 줄에 **「Max 한도컷·리셋 <시각>」을 반드시 적는다.** 이게 코덱스 감시자 §C.2의 「리셋 전 대기 / 리셋 후 되살리기」 판단 입력이다. 워커가 한도로 죽으면 리셋 후 `send_agent_prompt(workerId, "이어서 계속")`로 재개(§4 컷오프 재개). 실사례: 2026-08-26 Task 13b 워커가 프론트 작성 중 한도컷 → 리셋(7:30pm 밴쿠버) 후 같은 워커 재개로 손실 없이 마무리.
- **Pro(claude-c)는 내일 저녁 이후 가용** — 그 전엔 Max 하나로만 돈다. Max가 소진되면 대기.
- 무한 실행이 아니라 **중단 가능한 장기 루프**다. 한도 reset·paseo 장애·사용자 결정·외부 승인·같은 실패 3회는 반드시 멈추거나 대기하는 조건이다.

### E. 사용자 알림 채널 (텔레그램 — "손대야 하는 것" 전용)

무인 실행 중 사용자에게 닿는 창구는 둘로 **역할을 가른다**:

| 채널 | 언제 | 비고 |
|---|---|---|
| **paseo 앱 알림** | 워커 완료 등 루틴(제가 다음 단계로 넘어가려 받는 신호) | 사용자는 폰에서 이 루틴 알림을 음소거해도 됨 |
| **텔레그램** | **오직** ①사용자 결정 필요 ②되돌릴 수 없는 동작 승인 ③심각한 문제(같은 실패 3회·paseo 장애·한도 소진) | 폰이 텔레그램으로 울리면 = 무조건 봐야 하는 것 |

- **보내기**: `.claude/orchestration/notify.sh "결정 필요: <상황 한 줄>. A=<안1> / B=<안2>?"`
- **답 읽기(막혔을 때만)**: 알림을 보낸 뒤 `ScheduleWakeup`으로 15~30분 간격 대기 루프를 걸고, 깨어날 때 `.claude/orchestration/notify.sh --check <offset>`으로 사용자의 답장을 읽어 이어간다. 평소(질문 없을 때)엔 폴링하지 않는다.
- **루틴한 "작업 끝남"은 텔레그램으로 보내지 않는다** — 그래야 텔레그램 알림이 드물고 의미 있게 유지된다.
- 설정(토큰·chat_id)은 `.claude/orchestration/notify.env`(gitignore). 새면 BotFather `/revoke` 후 갱신.
- 자동으로 정할 수 있는 것(원문에 답이 있는 것 등)은 알림 없이 진행한다(무인 결정 5등급 = autonomous-loop 스킬 `decision-policy`). 텔레그램은 그중 `BLOCKED`/`STOP` 등급에만.

## 6. 워커 브리프 규율 (TDD) — 자체완결

워커는 콜드 스타트다. 브리프에 반드시 포함:
1. 저장소 1줄 소개 + **읽을 파일 목록**(해당 플랜 `## Task N` 절 + 가리킨 `screen-behaviors.md` 규칙 줄범위 + `MIGRATION-LEDGER.md`). 워커가 큰 플랜을 자기 예산으로 읽는다.
2. **범위**: 어느 Task/규칙 ID까지. 경계 밖은 "건드리지 말 것"으로 명시.
3. **TDD**: RED(실패 테스트 먼저)→GREEN→REFACTOR. **테스트 한 줄에 규칙 ID 하나**, `assert`에 값 하나씩(빈 테스트·항상참 테스트 금지).
4. **DB**: `supabase migration up`만(`db reset` 금지). **focused 테스트만** 돌린다.
5. **커밋**: 매 GREEN마다. **자기 파일만 `git add`**(`git add -A` 금지 — 남의 미커밋 삼킴). 공용 파일(`routes.tsx`·`StaffShell`·`_ui`·공용 mockData·`main.py`)은 손대지 말고 코디에 보고.
6. 창구는 `Consumes:`/`Produces:`에 **이름**으로(우리말 서술은 기계가 못 봄). DB 칸 나오면 서버층 짝 확인.
7. **컨텍스트 게이트**: 시작·종료 `/context`. 40%부터 새 읽기·탐색 금지 → 가장 가까운 GREEN/커밋 후 남은 일을 보고. 50%+는 상태 저장·보고만.
8. **완료 신호**: 끝에 `DONE` + 무엇을 커밋했는지 1줄.

## 7. 병렬 워커 규율 (어기면 가짜 실패)

1. **같은 브랜치 기반·다른 파일**(화면별 route 폴더 격리) 또는 worktree 격리. **공용 파일은 워커 금지 → 코디가 병합 때 배선.**
2. **커밋은 코디네이터가** 완료 회수마다. 워커는 자기 파일만 add.
3. 워커는 **`supabase migration up`만**. **전체 회귀는 코디가 클린 DB(`supabase db reset`)에서 1회.** ⚠️ 코디가 검증을 반복하면 공유 DB가 오염돼 **가짜 실패**가 난다 — 리셋하면 사라지는 실패는 오염이지 버그가 아니다.
4. 한 웨이브 **병렬 워커 5개 이하**(리뷰 부하·사용량 창 공유). 화면 다수는 배치로 나눈다.
5. **마이그 번호 정본 = `MIGRATION-LEDGER.md`.** 플랜 산문 옛번호 무시, `Create: supabase/migrations/…` 줄과 원장만 믿는다.

## 8. 함정 (계속 적용)

- **공유 DB 오염 = 가짜 실패**. 워커 `db reset` 금지, 코디 회귀는 클린 1회.
- **`git add -A` 금지**, 공용 파일은 코디만.
- **환자 노출 문구**: "취소 요청 접수/등록" 금지 → **"상담(직원 확인)으로 연결"만**.
- **되돌릴 수 없는 동작은 눈에 덜 띄게**(빨간 버튼은 확인창 안에서만). **막다른 길 금지**(막으면 해결 경로 함께). **끌 수 없는 스위치 금지**. **개인정보 열거 방지**(맞든 틀리든 같은 화면).
- **이모지 금지** — 아이콘은 SVG `<symbol>`+`<use>`.
- **낡은 `⏳`/미결**을 그대로 믿지 말 것 — 주제어 grep 재확인. 확정 시 뒤집힌 쪽에 역참조.
- **데모는 규칙의 부분집합**이다(다 반영 안 함). 정본 = `screen-behaviors.md` 규칙. 화면은 "데모와 닮았나"가 아니라 "규칙 ID를 다 덮었나"로 판정한다.
